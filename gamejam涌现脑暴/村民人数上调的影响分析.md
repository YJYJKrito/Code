# 村民人数调整方案

> **本文基于反编译 `testgame` 得到的真实实现**，不是设计文档。
> 上一版分析是按设计文档写的（假设有关系表、标签、事件卡），与实际代码差距很大，已整篇替换。

---

## 0. 结论

> **起始 24，上限 80。**

### 这个数字是怎么来的（以及一版错误答案的更正）

第一版我写的是"上限 60"，理由是"出生区扩到 16×16"。**那个理由是错的**，它只回答了"几何上放得下"，没回答"为什么是 60 而不是 40 或 80"，而且它把两个不同的数字混成了一个：

| 数字 | 它由什么决定 |
|---|---|
| **人口上限**（`ResolveBirths` 里那个） | 由**地图能舒适呈现多少**决定 |
| **讣告能承受的死亡数** | 由**同期死亡的人数**决定，与人口上限无关 |

### 上限真正的功能

`ResolveBirths` 里那个上限只在一种情况下起作用，就是**制止生育**。它不决定人口——人口的平衡点是出生与死亡相等的地方，而**那是玩家的法律决定的**，这正是本作的核心。

所以上限不是平衡数字，它是**「玩得好的时候，村子最后会长到多大」**。

### 关键认识。上限只在玩得好的时候才会被碰到

```
法律差  →  死亡率高  →  人口萎缩  →  永远碰不到上限
法律好  →  死亡率低  →  人口增长  →  碰到上限
```

**「人口越多讣告越多」这个假设是错的。** 讣告过载发生在**低人口加高死亡率**的时候；高人口只在玩得好的时候出现，而玩得好的时候死的人本来就少（多是寿终）。

这个实现里 20 天内几乎没有人会老死（年龄最多增长 1 岁），所以**一局的死亡数基本由法律的恶劣程度决定，不由人口数决定**。

→ **上限应该设高，不是设低。**

### 那具体多高

| 约束 | 推算 |
|---|---|
| 出生间距 2（切比雪夫）→ 每人占 4 格，密度锁死 | 想加人只能扩面积 |
| 村庄占地图不超过 1/4 才像个聚落 | 1536 ÷ 4 = 384 格 → **96 人** |
| 出生区必须落在强制草地范围内 | 20×16 的区域 = 320 格 → **80 人** |

**取 80。**

## 1. 先纠正一个前提。人口现在不是固定的

很多人以为这个游戏是"固定 20 个村民"，实际不是。

| | 现状 |
|---|---|
| **起始人数** | 20（`CreateNewGame` 里硬编码了 20 个名字） |
| **增长方式** | 生育会调 `Array.Resize` 把数组撑大 |
| **出生速率** | `ResolveBirths` 每 240 tick 结算一次，而且**成功一胎就 `break`** → 每 2 天最多 1 个新生儿 |
| **人口上限** | 50（`granaryFood < 40 或 存活数 >= granaryCapacity / 10` 就停止生育） |
| **一局有没有终点** | **没有**。`tick` 一直累加，游戏可以无限跑 |

所以"20"只是**初始值**，村子自己会长。

### 但这里有一个断口

> **模拟层的人口能长到 50，地图上却最多只显示 20 个。**

`MapViewBinder.PlaceVillagers` 的实现是

```
VillagerWalker[] actors = FindObjectsOfType<VillagerWalker>();   // 场景里手摆了几个就是几个
for (i = 0; i < actors.Length && i < map.spawnTiles.Length; i++) // spawnTiles 固定 20 个
    actors[i].PlaceAt(...);
```

**两处都在 20 卡死。** 第 21 个村民出生之后，模拟里有他、讣告里会有他、地图上找不到他。

**这是一个 bug，不是一个设计选择。** 调人数之前必须先修它。

## 2. 性能不是约束（先把这个担心排除掉）

模拟是 O(N) 的。逐 tick 要遍历村民的地方只有四处，全是一趟线性扫描。唯一沾到 O(N²) 的是 `ResolveBirths` 里的 `FindPartner`，而它每 240 tick 才跑一次，而且找到第一个合适的就返回。

| N | 每 tick 的操作量级 | 占 1 秒 tick 预算 |
|---|---|---|
| 20 | 约 100 | 微不足道 |
| 100 | 约 500 | 微不足道 |
| **500** | **约 2,500** | **仍然微不足道** |

**别为了性能去限制人数。** 那是在优化一个不存在的问题。

唯一沾得上边的是 `Array.Resize` 有 20 处，但生育每 240 tick 最多一次，一局下来不到十几次，可以忽略。

## 3. 讣告的推送模型（它约束的不是上限，是"同期死亡并发"）

### 现状

死一个人就弹一个横幅，3 秒自动收。这是**推送式**的。

### 它约束的是什么

**不是「一局总共死多少人」，是「短时间内死多少人」。**

一篇横幅 3 秒，还要玩家读完才能收。**连续死 3 个人，横幅就已经开始叠了；连续死 10 个，玩家会直接放弃阅读。**

| 局面 | 同期死亡 | 玩家反应 |
|---|---|---|
| 老死为主（法律不错） | 一两天一个 | 每篇都读，记得住是谁 |
| 一次饥荒 | 一个窗口死 5–8 个 | 开始跳过，只挑名字眼熟的看 |
| 一次瘟疫 / 一次处决潮 | 同 tick 死 3 个以上 | **直接不看，死亡变成了背景音** |

### 所以它和人口上限是什么关系

**几乎没有关系。** 触发"同期死亡并发"的是**法律的恶劣程度**，不是村子有多大。

一个 80 人的村子在好法律下，一年也死不了几个；一个 20 人的村子在坏法律下，两三天就能死光。

> **原本我在这一节写了一张"死亡数随人口增长"的表，那是错的假设。**
> 这个实现里 20 天内几乎没人老死（年龄最多长 1 岁），死亡几乎全部来自饥饿、恐惧和夭折——**全都由法律直接决定**。

### 那横幅推送什么时候会坏

**在"大屠杀"局里坏。** 无论村子是 20 人还是 80 人，只要玩家立出一套会引发饥荒或处决潮的法律，横幅就会连成一片。

**所以讣告分层要修的是"大屠杀"这个场景，和调人数是两件独立的事。** 两件都该做，但不要指望靠压低人数来回避前者。

## 4. 真正的约束二和三

### 约束二 · 角色是手摆的

`VillagerWalker` 和 `VillagerActorView` 都是场景里的 MonoBehaviour，`villagerIndex` 是 `[SerializeField]`，**手填的**。

| 人数 | 现在怎么做 | 要不要改 |
|---|---|---|
| ≤ 30 | 场景里手摆 30 个，逐个填 index | 能忍 |
| 60 | 手摆 60 个，填 60 个 index | **会疯**，必须改成运行时实例化 |
| 100+ | — | 必须 + 对象池 |

改法不复杂（一个预制体 + 一个循环 + 一个池），但**这是上 60 之前必须先做的事**。

### 约束三 · 出生点的几何

出生点用的是 5×4 抖动网格，间距 2（切比雪夫距离），覆盖 10×8 格。

**间距 2 意味着每人占 4 格，密度是锁死的。** 想加人只能扩大面积，不能加密。

| 人数 | 网格 | 覆盖面积 | 够不够放 |
|---|---|---|---|
| 20 | 5×4 | 10×8 | ✓ 现状 |
| **24** | **6×4** | **12×8** | ✓ 不用改生成器几何 |
| 30 | 6×5 | 12×10 | ⚠️ 四角会落到强制草地上之外，被推到别处 |
| 60 | 8×8 | 16×16 | 要同时放大"村庄空地"那块强制草地 |

生成器里有一段强制在村庄中心周围铺草地的逻辑

```
if (村庄范围内 && 该格是水 && |x-23| + |y-15| <= 6) 改成草地
```

那个菱形半径 6 就是为 20 人准备的。加人必须把它一起放大，否则出生点会被 `FindNearestHabitable` 推到村子外面去，看起来像散落的豆子。

## 5. 推荐方案

### 起始 24，上限 80

**为什么起始是 24**

24 是**不改生成器几何**的前提下能加到的最大值。出生网格从 5×4 改成 6×4 刚好落在现有的强制草地上；再往上（30 人需要 6×5）四角就会落到草地外，被 `FindNearestHabitable` 推到村子外面，看起来像撒豆子。

而且 24 个人的名字，玩家还记得住。

**为什么上限是 80**

上限由**地图能舒适呈现多少**决定，不由讣告决定（§3）。生日间距 2 把密度锁死，所以只能按面积算。20×16 的出生区 = 320 格，每人 4 格 = 80 人，占地图约 1/5，仍然像个聚落而不是一片均匀铺开的人群。

**80 不是"村子必须长到 80"，是"长到 80 之前不用管"。** 大多数局根本碰不到它，只有法律写得好、死亡率压得很低的局才会撞上。

### 这条路的代价，要如实说

**村子会大到玩家认不过来。** 起始 24 时你认识每个人；跑到 80 时你只认识最近死的几个。

我倾向认为这是**好事而不是坏事**——它是一条真实弧线：

> **你在你的法律下把村子养大了，然后你不再认识他们了。**

这句话本身就是这个游戏想说的东西之一。

但如果你的判断是"认识每个人"必须保持到底，那上限不该超过 50，走的是**分层**那条路（见 §7）。

### 无论上限多少，讣告分层都该做（半天）

它解决的是**大屠杀局面**，和调人数是两件独立的事。

```
普通死亡    → 不弹横幅，只进「讣告历史」列表，列表里加一个红点
异常死亡    → 弹横幅。判定标准例如
              · 同一 tick 死了 3 人以上（瘟疫、处决）
              · 死者的死因直接指向某条法
              · 死者是村里最年长或最年幼的
              · 死者的子女数 ≥ 3（有家庭的人）
              · 累计死亡数每跨过 10 的倍数
```

**这一改带来两个好处。** 横幅回归成"值得停下来看一眼的事"，而"谁死了"从推送变成可检索——玩家去翻列表找某人的结局，比被动看横幅更有黏性。

**成本半天。** 它和人数调整互不依赖，先做哪个都行。

## 6. 要改哪些地方（`20` 硬编码在四个位置，必须同步）

| # | 位置 | 现在 | 改成 |
|---|---|---|---|
| 1 | `VillageSaveService.CreateNewGame` 的名字数组 | 20 个名字 | **24 个名字**（要多准备 4 个） |
| 2 | `VillageMap.SpawnCount` | `const int = 20` | 24 |
| 3 | `VillageMapGenerator.PlaceSpawns` 的网格 | 5×4 | 6×4 |
| 4 | 场景里的 `VillagerWalker` + `VillagerActorView` | 手摆 20 个 | 手摆 24 个，**或改成运行时实例化** |
| 5 | `ResolveBirths` 的人口上限 | `granaryCapacity / 10`（= 50） | `granaryCapacity / 10` 改成按新上限算，或者换成一个独立常量 |
| 6 | 生成器里的强制草地菱形半径 | 6 | 跟着出生区一起放大 |

**这六处必须一起改。** 只改其中几个的后果是：

- 只改 1 不改 2/4 → 新增的 4 个村民**在地图上不存在**
- 只改 2/4 不改 3 → 出生点会重叠，被 `FindNearestSpawn` 推得七零八落
- 只改 3 不改 6 → 一半出生点被推到村子外面

## 7. 如果以后要更多，或者想保住"认识每个人"

两条路，方向和代价不同。

### 路线甲。上限继续往上（80 → 150）

只是继续扩出生区。代价是**地图上的村庄会占掉半张地图**，看起来不再像个村子，而是一片均匀铺开的人群。而且要动 `VillageMapGenerator` 的强制草地逻辑，让村庄范围和地形生成配合。

**十天里不建议走这条。**

### 路线乙。村民分层（保住"认识每个人"）

```
有名有姓的  20–30 人   → 有头像、能被点、死亡时写讣告
背景人口    其余        → 只有数字，参与产出和消耗，死亡只计入统计
```

这不是偷懒，是这类游戏的通行做法。它保住的正是最要紧的那件事——**玩家能记住的永远是有限的几十个人，而那几十个人才是故事发生的地方。**

**但这是结构性改动，十天里做不了。** 现在的实现里没有"背景人口"这个概念，加了要动模拟、存档、UI 三层。

### 为什么现在不建议走乙

十天，一个人的工时。路线甲改动集中在六处硬编码（§6），大半天的活；路线乙要动三层，而且每一层都要重新测。

**如果以后时间宽裕，乙是对的。** 现在甲是能交付的那个。

---

## 8. 一句话

> **人数上限不是被性能卡住的，也不是被讣告卡住的。它由「地图上还摆不摆得下一个村子」决定。**
>
> 起始调到 24、上限调到 80，改动集中在六处（§6），大半天的活。
> 讣告分层是另一件独立的事，它解决的是大屠杀局面，成本也是半天。
