# 模拟层测试台 · 说明

> 把《立法村》的**模拟层**从 Unity 里剥出来，做成一个能跑的控制台程序。
> **一次 30 年 × 120 种子的全扫是 9 秒。**
>
> 它不是"再实现一遍"—— 抽的就是反编译出来的**真代码**：
> 真的 `CreateNewGame`、真的 `SimulateTick`、真的 `LawEngine`、真的 `Farmland`。

---

## 0. 它能回答什么问题

| 问题 | 对应扫描 |
|---|---|
| 改完之后，**不同的法条组能不能跑出不同结局**？ | `lawsets` |
| 33 条法里，**有几条真的对结局有影响**？ | `single` |
| 40 多个状态量里，**哪些在一局里真的会动**？ | `params` |
| 为什么村子会死？**死因是什么、从第几年开始、母亲有几个**？ | `yearly` |

后面所有平衡改动，都应该**先跑一遍再改**，改完**再跑一遍对比**。

## 1. 装起来（三步）

```bash
# ① 装 ILSpy 的命令行版（只需一次）
dotnet tool install -g ilspycmd

# ② 从游戏包体里的 DLL 重建测试台
python setup.py "E:\CODE\testgame\My village_Data\Managed\Assembly-CSharp.dll"

# ③ 跑
cd pscan
dotnet run -c Release -- lawsets 40
```

`setup.py` 做四件事：反编译 → 抽 23 个模拟类 → 抽建局代码 → 打实验开关。
**它会把每条 patch 的结果打出来。**

## 3. 四个扫描怎么读

### `lawsets [种子数]` — 最重要的一栏

```
dotnet run -c Release -- lawsets 40
```

**「活下来」的判定是末人口 ≥ 5。**

> **10.14 这一版已经做到 9/9 全活。**
> 所以这一栏现在的看点**不再是"活几个"，而是「组间差距有多大」** ——
> 如果各组末人口都挤在同一个数（比如都顶到上限），说明**又回到了"结局都差不多"**，只是从底端饱和变成顶端饱和。

三列都要看：
- **末人口=1 占比** —— 上一版是 4 个组 100%，现在是 0%
- **全程最低人口 中位** —— 村子**会不会掉下去再爬回来**。是 1 = 没爬回来（吸收态）；7–20 = 有回弹
- **末人口 最大值** —— 有没有**顶到人口上限**（当前上限 120）

### `single [种子数]` — 法条有没有意义

```
dotnet run -c Release -- single 40
```

**有效条数 / 33。上一版 7/33，当前 23/33 —— 目标是 ≥ 30/33。**

> 规律：这一栏和 `lawsets` 是联动的。
> 只要结局还被锁死，`single` 就一定低 —— **不要单独去调法条**。
>
> ⚠ 判定是**三元组完全相等**（最小/中位/最大都相同才算"无影响"）。
> 别改成"和中位数比"——那样会让一堆 6/10/15 的组被误判成有效（这个坑我踩过）。

### `params [种子数]` — 哪些参数在做设计时能用

```
dotnet run -c Release -- params 120
```

**判定列写「★ 基本不变」的，不要拿来做机制** —— 玩家看不见也影响不到。

> ⚠ 判定用的是"最大值和最小值差不到 5%"。**它是一个粗筛**。
> 例：`平均恐惧 7–23` 被判成"会动"，但它在**第 7 年之后就不动了** —— 这种要看 `yearly` 才能发现。

### `res` — 恐惧 / 税库 / 威信的分布

```
dotnet run -c Release -- res 20
```

给新机制定阈值用。**恐惧的实测分位是关键**：p50=5 · p90=12 · p95=27 · **p99=41** · max=93。

### `fixes` — 三个资源的候选改法

### `farm` — 耕地 / 荒地机制

```
dotnet run -c Release -- farm 12
```

看荒地有没有真的被开垦掉、开垦成本扫档。

### `yearly` — 逐年机制插桩（固定种子 7929）

```
dotnet run -c Release -- yearly
```

每年一行，含 **死因分布** 和 **合格母亲数**。**排错就靠它。**

现在会看到两件事：
- 死因栏几乎全是 `饥饿N`
- 合格母亲数在**第 3 年就归零，然后再也不动**

## 4. 改完之后的标准流程

```bash
# ① 改 Unity 工程 → 重新打包 → 拿到新的 Assembly-CSharp.dll
# ② 重建测试台
python setup.py "<新包体的路径>\My village_Data\Managed\Assembly-CSharp.dll"

# ③ 先确认测试台本身没错（看有没有 patch 报 [FAIL]）

# ④ 跑两个关键指标
cd pscan
dotnet run -c Release -- lawsets 40    # 看「组间差距」有没有被拉平（别只看活几个）
dotnet run -c Release -- single 40     # 看 23/33 有没有往上走
```

**别只看最终数字** —— 如果 `lawsets` 里各组的末人口都挤到上限附近，说明**只是从底端饱和换成了顶端饱和**。

### 想扫参数但不想重编 Unity？

改 `pscan/Config.cs` 里的默认值，再跑。**默认值就是当前构建的真实数值**，不动它 = 测的是真游戏。

```csharp
public static int BirthChildCap = 12;     // 生育子女上限
public static int DegradePct = 2;         // 耕地退化概率 %
public static int Immigration = 2;        // 移民：每次来几人（0=关）
public static int ImmThreshold = 25;      // 移民触发人口
public static int ImmGranary = 20;        // 移民的粮仓门槛 ★ 别设太高
```

## 5. ★ 当 patch 失败时

`setup.py` 打的是**字符串替换**。如果程序改动了那几行，会看到：

```
[FAIL] 生育子女上限 —— 找不到目标代码

*** 有 patch 没打上 ***
```

**这不是脚本坏了，是测试台和工程对不上了。** 处理顺序：

1. 打开 `setup.py`，找到 `PATCHES` 里报错的那一条
2. 看它的 `old` 字符串 —— 去反编译源码里搜一下，看现在长什么样
3. **判断：这是程序改对了，还是改错了？**
   - 改对了 → 更新 `old` 字符串（或者干脆把这条 patch 删掉，让工程里的值直接生效）
   - 没看懂 → **停下来问**，别硬猜

> ⚠️ **绝对不要无视 `[FAIL]` 继续跑。**
> 那意味着测试台测的是**和工程不一样的东西**，跑出来的数会误导人 ——
> 这比没有测试台糟得多。

## 6. 已知限制（不要相信的地方）

| 限制 | 说明 |
|---|---|
| **它跑的是反编译代码** | 读到的是 IL 还原出来的 C#，**不是原始源码**。变量名是 `num4` 这种。逻辑等价，但**行号对不上** |
| **它测的就是当前构建的真实现状** | **已修复的 bug 不在里面**（钳位 / 存档改活状态 / 暂停锁 10.14 都修了）—— 所以现在的数比上一版干净 |
| **它不跑渲染 / 存档 / UI** | 只有模拟层。读档往返、UI 显示都得在真游戏里验 |
| **判定阈值是粗筛** | 「基本不变」用的是 5% 极差，会漏掉"前 7 年会动、之后不动"这种 |
| **每年固定推 2920 tick** | 真游戏是按帧累积的，边界上可能有 ±8 tick 的差异 |
| **只测 20–120 个种子** | 中位数够用，**要看极端值就得加大种子数** |
