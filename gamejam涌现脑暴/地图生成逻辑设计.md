# 地图生成逻辑设计

> 目标：随机地形（草地 / 沙漠 / 水域 / …），每局不同，像沙盒游戏。
> 先说三个决定后面一切的前提，再给流水线。

---

## 0. 开写之前要拍板的三件事

### ① 「8×8 像素块」到底是最小**逻辑**单位，还是最小**渲染**单位？

这两个是完全不同的东西，混在一起会出大问题：

| | 逻辑格 | 渲染块 |
|---|---|---|
| 是什么 | 游戏规则看得见的格子。村民站在哪、哪块地能种、水挡不挡路 | 画一个格子的最小色块 |
| 现在设计里的值 | **24×16**（定版 D2 已定） | 还没定 |

**如果 8×8 是最小逻辑单位**：一屏就有上万格，20 个村民会变成几个像素大的点，你的核心（讣告、法槽）会被巨大的地图稀释掉。而且 AI 美术要画的是"每个地形的色块"，反而更费。

**推荐：两个网格分开。**
- **逻辑格 24×16**（保持定版不变），一格 = 一个地形类型
- **渲染时，一个逻辑格 = 4×4 个 8×8 色块**（32×32 像素）
- 那 16 个色块用同一个地形的**不同深浅**随机搭配 → 这就是你要的"纯色物块随机组合"的观感

**你想要的沙盒感，90% 来自「色块的随机搭配 + 地形的自然形状」，不来自"格子足够小"。** 后者只会让画面变糊。

### ② 地图要不要影响玩法？

**强烈建议：要。** 理由不是"更好玩"，而是——

> 你的游戏有一个**承载力模型**（`PROD_BASE` / `CROWD_K`），它现在是一个常数。
> **如果地图决定可耕地有多少，承载力就成了地图的函数。**
> 于是「同一个种子 → 同一个村子」这句话里，**地图本身**也成了一个变量。

这是白送的重玩性：换个种子，不只是换二十个人的性格，是换一整块地。

### ③ 地图**不存档**，只存种子

地图是种子的纯函数。存档里只写种子，读档时重新生成一遍。
→ 省掉存档体积、省掉版本迁移、省掉"存档里的地图和新版本对不上"这类 bug。

## 1. 生成流水线（八步）

每一步都是**纯整数、确定性、无浮点**（沿用现有 `Rng` 纪律）。

```
① 种子派生     master seed → 每层一个子种子
② 高程场       整数噪声，3 个八度
③ 湿度场       第二个噪声，另一个子种子
④ 生物群系     高程 × 湿度 → 查表得到地形类型
⑤ 水体细化     元胞自动机平滑（关键一步）
⑥ 河流         可选：高处找泉眼，随机游走下山
⑦ 约束修复     连通性 / 耕地配额 / 出生点
⑧ 验收与重掷   不合法就换个子种子重来
```

---

## 2. 每一步具体怎么做

### ① 种子派生

不要所有层都用同一个 `seed`，否则你调一个参数会**把整张地图重新洗一遍**，没法对比。

```csharp
ulong seedElev = Rng.Mix64(seed ^ 0x01);   // 高程
ulong seedMoist= Rng.Mix64(seed ^ 0x02);   // 湿度
ulong seedBiome= Rng.Mix64(seed ^ 0x03);   // 群系散点
ulong seedDet  = Rng.Mix64(seed ^ 0x04);   // 渲染细节
```

**子种子必须由 master seed 派生**，这样"同种子同地图"仍然成立。

### ② 高程场（整数噪声）

不要直接给每格随机一个高度——**那看起来是雪花噪点，不是地形**。

正确做法：**低分辨率点阵 + 插值**。

1. 铺一张 `8×8` 的点阵（比 24×16 的逻辑格粗），每个点用 `Rng` 取 `0..255`
2. 逻辑格 `(x,y)` 的高程 = 把点阵**双线性插值**上来
3. 叠 3 个八度：粗点阵给大势（山、谷），细点阵给细节，振幅逐层减半

整数插值（不用 float）：
```
v = (a * (256 - t) + b * t) >> 8     // t ∈ [0,256]
```

结果是一个 `0..255` 的高程图。**它决定海岸线和大块地形**。

### ③ 湿度场

同样的方法，换一个子种子。

高程决定"这里是不是水"，湿度决定"这里是草原还是沙漠"。

### ④ 生物群系分类（查表）

用 `高程 × 湿度` 查一张表：

| 高程 \ 湿度 | 干 | 中 | 湿 |
|---|---|---|---|
| **低** | **水域** | **水域** | **水域** |
| **中低** | 沙地 | **草地** | **草地** |
| **中高** | **沙漠** | 草地 | 林地 |
| **高** | 岩石 | 岩石 | 岩石 |

**先定死了四类：水域 / 沙漠 / 草地 / 岩石。** 林地之类以后再加。

阈值（建议先用这套，之后扫参）：
- 高程 `< 60` → 水
- 高程 `60..110` 且湿度 `< 70` → 沙漠
- 高程 `> 200` → 岩石
- 其余 → 草地

### ⑤ 水体细化 ★ 最关键的一步 ★

上一步出来的水是**散落的小点**，看起来像噪点。

**用元胞自动机把它连成片：**

```
重复 4 次：
    对每一格，数它 8 个邻居里有几个是水
    如果邻居里水 ≥ 5 个 → 这一格变成水
    如果邻居里水 ≤ 1 个 → 这一格变成陆地
```

**这一步把"雪花"变成"湖泊与岛屿"。** 十几行代码，纯整数，效果立竿见影。

> **这是整个设计里性价比最高的一步。** 你想要的"沙盒游戏那种地形"，视觉上的自然感主要来自这里。

### ⑥ 河流（可选，但建议做）

湖泊有了，但没有水系会显得死板。

1. 随机挑一个**高程高**的格子当泉眼
2. 每一步走向**八邻域里高程最低**的那格
3. 走过的格子标记成水
4. 走到地图边缘或走满 40 步为止
5. 可以生成 1–2 条

河流会把村庄**物理切开**——这对玩法是好消息，见 §4。

### ⑦ 约束与修复 ★ 别跳过 ★

**纯随机一定会生成玩不了的地图。** 必须加约束：

| 约束 | 为什么 | 怎么修 |
|---|---|---|
| **草地格数 ≥ 30%** | 草地对应当耕地。太少 → 承载力 ≈ 0 → 开局就饿死 | 不够就降低水域阈值重来 |
| **出生点之间必须连通** | 河把村庄切成两半，一半人永远拿不到粮仓 | 洪水填充检查；不行就搭一座桥，或把河往边上推 |
| **出生点脚下不能是水 / 岩石** | 村民站在湖里 | 就近推到最近的草地格 |
| **地图边缘不能大面积是水** | 看起来像孤岛，相机边界很丑 | 把最外两圈的高程抬高 |

### ⑧ 验收与重掷

```
尝试 N = 1..8：
    生成地图
    跑约束检查
    通过 → 采用
    不通过 → seed = Rng.Mix64(seed)，回到 ②

8 次都不过 → 用一张手工保底地图（保证能玩）
```

**重掷也必须是确定性的**（用 `Mix64` 递推，不要用时间）。否则"同种子同地图"就废了。

## 3. 视觉层：8×8 色块怎么用

逻辑格定下来之后，渲染层随便玩：

**① 每个地形给一套 3–5 色的调色板**

| 地形 | 调色板（示意） |
|---|---|
| 草地 | `#4A7C3F` `#5A8F4A` `#3E6B35` `#6BA05A` |
| 沙漠 | `#D9C08C` `#C9AE7A` `#E5CFA0` |
| 水域 | `#3A6B8A` `#44789A` `#2F5C78` |
| 岩石 | `#6B6B6B` `#7A7A7A` `#5C5C5C` |

**② 每格从那套调色板里挑一个**

```csharp
int v = Rng.Range(seedDet, 0, Rng.CH_MAP, tileIndex, 0, palette.Length);
```

一格渲染成 4×4 个 8×8 色块，16 个块各挑各的 → **这就是"随机组合"的观感**。

> ⚠️ **别让每个 8×8 块完全独立随机**，那又是噪点。
> 让同一格里的 16 个块有 70% 概率用主色、30% 概率用邻近色。**有主次才有质感。**

**③ 边界过渡（很便宜，效果很好）**

地形硬切会露出格子边。在两种地形的交界格上，用一张**固定的抖动图案**决定这一格的哪几个 8×8 块用邻居的颜色。

一次写好，所有边界都好看。

## 4. 玩法层：地形怎么接进现有模拟

分三档，按你的工时往上加。**第一档几乎零成本，第三档是真正的大收益。**

### Tier 0 · 承载力（几乎零成本，**建议必做**）

```
可耕地比例 = 草地格数 / 总格数
地图承载力 = 基准承载力 × (可耕地比例 / 参考比例)
```

**关键约束（否则会毁掉你已经校准好的数值）：**
> **要让「跨所有种子的平均值」保持不变。** 地图改变的是**方差**，不是**均值**。
> 否则你那 60 条测试里测"结局梯度""寄存器方差"的那几条会静默失准——**而且不会报错**。

具体做法：先算出跨 100 个种子的平均可耕地比例当参考值，再按它归一化。

**顺带的好处**：现在"这局为什么饿死"有了一个**看得见的物理原因**——这村子的地本来就薄。

### Tier 1 · 空间化的关系表（中等成本，收益大）

现在的关系表 `rel[i*N+j]` 是一个**环**：村民 `i` 的"邻居"是 `(i+1)%N`。这是个抽象概念，玩家看不见。

**改成按地图距离算**：住得近的人形成关系，住得远的不形成。

于是「饥则抢：抢最近的邻居」**第一次真的是字面意思**——抢的是住他旁边的那个人。

而且：**河两岸会自然形成两个阵营**。敌对关系会因为地理而聚集，不是均匀撒开的。

这直接强化了你最想要的东西：**玩家能看出"为什么偏偏是他们俩打起来了"**。

### Tier 2 · 地形阻隔（成本较高）

水不能走 → 村民被河隔开 → 两岸的物资和恐惧传不过去。

好处是戏剧性极强（**河对岸的瘟疫传不过来，但粮仓也够不着**）。
代价是要写寻路，而且 20 个人在一张小图上寻路，收益未必抵得上工时。

**建议：18 天里不做。** 但要保证 Tier 1 的空间关系**照常跨水计算**（只是"过不去"这件事不模拟）。

## 5. 渲染：因为全是纯色，**整张地图就是一张贴图**

这是个很划算的推论：既然每个块都是纯色，那地图不需要 Tilemap、不需要几千个 GameObject。

**做法**：
1. 在加载时（或换种子时）算一次地图
2. 用 `SetPixels32` 把整张地图写进**一张 Texture2D**
3. `Apply()` 一次
4. 挂到一个 SpriteRenderer 上

**结果**：整张地图 = **1 个 draw call**，运行时零开销。

尺寸参考：逻辑格 24×16 × 32px = **768×512 像素**。一张 768×512 的 RGBA32 贴图 = **1.5 MB**。完全可以接受。

> ⚠️ 两个坑：
> - `SetPixels32` 是**左下角为原点**、且数组是**逐行**的。y 轴翻转是这里最常见的 bug。
> - `Apply()` 只在生成时调一次，**不要放进 Update**。

## 6. 确定性纪律（沿用你现有的那套）

| 规则 | 为什么 |
|---|---|
| **只用 `Rng.For / Range / Chance`** | 禁 `UnityEngine.Random`、禁 `System.Random` |
| **禁 float / double** | 噪声插值用 `>> 8` 定点，别用 `Mathf.Lerp` |
| **地图生成给一个专属 channel** | 比如 `CH_MAP = 8`，别和 `CH_VILLAGER` 混 |
| **子种子必须由 master seed 派生** | 否则"同种子同地图"不成立 |
| **重掷用 `Mix64` 递推** | 别用时间、别用计数器以外的东西 |

**加一条测试**（放进你现有的 `_tests`）：
> 同一个种子生成两次地图，**逐像素哈希相同**；不同种子生成，**≥80% 的地图不相同**。

| 河流条数 | 1–2 | |
| 最大重掷次数 | 8 | 超过就用保底地图 |

## 8. 约束检查与重掷（详细）

> 这一节是 §2⑦⑧ 的展开。**这块最容易写出"大部分时候能跑、偶尔卡死或生成废图"的代码。**

### 8.1 一条总原则：能修就不要重掷

| | 代价 | 什么时候用 |
|---|---|---|
| **修（Repair）** | 只改局部，快 | 改的是**局部异常** |
| **掷（Reject）** | 重跑整条流水线；通过率低时会连锁失败 | 改的是**全局比例 / 分布** |

**判据一句话**：*这个毛病是"某几个格子不对劲"，还是"整张图的构成比例不对劲"？*
前者修，后者掷。**试图靠修来改比例，会陷入"改了 A 又违反 B"的死循环。**

### 8.2 检查清单与处置

| # | 检查 | 判据 | 处置 | 为什么 |
|---|---|---|---|---|
| C1 | 水域占比 | ≤ 25% | **掷** | 全局比例 |
| C2 | 可居地占比 | ≥ 45% | **掷** | 全局比例。太低 → 承载力≈0 → 开局就饿死 |
| C3 | 边缘水 | 最外 1 圈的水格 ≤ 20% | **修**（抬高外圈高程） | 局部，重掷太浪费 |
| C4 | 出生点合法性 | 每个出生点脚下是可居地 | **修**（推到最近可居格） | 纯局部 |
| C5 | 出生点间距 | 两两切比雪夫距离 ≥ 2 | **修**（沿最小位移推开） | 纯局部，防重叠 |
| C6 | 连通性 | 见 8.4 | **修**（搭桥）/ 有条件放行 | 见下 |
| C7 | 出生点到水源 | 至少 60% 的出生点，8 格内有水 | **掷** | 全局分布 |

**C6 单独说**——因为它是一个真正的设计决策，不是技术问题：

> 一座被河切开的村子，看起来是 bug 还是 feature？

我的判断：**是被切开的村子是 feature，但切成 1 对 19 是 bug。**

规则：
- **默认要求全连通。** 不连通就搭一座 1 格宽的桥（成本最低的修复）。
- **但留一个开关**：允许**恰好一次**分裂，前提是**每个分量的出生点数 ≥ 4**。
  这样你会得到"河东三户、河西十七户"这种地理格局——**这正是 Tier 1 空间关系最出戏的地方**。
- 任何分量出生点 < 4 → 一律搭桥。

### 8.3 检查顺序：从便宜到贵

```
第 1 趟  O(n)  一趟扫完同时统计：C1 / C2 / C3
                └ 不过 → 立刻掷，后面全都不用算
第 2 趟  O(n)  查邻域：C7
第 3 趟  O(n)  洪水填充：C6          ← 最贵，放最后
第 4 趟  O(n²) 出生点两两距离：C5     ← n=20，只有 400 次，其实很便宜
```

**注意 C4/C3/C5 是"修"，所以要在检查之前做**（先修再查），而 C1/C2/C7 是"掷"，查不过直接 early-out。

正确的顺序是：
```
修 C3 → 修 C4 → 修 C5 → 查 C1 → 查 C2 → 查 C7 → 查并修 C6 → 复查一遍 → 出门
```
**最后那次"复查"不能省**——修复动作可能引入新的违规（抬高边缘 → 可居地变多 → 可能顺带改变连通性）。

### 8.4 洪水填充（连通性检查）

★ **用显式栈，不要递归。** 递归在边界情况下会爆栈，而且你现有纪律里"Tick 内不 new"的思路要求预分配。

★ **连通性用四邻域，不要用八邻域。** 八邻域会让村民从两个斜对角的格子之间"挤过去"，视觉上看起来像穿墙。

```
// compId: 预分配 int[W*H]，复用（每次 Array.Clear，不要重新 new）
// 返回连通分量数
int FloodFill(Map m, int[] compId, int[] stack)
{
    Array.Clear(compId, 0, m.W * m.H);
    int comps = 0;

    for (int start = 0; start < m.W * m.H; start++)
    {
        if (!m.Habitable(start) || compId[start] != 0) continue;

        comps++;
        int sp = 0;
        stack[sp++] = start;
        compId[start] = comps;

        while (sp > 0)
        {
            int cur = stack[--sp];
            int cx = cur % m.W, cy = cur / m.W;

            for (int k = 0; k < 4; k++)          // ← 四邻域
            {
                int nx = cx + DX4[k], ny = cy + DY4[k];
                if (nx < 0 || ny < 0 || nx >= m.W || ny >= m.H) continue;

                int ni = ny * m.W + nx;
                if (!m.Habitable(ni) || compId[ni] != 0) continue;

                compId[ni] = comps;
                stack[sp++] = ni;
            }
        }
    }
    return comps;
}
```

统计每个分量里有多少个出生点，一次遍历 `spawns[]` 就够。

### 8.5 搭桥（C6 的修复）

```
// 把两个分量接起来：从 A 里任取一格，从 B 里任取一格，
// 沿两点之间的直线（Bresenham）把路上的水格改成草地
void Connect(Map m, int tileA, int tileB)
{
    // ★ 选格规则必须全序：取分量里 **tile index 最小** 的可居格
    //   否则同一张图在不同平台可能连到不同位置 —— 见 8.7
    foreach (int t in BresenhamLine(tileA, tileB))
        if (m.IsWater(t)) m.Set(t, GRASS);
}
```

**桥要窄（1 格）**，而且**放在两个分量最近的一对格子之间**（而不是随便连），这样看起来像"村口那座桥"而不是一条莫名其妙的路。

### 8.6 主循环结构

```
Map Generate(ulong seed)
{
    ulong s = seed;
    int[] rejectBy = new int[NUM_CHECKS];      // 调参期用，统计每个检查拒了多少次

    for (int attempt = 0; attempt < MAX_ATTEMPTS; attempt++)   // MAX_ATTEMPTS = 8
    {
        var m = BuildRaw(s);          // §2 ①②③④⑤⑥：高程→湿度→群系→平滑→河流

        Repair(m);                    // C3 → C4 → C5（局部修复）
        var v = Check(m);             // C1 → C2 → C7 → C6（只读检查）
        if (!v.ok) { RepairConnectivity(m); v = Check(m); }     // C6 允许修一次再判

        if (v.ok)
        {
            m.usedSeed = s;           // ★ 把**实际用的**种子存下来，存档存它
            BakeTexture(m);
            return m;
        }

        rejectBy[v.firstFail]++;
        s = Rng.Mix64(s);             // ★ 确定性递推
    }

    return FallbackMap(seed);         // 8 次都不过 → 手工保底图
}
```

**两个必须注意的点**：

- **`m.usedSeed` 是"实际用的种子"，不是输入种子。** 存档要存它。否则读档时重新生成，重掷链不一样，就得到另一张图了。
- **重掷用 `Rng.Mix64` 递推**，不能用 `s + 1`（连续种子生成的图可能高度相关），也不能用时间。

### 8.7 确定性纪律：修复函数里的三个坑

这三个坑有个共同点：**它们在编辑器和真机上表现一致，但在两台机器上可能不一致**，而且不报错。

**① 平局必须全序。**
"推到最近的可居格"——如果最近的格有两三个，选哪个？
```
int best = -1, bestD = int.MaxValue;
for (int i = 0; i < W*H; i++)          // ← 从小到大遍历
{
    if (!m.Habitable(i)) continue;
    int d = Dist2(i, spawn);
    if (d < bestD) { bestD = d; best = i; }   // ← 严格小于：平局保留先遇到的（index 更小）
}
```
**用 `<` 而不是 `<=`，就等价于"平局取 index 最小者"。** 这是个全序，跨平台一致。
（这条和你现有的"排序必须给全序比较器"是同一条纪律。）

**② 不要用 `Dictionary` / `HashSet` 存分量。**
它们的迭代顺序不保证跨运行时一致。用定长数组 + 整数分量 id。

**③ 不要用 `Mathf` / `float` 算距离。**
`Dist2` 用整数平方距离。开方只在**显示**的时候做，绝不用在比较里。

### 8.8 ★ 重掷会移动均值 —— 必须补偿 ★

**这是这一节最重要的一条，而且不做的话你不会收到任何报错。**

重掷不是"过滤掉坏图"，它是**条件采样**：留下来的分布 ≠ 生成器的原始分布。

> 如果你拒绝了所有"可居地 < 45%"的图，那么**被接受的图的平均可居地比例，一定高于原始分布的平均值**。

后果：你的村庄会**系统性地偏富**——因为最瘦的地都被你扔掉了。而且是静默的。你那 60 条测试里测"结局梯度""寄存器方差"的那几条会慢慢失准。

**正确做法**：

```
1. 跑 2000 个种子，只统计【通过验收的】地图的可居地比例
2. REF_RATIO = 它们的平均值      ← 不是理论值 45%，是实测值
3. 承载力归一化：地图承载力 = 基准 × (本图比例 / REF_RATIO)
4. 加一条测试：跨 200 个种子的平均承载力，与"无地图基线"的差 < 5%
```

**一句话：基准要在"下游"测，不能在"上游"测。**

### 8.9 怎么调参：先量通过率，不要猜

调参期打开 `rejectBy[]`，跑 1000 个种子，看哪一项在拒：

| 现象 | 含义 | 该怎么办 |
|---|---|---|
| 总通过率 < 40% | 太严 | 先看谁在拒 |
| 某一个检查占了 > 60% 的拒绝 | 瓶颈 | **改生成参数**（噪声八度、成水阈值），**不是改阈值** |
| 全部通过率 = 100% | 约束形同虚设 | 说明生成器本来就温和，可以调狠一点 |

**建议目标：通过率 40%–80%。** 太低说明生成器参数和约束不匹配；太高说明约束没起作用。

**修改生成参数（而不是约束阈值）**才是对的——约束是"底线"，生成参数是"倾向"。

### 8.10 这一块要加的测试

放进你现有的 `_tests`（这几条都可以脱机跑，不需要 Unity）：

| # | 测试 | 断言 |
|---|---|---|
| T09_01 | 同种子两次生成地图，**逐像素哈希一致** | 完全相等 |
| T09_02 | 不同种子生成，地图不相同 | ≥80% 的种子的哈希互异 |
| T09_03 | 1000 个种子的**通过率** | ≥ 40% |
| T09_04 | 拒绝不集中在单一检查上 | 任一检查的拒绝占比 < 60% |
| T09_05 | 所有种子的出生点都在可居格上 | 无一例外 |
| T09_06 | 连通分量里最小分量的出生点数 | ≥ 4（或只有 1 个分量） |
| T09_07 | 不触发保底地图的比例 | ≥ 99%（1000 个种子里 ≤ 10 个用保底） |
| T09_08 | ★ **重掷后平均承载力 ≈ 无地图基线** | 差 < 5% |

> **T09_07 是最容易被忽略但最致命的一条。** 保底地图一旦频繁触发，玩家会周期性地看到**同一张图**——而他会立刻发现"这游戏的地图总是重复"。这个比例必须盯着。

## 9. 要你拍板的三件事

1. **逻辑格保持 24×16，还是真的要放大到像素级？**
   我强烈建议前者（理由见 §0①）。如果坚持后者，整套设计要重做——相机、村民尺寸、寻路、性能全部要重估。

2. **地形接玩法接到第几档？**
   我的建议：**Tier 0 必做 + Tier 1 做**。这两档加起来大概 1.5 人天，但它把"地图"从一个装饰变成了核心系统的一部分，而且是**直接喂给你正在做的那个承载力模型**。
   Tier 2 建议 18 天里不做。

3. **被河切开的村子，允许吗？**
   我的建议：**允许，但只允许一次，且每个分量至少 4 个出生点**（§8.2 的 C6）。它给 Tier 1 的空间关系白送了一个"河东三户、河西十七户"的格局。
   如果你觉得 18 天里不想承担这个复杂度，直接**一律要求全连通 + 搭桥**，也是完全可以的。
