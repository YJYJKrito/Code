# 法条扩展 · 实现方案（给程序）

> **配套**：`法条扩展目录.md`（设计视角，讲每条法为什么这么设计）。本文是**实现视角**。
> **目标**：法条库从 25 条扩到 **70 条**，其中 45 条是新增的。

---

## 0. 先说最要紧的一件事

**不要用现在的写法加法条。**

现在的做法是：`LawDefinition` 里 `condition` 和 `effect` 是**给玩家看的字符串**，真正的行为写在 `VillageLifecycleService` 里一堆按 id 硬编码的 if 分支。

```
LawCatalog 里写着   「饥则抢：饥饿 > 55 → 抢邻居 12 金币」
代码里              （没有任何分支引用 id = 2）
结果                玩家选中它，卡面描述清清楚楚，村庄毫无变化
```

**现在 25 条里有 15 条是这样。** 按同样的写法加到 70 条，会有 **60 条是空的**。

所以这份方案分两段。

- **第一段**：把「条件」和「效果」从显示字符串升级成**真正的数据结构**，配一个分发器。做完之后加法条就只是填表
- **第二段**：用新表实现 45 条新法

**第一段不做，第二段就是往一个漏的桶里加水。**

## 1. 目标架构

现在的 `LawDefinition` 只描述"给玩家看什么"，要让它同时描述"机器做什么"。

```csharp
public sealed class LawDefinition
{
    // ── 显示（已有）──
    public int    id;
    public string name;
    public string condition;      // 保留，给卡面用
    public string effect;         // 保留，给卡面用
    public string description;
    public int    category;
    public bool   hidden;
    public int    unlockType;
    public int    unlockThreshold;
    public int    treasuryCost;
    public string unlockHint;

    // ── 行为（新增）──
    public LawCond[]   conds;     // 全部满足才触发，空数组 = 恒真
    public LawEffect[] effects;   // 依次执行
    public int         cooldown;  // 触发后冷却多少 tick，0 = 不限
    public int         reserved;  // 未使用，留给以后
}

public struct LawCond
{
    public byte kind;    // CondKind
    public byte field;   // FieldKind
    public int  a;       // 阈值 / 第一参数
    public int  b;       // 第二参数
}

public struct LawEffect
{
    public byte kind;    // EffectKind
    public byte field;   // FieldKind
    public byte scope;   // ScopeKind
    public int  amount;
    public int  chance;  // 触发概率百分数，100 = 必定
}
```

**判据**：任何一条法，如果它的行为用 `conds + effects` 表达不出来，那说明缺一个原语——**加原语，不要加 if 分支**。原语是可复用的，if 分支是一次性的。

## 2. 原语清单

### 2.1 `FieldKind`（可读写的数值）

```
0  Hunger      饥饿
1  Fear        恐惧
2  Gold        金币
3  Food        个人存粮
4  Children    子女数
5  Age         年龄
6  Gender      性别
7  Granary     公共粮仓
8  Treasury    税库
9  Prestige    威信
10 Alive       存活（只读，用于判定）
11 BirthCd     生育冷却
```

### 2.2 `CondKind`（条件，13 个）

| id | 名字 | 参数 | 含义 |
|---|---|---|---|
| 0 | `SelfGt` | field, a | 自身 field > a |
| 1 | `SelfLt` | field, a | 自身 field < a |
| 2 | `SelfEq` | field, a | 自身 field == a |
| 3 | `NeighborGt` | field, a | 相邻者 field > a |
| 4 | `AliveGt` | a | 存活人数 > a |
| 5 | `AliveLt` | a | 存活人数 < a |
| 6 | `CountGt` | field, a, b | 存活村民中 field > a 的人数 > b |
| 7 | `AvgGt` | field, a | 存活村民的 field 平均值 > a |
| 8 | `ResLtPopTimes` | field, a | 资源 field < 存活人数 × a |
| 9 | `Periodic` | a | tick % a == 0 |
| 10 | `DeathsThisTick` | a | 本 tick 死亡人数 ≥ a |
| 11 | `HasLaw` | a | 已装 id == a 的律法 |
| 12 | `NearestEdge` | a | **保留**，见 §6 的邻接说明 |

> **`SelfGt` / `SelfLt` / `SelfEq` 是三个而不是一个**，因为条件里的比较方向是数据，不是代码。加一个 `opField` 也行，两种都行，选一种写死。

### 2.3 `ScopeKind`（效果作用对象，6 个）

```
0  Self        自己
1  Neighbors   相邻两人 (i+1)%N 和 (i+N-1)%N
2  All         全体存活村民
3  Granary     公共粮仓
4  Treasury    税库
5  Prestige    威信
```

### 2.4 `EffectKind`（效果，13 个）

| id | 名字 | 参数 | 含义 |
|---|---|---|---|
| 0 | `Add` | scope, field, amount | 给某范围的 field 加 amount（可为负，带 0..99 软钳位） |
| 1 | `Move` | scope→Self, field, amount | 从 scope 转移 amount 到自身（粮仓/邻居/税库） |
| 2 | `Drain` | Self→scope, field, amount | 从自身转移 amount 到 scope（征粮、遗产） |
| 3 | `Steal` | field, amount | 抢相邻者的 field（不足则全拿） |
| 4 | `KillSelf` | — | 杀死自己 |
| 5 | `KillMaxOf` | field | 杀死 field 最高的存活村民 |
| 6 | `KillYoungest` | — | 杀死年龄最小的存活村民 |
| 7 | `ModifyLawStrength` | a(槽位或 id), amount | 改另一条法的幅值 |
| 8 | `DisableLaw` | a(槽位或 id) | 让另一条法失效 |
| 9 | `ModifyBirthCd` | scope, amount | 改生育冷却 |
| 10 | `SetField` | scope, field, amount | 直接设值（不是加减） |
| 11 | `BroadcastFrom` | field, amount | 把自身 field 的差额广播给全体（哭丧） |
| 12 | `FillTo` | scope, field, cap | 补到某个上限（屯粮） |

**13 个条件 + 13 个效果 = 26 个原语，能表达 §5 的全部 45 条法。** 这个数量不大，而且写完一次之后所有法都受益。

## 3. 分发器

```csharp
private static bool EvalCond(VillageSaveData d, int i, in LawCond c)
{
    switch (c.kind)
    {
        case CondKind.SelfGt:      return ReadField(d, i, c.field) > c.a;
        case CondKind.NeighborGt:  return ReadField(d, (i + 1) % N, c.field) > c.a
                                       || ReadField(d, (i + N - 1) % N, c.field) > c.a;
        case CondKind.CountGt:     return CountAbove(d, c.field, c.a) > c.b;
        case CondKind.ResLtPopTimes: return ReadRes(d, c.field) < CountAlive(d) * c.a;
        // …其余同理
        default: return false;
    }
}

private static void ApplyEffect(VillageSaveData d, int i, in LawEffect e, int tick)
{
    if (e.chance < 100 && !Rng.Chance(d.rngSeed, tick, CH_LAW + (int)e.kind, i, e.chance)) return;
    switch (e.kind) { /* … */ }
}
```

主循环

```csharp
foreach (var law in activeLaws)
{
    if (law.cooldownLeft > 0) { law.cooldownLeft--; continue; }
    bool fired = false;
    for (int i = 0; i < aliveCount; i++)
    {
        if (!AllCondsPass(data, i, law.def.conds)) continue;
        foreach (var e in law.def.effects) ApplyEffect(data, i, e, tick);
        fired = true;
    }
    if (fired && law.def.cooldown > 0) law.cooldownLeft = law.def.cooldown;
}
```

**冷却字段是必须的。** 没有它，`哭丧` 这类法会在每个 tick 都触发一次，和处决形成自激振荡（见 `法条扩展目录` §9）。

## 4. 把现有 10 条法迁过来（验证架构够用）

**先只迁移这 10 条，不改任何行为。跑一遍对照，哈希必须完全一致。** 这是证明架构没写错的方式。

举三条做例子。

| 现有写法 | 表定义 |
|---|---|
| `law1 济贫`：`HasLaw(data,1) && hunger>45` → 免费从粮仓吃饭 | `conds=[SelfGt(Hunger,45)]`<br>`effects=[Move(Granary→Self, Hunger, 4)]`（粮仓−1 另行处理） |
| `law3 税收`：`tick%240==0 && HasLaw(3) && gold>60` → gold−12, granary+3, treasury+3 | `conds=[Periodic(240), SelfGt(Gold,60)]`<br>`effects=[Add(Self,Gold,−12), Add(Granary,3), Add(Treasury,3)]` |
| `law4 恐惧蔓延`：`tick%30==0 && HasLaw(4) && fear>45` → fear++ | `conds=[Periodic(30), SelfGt(Fear,45)]`<br>`effects=[Add(Self,Fear,1)]` |

**十条全部迁移完，逐条比对行为一致之后，才动新法。**

### 5.5 法改法（id 44–49）★ 需要 `lawStrength[5]`

**这一组要先加一个字段**

```csharp
public int[] lawStrength = new int[5];   // 与 lawIds 等长，初值全 0
```

结算时，每条法的 `amount` 乘以系数

```csharp
int scale = 100 + Mathf.Clamp(lawStrength[slot], -100, 100);
amount = amount * scale / 100;
```

**`Clamp` 是必须的。** 没有它，`峻法` 会在几十 tick 内把 `lawStrength` 推到几千（见下）。

| 46 | **缓征** | `CountGt(H,70,4)` | `ModifyLawStrength(税收槽,−2)` `ModifyLawStrength(济贫槽,+2)` | 240 |
| 47 | **整肃** | `CountGt(F,50,5)` | `ModifyLawStrength(医药槽,−3)` `ModifyLawStrength(劳役槽,+2)` | 240 |
| 48 | **威权** | `SelfGt(Prest,80)` | 对所有活跃槽 `ModifyLawStrength(槽,+1)`、`Add(Prest,−5)` `Add(Treas,−8)` `Add(Gran,−2)` | 60 |

> **凡是"给另一个数持续加值"的法，必须有冷却或者钳位。** 这一条在 `法条扩展目录` §6.3 里是设计约束，在这里是**实现上的硬要求**。

| 68 | **连坐** | `本 tick 邻居死了` **见注** | `Add(Self,Fear,8)` | 0 |
| 69 | **守望** | `SelfGt(Food,10)`, `NeighborGt(H,70)` | `Move(Self→Neighbor, Food, 3)` `Add(Self,Fear,−2)` | 0 |
| 70 | **共井** | `相邻者存活` | 双方存活时 `Add(Self,Hunger,−1)`；自己存活而邻居死亡时 `Add(Self,Hunger,2)` | 0 |

> **注**：`66` 的条件是"邻居的 F 比自己高 15 以上"——比较的两个对象一个是邻居一个是自己，**现有 `NeighborGt(field, a)` 只支持对常数**。加一个 `NeighborRelative(field, delta)`。
> `68` 需要"邻居本 tick 死亡"，`OnDeath` 的邻接版本。可以在 `65`（`57`）做 `OnDeath` 时顺带写一个"本 tick 死亡标记数组"，`68` 读它。
>
> 这是第七、第八个缺口。

## 6. 关于"相邻"的定义

现有的实现里唯一存在的空间关系是**数组下标相邻**。

```
村民 i 的邻居 = (i + 1) % N 和 (i + N - 1) % N
```

**这是环形的**，所以 0 号和 19 号（或 79 号）也是邻居。

**一定要写进卡面文案。** 玩家看不到数组，他看到的是一排村民，得让他知道"你左右的人就是你的邻居"。否则 `比邻` `阋墙` `连坐` 这几条法的行为在玩家眼里是随机的。

## 7. 自检工具（**这一节比 45 条法更重要**）

加一个开发期检查，遍历 `LawCatalog.Definitions`，逐条断言

```
1. 每条法至少有一个 cond 或一条 effect —— 否则是纯装饰
2. 每条法在 VillageLifecycleService 里被引用过 —— 否则是空法（就是现在这 15 条的死因）
3. 所有 id 唯一 —— 撞名的会静默覆盖
4. 所有 name 唯一 —— 同上
```

**做成一个菜单项，一键跑，结果打到 Console。** 每次加完法条跑一次。

**这 15 条空法不是一次失误，是「没有东西在防它」。** 这个工具做一次，以后就不会再漏。

## 8. 分阶段与工时

| 阶段 | 做什么 | 工时 | 验收 |
|---|---|---|---|
| **1** | 定义 `LawCond` / `LawEffect` / 原语枚举 + 分发器 | 0.5 天 | 编译通过 |
| **2** | **把现有 10 条有效法迁到表上**，逐条比对行为一致 | 0.5 天 | **同一 seed 跑 2000 tick，迁移前后哈希完全一致** |
| **3** | 把现有 15 条空法**补齐或删掉** | 0.3 天 | 自检工具报 0 条空法 |
| **4** | 实现 §2 之外发现的 8 个缺口原语 | 0.4 天 | — |
| **5** | 填 §5 的 45 条新法 | 0.8 天 | 自检工具全绿 |
| **6** | 调参（大概率需要，见下） | 0.5 天 | 见验收 |
| | **合计** | **≈3 天** | |

### 第 2 步是整个方案的地基

**迁移前后哈希必须完全一致。** 如果不一致，说明表定义和原来的 if 分支行为不等价，**这时候停下来查，不要往下走**。带着一个不等价的架构往下加 45 条法，后面出问题你分不清是新法的锅还是架构的锅。

### 第 6 步不能省

45 条法会显著改变数值平衡。加完之后必须重新跑一遍标定，确认：

- [ ] 存活人数的**跨 seed 标准差**没有塌掉（塌了 = 系统退化到不动点）
- [ ] 结局不是非 0 即满（两极占比 ≤ 55%）
- [ ] 不存在某一条法一装就赢（单法 dominance）
- [ ] 不存在某一条法装了等于没装（再跑一次自检）

**第 3 条最容易出。** 45 条新法里有几条（`峻法` `威权` `序齿`）是给别的法加幅值的，**它们一旦失控，整套法律系统会被一条法主宰**。所以 `lawStrength` 的钳位不是可选项。
