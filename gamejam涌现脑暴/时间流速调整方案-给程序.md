# 时间流速调整方案（给程序）

> **目标**：默认 **20 游戏日 / 真实秒**；日历改成 **360 天一年**；**最低档要能看清个人**。
>
> ⚠️ **这份方案里有一个致命岔路。** 走错了会把全部已标定的数值一次毁掉。见 §1。

---

## 1. ★ 核心决定：日历必须和动力学解耦 ★

### 1.1 `TicksPerYear` 不只是"一年有多少 tick"

现在它等于 **2400**，而工程里所有周期常数都是相对它定的

```
吃饭        每 20 tick
恐惧        每 30 tick
粮仓结算    每 60 tick
夭折判定    每 120 tick
生育/税收/劳役 每 240 tick
生育冷却     720 tick   （= 2400 的 0.3 倍 = 0.3 年）
```

**`TicksPerYear : 各周期` 这一组比例，就是全部动力学。** 改了分子不改分母，动力学就变了。

### 1.2 走错路的后果（**算给你看**）

如果按直觉把 `TicksPerYear` 从 2400 改成 360×120 = 43,200，而周期常数不动

| 机制 | 现在（每年） | 改错之后（每年） | 后果 |
|---|---|---|---|
| 生育冷却 720 tick | 0.3 年 | **0.017 年** | 一个女性**一年能生 60 次** |
| 夭折判定每 120 tick | 20 次 | **360 次** | `1 − 0.98³⁶⁰ = 99.9%` → **每个婴儿必死** |
| 税收每 240 tick | 10 次 | **180 次** | 税库爆炸 |
| 吃饭每 20 tick | 120 次 | **2,160 次** | 粮食消耗涨 18 倍（产出也涨，勉强抵消） |

**改完的瞬间经济就崩了。** 这不是"需要重新调参"，这是"整局跑不起来"。

### 1.3 正确的做法

> **`TicksPerYear` 一个字不动（2400），新增一个纯显示的 `DaysPerYear = 360`。**

```
TicksPerYear = 2400      ← 动力学单位，不动
DaysPerYear  = 360       ← 新增，只影响"第几天"这个显示
```

**同一个 tick 数，被解释成 18 倍多的"天"。动力学完全不变。**

## 2. 速率换算

```
目标        20 游戏日 / 真实秒
1 游戏年    = 360 ÷ 20 = 18 真实秒
tick 速率   = 2400 ÷ 18 = 133.33 tick/秒
```

**注意是 133 tick/秒，不是 2400。** 因为在新日历里 20 "天"只占 20/360 = 1/18 年。

### 各机制的实时频率（都会变得可见）

| 机制 | tick 周期 | 133 tick/秒下 | 玩家能不能看清 |
|---|---|---|---|
| 吃饭 | 20 | **6.7 次/秒** | 看得见 |
| 恐惧变化 | 30 | 4.4 次/秒 | 看得见 |
| 粮仓结算 | 60 | 2.2 次/秒 | 看得见 |
| 夭折判定 | 120 | 1.1 次/秒 | 看得见 |
| 生育 / 税收 | 240 | 0.6 次/秒 | 看得见 |
| 长一岁 | 2400 | 每 18 秒 | 看得见 |
| 老死 | 每年生日 | 每 18 秒一次机会 | 看得见 |

**没有任何一个快到看不见。** 这一点是设计上舒服的。

## 3. 要改的清单

### 3.1 日历层（`VillageTime.cs`）

```csharp
// ── 现在 ──
public const int TicksPerDay = 120;
public static int ToDay(int tick) => tick / 120 + 1;
public static string FormatDayTime(int tick)
{
    int num = Math.Max(0, tick);
    int num2 = ToDay(num);
    int num3 = num % 120 * 6;
    num3 = (num3 + 480) % 1440;
    return "第 " + num2 + " 天 · " + (num3/60).ToString("00") + ":" + (num3%60).ToString("00");
}

// ── 改成 ──
public const int TicksPerYear = 2400;    // 从 VillageLifecycleService 挪过来，统一放一处
public const int DaysPerYear  = 360;

public static int ToDay(int tick)
    => (int)((long)Math.Max(0, tick) * DaysPerYear / TicksPerYear) + 1;

public static string FormatDayTime(int tick)
{
    long t = Math.Max(0, tick);
    int day = (int)(t * DaysPerYear / TicksPerYear) + 1;
    // 一天之内的进度，单位是 1/TicksPerYear 天
    int frac = (int)(t * DaysPerYear % TicksPerYear);      // 0 .. 2399
    int minutes = frac * 1440 / TicksPerYear;              // 0 .. 1439
    return "第 " + day + " 天 · " + (minutes/60).ToString("00") + ":" + (minutes%60).ToString("00");
}
```

> ⚠️ **必须用 `long` 做中间量。** `tick * 360` 在 tick 超过 600 万时会溢出 `int`。
>
> **顺手修一个现存的小 bug。** 现在的 `tick % 120 * 6` 最大只有 `120 × 6 = 720`，而 24 小时是 1440 分钟 —— **那个时钟只覆盖了 12 小时**。改成上面的写法之后会正确覆盖 24 小时。

### 3.2 生育冷却的显示

`VillagerStatusPanelController` 里

```csharp
// ── 现在 ──
" 生育冷却约 " + Mathf.CeilToInt((float)save.villagerBirthCooldown[index] / 120f) + " 天"

// ── 改成 ──
" 生育冷却约 " + (save.villagerBirthCooldown[index] * VillageTime.DaysPerYear / VillageTime.TicksPerYear) + " 天"
```

**注意数值会变大。** 720 tick 原本显示 6 天，现在显示 **108 天**。这**不是 bug**——在新日历里 720 tick 本来就等于 108 天（约 3.6 个月），一年的 0.3 倍，和原来完全一致。

### 3.3 速率层（`VillageUiController.UpdateSimulation`）

```csharp
// ── 现在 ──
_tickAccumulator += Time.deltaTime;          // deltaTime 已被 timeScale 缩放
while (_tickAccumulator >= 1f && num < 20)   // 1 秒 1 tick，每帧最多 20
{
    VillageLifecycleService.Advance(currentSave, 1);
    _tickAccumulator--;
    num++;
}

// ── 改成 ──
_tickAccumulator += Time.unscaledDeltaTime * _ticksPerSecond;   // ★ 不走 timeScale
while (_tickAccumulator >= 1f && num < MAX_TICKS_PER_FRAME)
{
    VillageLifecycleService.Advance(currentSave, 1);
    _tickAccumulator -= 1f;
    num++;
}
if (num == MAX_TICKS_PER_FRAME) _tickAccumulator = 0f;   // 防止落后越积越多
```

```csharp
private const int MAX_TICKS_PER_FRAME = 200;   // 从 20 提到 200
private float _ticksPerSecond = 133.33f;       // 由速度档位设置
```

### 3.4 ★ `Time.timeScale` 必须和 tick 速率解耦 ★

**现在 `Time.timeScale` 就是速度档位**

```csharp
private void SetSpeed(int speed, ...)   // speed ∈ 1..3
{
    Time.timeScale = speed;              // ← 直接当倍速用
}
```

**改成 133 之后不能这么干**，因为 `Time.timeScale` 还管着

- `VillagerWalker.Update` 里的 `speed * Time.deltaTime` → **村民会瞬移**
- `PanelReveal` / `PressFeedback` 之类的 UI 动效

```csharp
// ── 改成 ──
private void SetSpeed(int tier, bool savePreference = true)
{
    _ticksPerSecond = DAYS_PER_SECOND[tier];                    // 4, 8, 20 天/秒 → tick 速率
    // 表现层单独给一个封顶的倍率，村民走路才不至于瞬移
    Time.timeScale = Mathf.Clamp(_ticksPerSecond / 133.33f, 1f, 4f);
}
```

> **`Clamp(..., 1f, 4f)` 这个上限是必要的。** 村民的游荡是纯表现（`VillagerWalker` 不碰 `VillageSaveData`），但它用 `Time.deltaTime`。不封顶的话 20 倍速下他们会以肉眼无法跟踪的速度乱窜。

### 3.5 速度档位（**用户要求：最低档要能看清个人**）

```csharp
// 下标 = 档位，值 = 每秒推进多少游戏日
private static readonly float[] DAYS_PER_SECOND = { 2f, 8f, 20f };
//                                                慢    中    快(默认)
```

| 档 | 天/秒 | tick/秒 | 一年耗时 | 用途 |
|---|---|---|---|---|
| **慢** | 2 | 13.3 | 180 秒 | **看清个人** |
| **中** | 8 | 53.3 | 45 秒 | |
| **快**（默认） | 20 | 133.3 | **18 秒** | 看一辈子的兴衰 |

**"慢"档为什么是 2 天/秒**。这个档下

```
吃饭     每 1.5 秒一次
恐惧变化 每 2.25 秒一次
长一岁   每 90 秒一次
```

**能盯着一个村民看他的饥饿数字一点点往上爬。** 这就是"看清个人"。

> ⚠️ **"慢"档下一辈子要跑 4.5 小时**，所以它不是用来玩一辈子的，是用来**观察某个人现在怎么了**。真正的"瞬间看清"还得靠刚做的**暂停 + 单步**。

### 3.6 存档

`VillageSaveData.speedMultiplier` 现在的语义是 1..3 档位，**不用改**（档位还是 1..3，只是每档代表的天数变了）。

## 4. ★ 三个会被高倍速打爆的地方 ★

这三处和"tick 速率"无关，是**假设了"1 秒 1 tick"**的代码。不提速没事，一提速就坏。

### 4.1 自动存档：会从每 30 秒变成每秒 4 次

```csharp
if (_ticksSinceSave >= 30)   // 现在 = 每 30 秒
{
    _ticksSinceSave = 0;
    GameSession.SaveCurrent();
}
```

**133 tick/秒下 → 每秒存档 4.4 次。** 每次都要 JSON 序列化整个 `VillageSaveData`（含 `Array.Resize` 过的讣告数组）再写盘。

**改成按真实时间**

```csharp
private float _secondsSinceSave;
...
_secondsSinceSave += Time.unscaledDeltaTime;
if (_secondsSinceSave >= 30f)
{
    _secondsSinceSave = 0f;
    GameSession.SaveCurrent();
}
```

**顺便说一句**：这个改动本身是对的，和速率无关——**存档间隔本来就该按真实时间，不该按 tick**。

### 4.2 讣告横幅：会被同一帧的多次死亡覆盖

```csharp
while (_tickAccumulator >= 1f && num < MAX_TICKS_PER_FRAME)
{
    int obituaryCount = currentSave.obituaryCount;
    LifecycleReport report = VillageLifecycleService.Advance(currentSave, 1);
    ...
    if (currentSave.obituaryCount > obituaryCount)
        ShowMessage(currentSave.obituaryTexts[num2].Replace("\n", " "), obituary: true, 6f);
    else if (!string.IsNullOrEmpty(report.eventText))
        ShowMessage(report.eventText, obituary: false, 4f);
    ...
}
```

**`ShowMessage` 在 tick 循环里被调用。** 一帧要跑 2 到 9 个 tick（慢档更少），**如果这一帧里死了 3 个人，横幅会被覆盖 3 次，玩家只看到最后一个。**

**改成攒起来，出循环之后一次性显示**

```csharp
// 循环外先清空
_obituaryBatch = 0;
_obituaryFirstIndex = currentSave.obituaryCount;

while (...)
{
    VillageLifecycleService.Advance(currentSave, 1);
    ...
}

// 循环之后统一处理
int newDeaths = currentSave.obituaryCount - _obituaryFirstIndex;
if (newDeaths == 1)
    ShowMessage(currentSave.obituaryTexts[currentSave.obituaryCount-1].Replace("\n"," "), obituary: true, 6f);
else if (newDeaths > 1)
    ShowMessage($"本刻有 {newDeaths} 人死去。", obituary: true, 6f);
```

> **这一改顺带解决了一个设计问题。** 一次死三个人，玩家看到的应该是"本刻有 3 人死去"这种**事件**，而不是三条被截掉的讣告。**聚合本身比逐条推送更对。**

### 4.3 每帧最多 tick 数

`num < 20`。133 tick/秒、60fps 下每帧只要 **2.2 个 tick**，`20` 是够的。

但**低端机掉到 15fps 时每帧要 8.9 个**，还是够。**但如果以后加更快的档位就不够了。**

建议提到 **200**，理由是"防落后"——`while` 循环里那句 `if (num == MAX) _tickAccumulator = 0f` 会丢掉积压，**丢积压比卡顿好**（时间会慢下来，但不会爆）。

## 5. 不受影响的（**明确列出，免得白改**）

| 东西 | 为什么不用动 |
|---|---|
| 吃饭 20 / 恐惧 30 / 粮仓 60 / 夭折 120 / 生育 240 | **全是相对 tick 的**，`TicksPerYear` 和 tick 速率都没改 |
| 生育冷却 720 / 父亲 360 | **它本来就代表 0.3 年**，新日历下还是 0.3 年 |
| 老死曲线（`OLD_AGE_ONSET/DIV/CAP`） | **按生日判定**，天然跟着 `TicksPerYear` 走 |
| `Rng` | 无状态，`(seed, tick, channel, seq)` 纯函数 |
| 存档结构 / 版本号 | `tick` 是 `int`，`villagerAgeTicks` 上限还是 2400 |
| 暂停 / 讣告历史 / 法律选择 | 和速率无关 |
| 律法解锁 / 税库 / 威信 | 和速率无关 |

**这一节比第 3 节重要。** 大部分人会本能地想去改那些周期常数——**一个都不用改**。

## 6. 验收

### 时间层

- [ ] 默认档下，**盯着"第 N 天"看：1 秒过去，数字加 20**
- [ ] 默认档下，**盯着一整年：18 秒**
- [ ] "慢"档下，**能看清一个村民的饥饿数字在涨**（约每 2 秒 +1）
- [ ] `ToDay` 在 tick = 2400 时返回 **361**（第二年的第一天）
- [ ] `FormatDayTime` 的时钟能覆盖 **00:00 到 23:59 全天**（现在只覆盖 12 小时）

### 动力学不变（**最重要**）

- [ ] **同 seed、同律法下，把速率调到最慢，跑 2400 tick，终局人口与改动前完全一致**
- [ ] 一局里长一岁的次数 = 跑过的 tick / 2400，**和速率无关**
- [ ] 生育总数在一局里和改动前同量级（**如果爆炸，说明 `TicksPerYear` 被误改了**）

### 基础设施

- [ ] 默认档下挂机 5 分钟，**存档次数 ≤ 10 次**（不是 1000 次）
- [ ] 一次死 3 个人时，**横幅显示"本刻有 3 人死去"**，而不是只显示最后一个
- [ ] 默认档下帧率不掉、GC 不抖
- [ ] 切档、暂停、存档、读档都不出问题

## 8. 一句话

> **`TicksPerYear` 是动力学的单位，不是日历的单位。**
>
> **想改日历就加一个 `DaysPerYear` 用于显示，别去动它。**
> **动它一下，生育率涨 18 倍、婴儿全部夭折——而且不会报错，只会让游戏变得"玩不了"。**
