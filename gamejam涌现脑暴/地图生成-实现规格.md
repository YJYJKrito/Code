## 三条最重要的连带影响

**① §6 渲染整节作废重写。** Bayer 抖动矩阵、调色板、4×4 色块那一套**全部不要了**——那是为了在"没有美术"时用程序化方式造出地形感。现在有真实拼图了，渲染变成「查表选变体 + 贴上去」。

**② §12.3 P1-3「相机可以砍掉」改判。** V1 的理由是「768×512 在 1080 基准下整图一屏放得下」。**现在贴图是 1536×1024，"世界"区只有 568 高——放不下了。** 相机、平移，都得做，那半天省不掉。

**③ 地形种类换了两个。** 岩石（Rock）没有美术，**删掉**；沙地（Sand）也没有，**删掉**。新增**树木**（V1 说"推不出来"而砍掉的那个）和**耕地**（V1 里是草地的一个属性，现在独立成一类）。

> ⚠️ **改地形枚举 = 改 `MAPGEN_VERSION`。** V1 的存档读进来会换图。见 §12.1 P0-2。

## V2 不需要改的

污染检查口径、channel 分配机制、元胞自动机、河流游走、约束检查与修复的整体结构、确定性纪律、Tier 0/1 接法——**这些全部照旧**。V2 改的是**尺寸、种类、和渲染**。

## 2. 数据结构

### `Sim/Terrain.cs`

```csharp
public static class Terrain
{
    public const byte Water     = 0;
    public const byte Grass     = 1;   // ★ V2 重排
    public const byte Desert    = 2;
    public const byte Farmland  = 3;   // ★ V2 新增（原 Rock 的生态位）
    public const byte Trees     = 4;   // ★ V2 新增（原林地）
    public const byte Wasteland = 5;   // ★ V3 新增（高海拔，可开垦）
    public const int  COUNT     = 6;

    /// <summary>村民能不能站在这格上。水域不行，其余都行。</summary>
    public static bool Habitable(byte t) => t != Water;

    /// <summary>算不算可耕地（Tier 0 的承载力只看这个）。</summary>
    public static bool Arable(byte t) => t == Farmland;   // ★ V2 改动

    /// <summary>这类地形有几张变体图（渲染层用，见 §6）。</summary>
    public static int VariantCount(byte t) => t switch
    {
        Grass     => 6,
        Farmland  => 4,
        Trees     => 3,
        Water     => 4,
        Desert    => 2,
        Wasteland => 4,   // ★ V3
        _         => 1,
    };

    /// <summary>★ V3：能不能被《开垦》变成耕地。</summary>
    public static bool Tillable(byte t) => t == Grass || t == Wasteland;
}
```

> **可以直接重排编号，不用留空位。**
>
> ⚠️ **但 V3 之后理由变了。** V1/V2 的理由是「地图不存盘，所以世界上不存在一份按下标存的旧地形数组」——**V3 之后地图会存盘了**（§2.5）。
>
> **V3 仍然可以重排编号**，因为 `MAPGEN_VERSION` 就是不匹配作废重生的机制：版本号对不上，旧地形数组直接丢掉。
>
> 所以 `Sand` 和 `Rock` **直接删掉**，不留墓碑。`Wasteland` 占 5。
>
> **`MAPGEN_VERSION` 必须 +1**（→ **3**）——这是**唯一**保证"玩家昨天存的档不会在今天静默换一张图"的东西。

> **「可居」与「可耕」是两件事，别混。** 沙漠和树木能站人（可居），但不产粮（不可耕）。设计文档里"草地 ≥30%"和"可居地 ≥45%"两个数打架，就是因为这两件事没分开。
>
> **V2 的变化**：`Arable` 从 `t == Grass` 改成了 `t == Farmland`。**这是语义变更，不是等价替换**——耕地现在是独立的一类地形，由出生点派生（§4.7），不再等于"所有草地"。

### 2.3 六个种类与美术的对应

| 枚举 | 名 | 变体数 | 怎么来的 | 可居 | 可耕 | 可开垦 |
|---|---|---|---|---|---|---|
| `Water` | 水体 | 4 | 噪声 + 元胞自动机 + 河流 | ❌ | ❌ | ❌ |
| `Desert` | 沙漠 | 2 | 低地 + 低湿度 | ✅ | ❌ | ❌ |
| `Grass` | 草地 | **6** | 兜底 | ✅ | ❌ | **✅** |
| `Trees` | 树木 | 3 | 高湿度 | ✅ | ❌ | ❌ |
| `Wasteland` | **荒地** | **4** | **高海拔**（★ V3） | ✅ | ❌ | **✅** |
| `Farmland` | **耕地** | 4 | **出生点周围 + 被开垦的地**（§4.7） | ✅ | **✅** | ❌ |

**23 张地形图 + 房子 2 + 粮仓 2（建筑层，§2.4）= 27 张，和美术给的清单完全对上。**

> ★ **V3 变更**：新增 `Wasteland`（4 变体）。**它的生成规则和开垦/退化机制见单独文档** `荒地与开垦退化-实现方案-给程序.md`——那份文档还改了一条更重要的东西（**地图不再冻结**），**动手前必读**。

### 2.4 房子与粮仓（**不属于地形**）

**MapGen 不生成房子和粮仓。** 它们是模拟层/玩家建造的，和地形是**两层**。

MapGen 要做的只有一件：**把地形层交给渲染层，让上面还能叠一层建筑物**。

```csharp
// Game/MapRenderer.cs —— 合成两层
void Bake(GameMap m, IBuildingLayer buildings)
{
    for (int tile = 0; tile < GameMap.TILES; tile++)
    {
        int sprite = TileSprite(m, tile);       // ① 地形：查变体表
        Blit(sprite, tile);
        int b = buildings.SpriteAt(tile);       // ② 建筑：盖在上面，-1 表示没有
        if (b >= 0) Blit(b, tile);              //    房子 2 种 / 粮仓 2 种
    }
}
```

**渲染层不关心建筑从哪来**——它只接受一个「每格给一张图」的接口。模拟层怎么决定在哪盖房、盖哪种，是它自己的事。

> **为什么写这一条**：避免程序在 MapGen 里去找房子粮仓的图。**它们不在 `Terrain` 枚举里，也不该在。**

### `Sim/GameMap.cs`

```csharp
public sealed class GameMap
{
    public const int W = 48, H = 32, TILES = W * H;   // ★ V2：1536（原 384）
    public const int NEI = 4;                          // Tier 1 每个村民的地理邻居数

    /// <summary>★ 生成算法版本。改任何生成逻辑就 +1。存档里存一份，不匹配时作废本局。
    /// 【为什么必须有】你 jam 期间一定会改生成算法，而地图是种子的纯函数 ——
    ///   不比对版本的话，玩家昨天存的档今天打开会**悄悄换一张地图**，且不报错。见 §12.1 P0-2。</summary>
    public const int MAPGEN_VERSION = 3;   // ★ V3：地形枚举加了 Wasteland

    /// <summary>★ V3：这个数组**在游戏进行中会被改**（开垦/退化）。
    /// → 必须进 HashState，必须存档。见 §2.5。</summary>
    public byte[]  terrain;      // TILES，值域 = Terrain.*
    public short[] spawn;        // World.N 个，每个村民的格子下标
    public ulong   usedSeed;     // ★ 重掷之后实际用的种子

    // Tier 1：地理邻接表。neighbor[i*NEI + k]，-1 表示不足
    public short[] neighbor;

    // 派生量（避免每 tick 重算）
    public int arableCount;      // ★ V2：耕地格数（原来是草地格数）
    public int habitableCount;
    public int compCount;        // 连通分量数
    public int compMinSpawn;     // 最小分量里的出生点数
}
```

> **注意内存。** `terrain` 256 → **1,536 字节**（`byte[]`），`neighbor` 不变（跟村民数走）。`spawn` 不变。**地图本身还是很小的**，涨的只是渲染贴图（§8）。

### ★ V2 新增：变体不存进 `GameMap` ★

**变体（这一格用哪张图）不存字段，渲染时现算。** 理由是它属于表现层，见 §3 的 `CH_MAP_DETAIL`：

```csharp
// 渲染层每次取变体都现算，不缓存进 GameMap
int VariantAt(GameMap m, int tile)
{
    int n = Terrain.VariantCount(m.terrain[tile]);
    if (n <= 1) return 0;
    int v = Rng.Range(m.usedSeed, 0, CH_MAP_DETAIL, VariantSeq(tile), 0, n);
    return v;
}
```

**这样做的三个好处**：不进哈希（§3 的纪律）、不占存档、改变体数量不用动数据结构。

> **不要"改进 `GameMap` 加一个 `variant[]` 字段"** —— 那会把它拖进确定性校验的范围，而它对玩法零影响。

### 2.5 ★★ 地图必须进 `HashState` 和存档（**V3 改判**）★★

> ⚠️ **这一节推翻了 V1/V2 的结论。** V1/V2 说「地图开局冻结、不存盘」——**V3 之后那是错的**：开垦和退化每 tick 都在改 `terrain[]`。
> **完整论证在 `荒地与开垦退化-实现方案-给程序.md` §5。**

| 件 | V1/V2 | **V3** |
|---|---|---|
| `HashState` | 只进 `usedSeed` | **必须进 `terrain[]`** |
| 存档 | 只存 `usedSeed` + `MAPGEN_VERSION` | **必须存 `terrain[]`**（1536 字节 ≈ 2KB）|
| `arableCount` | 派生量 | **读档后必须重算**（不能直接读存档里的值）|

**为什么 `HashState` 必须进整份 `terrain[]`**：两台机器跑同一 seed，如果开垦/退化的顺序分叉了，**只哈希 `usedSeed` 是看不出来的**——而它会一路错下去，**不报错**。

**代价**：1536 字节 × 133 tick/秒 = 204,000 字节操作/秒 —— **可以忽略**。

**为什么存档存整个数组而不是"变更日志"**：变更日志要重放、要处理丢失、要保证顺序，**而整个数组只有 2KB**。

> ⚠️ **不要只哈希 `arableCount`。** 两张地图可能耕地数相同但形状不同，而形状影响 Tier 1 的地理邻接——**只哈希计数会漏掉分叉**。

## 3. 随机数：channel 分配

沿用现有 `Rng.For(seed, tick, channel, seq)`。地图生成**不走 tick**，一律传 `tick = 0`。

| channel | 常量名 | 用途 |
|---|---|---|
| 8 | `CH_MAP_ELEV` | 高程点阵 |
| 9 | `CH_MAP_MOIST` | 湿度点阵 |
| 10 | `CH_MAP_BIOME` | 群系抖动 |
| 11 | `CH_MAP_RIVER` | 泉眼与游走 |
| 12 | `CH_MAP_SPAWN` | 出生点锚点与抖动 |
| 13 | `CH_MAP_DETAIL` | ★ V2：**地块变体的选择**（表现层，不进哈希） |

> **`CH_MAP_DETAIL` 的语义在 V2 变了**：V1 是"4×4 个色块各挑各的颜色"，V2 是"这一格用这类的第几张变体图"。**位号不变，用途换掉。**

> **不再做"子种子派生"**（设计文档 §2① 那一套）。channel 已经提供了同样的隔离，两套机制叠着用只会让调参更难。**重掷时直接改 master seed，所有 channel 一起换**——这才是我们想要的。

`seq` 用格子的线性下标 `y * W + x`。这样每个格子有独立的随机流，且跨平台一致。

## 4. 生成算法

### 4.0 主流程

```
GameMap Generate(ulong seed)
{
    ulong roll = seed;
    for (int attempt = 0; attempt < MAX_ATTEMPTS; attempt++)   // MAX_ATTEMPTS = 8
    {
        var m = BuildRaw(roll);        // 4.1 ~ 4.5
        PlaceSpawn(m, roll);           // 4.6
        var v = CheckAndRepair(m, roll);// §5（先修局部，再查全局）
        if (v.ok)
        {
            m.usedSeed = roll;         // ★ 实际用的种子
            BuildNeighbors(m);         // §7.2 Tier 1
            return m;
        }
        RejectStat.Record(v.firstFail);
        roll = Rng.Mix64(roll);        // ★ 确定性递推
    }
    return FallbackMap(seed);          // 手工保底图，usedSeed = seed
}
```

### 4.1 高程场

**点阵尺寸（这一条设计文档里缺，现在定死）：**

| 八度 | 点阵（**V2**） | 振幅权重 |
|---|---|---|
| 1（大势） | **12×8** | 1/2 |
| 2（中景） | **24×16** | 1/4 |
| 3（细节） | **48×32** | 1/4 |

> ★ **V2 把三张点阵都翻倍了**（原来 6×4 / 12×8 / 24×16）。理由是**地形块的大小要跟着地图一起长**——如果点阵不动而地图翻倍，八度 3 的细节就变成 2×2 格一个点，地形会碎成噪点。**翻倍之后，每一档地形块的绝对格数不变，观感一致。**

点阵 `(lx, ly)` 的值 = `Rng.Range(roll, 0, CH_MAP_ELEV, ly * LW + lx, 0, 256)`，范围 `0..255`。

**双线性插值（整数，无浮点）：**

```
// tx, ty ∈ [0,256] 是该格在点阵单元内的位置
int top = ( v00 * (256 - tx) + v10 * tx ) >> 8;
int bot = ( v01 * (256 - tx) + v11 * tx ) >> 8;
int h   = ( top * (256 - ty) + bot * ty ) >> 8;
```

三个八度加权求和 → 高程 `0..255`。

> ⚠️ 中间乘法最大 `255 * 256 = 65280`，`int` 完全装得下。**但别用 `short`。**

### 4.2 湿度场

同 4.1，把 channel 换成 `CH_MAP_MOIST`。

### 4.3 群系分类（★ V2 重写：删岩石沙地，加树木 ★）

```
if      (elev < 60)                          → Water
else if (elev < 110 && moist < 70)           → Desert
else if (elev > WASTE_ELEV)                  → Wasteland  // ★ V3 新增，175 ≈ 11%
else if (moist > TREES_MOIST)                → Trees      // ★ V2 新增
else                                         → Grass
```

**五类由噪声直接定，第六类（耕地）由出生点 + 开垦派生（§4.7 / V3 文档）。**

> ★ **V3：`elev > WASTE_ELEV` 这一条必须排在 `Trees` 前面。** 高海拔优先判荒地，剩下的才看湿度长树——**否则高湿的高地会变成森林而不是秃岭**。

**V1 → V2 的三处变化：**

| V1 | V2 | 为什么 |
|---|---|---|
| `elev > 200 → Rock` | **删掉** | 美术没给岩石图。**高地现在靠树木表达**（高地通常湿度高） |
| `moist < 40 → Sand` | **删掉** | 美术没给沙地图。原来那条是「沙漠到草地之间的过渡带」，**现在沙漠直接接草地** |
| （无） | `moist > TREES_MOIST → Trees` | V1 说「林地推不出来」，那是因为它当时想用**两个场一起**推。**只用湿度就推得出来**：湿的地方长树 |

**`TREES_MOIST` 初值 = 165。** 估算依据：三层加权平均之后湿度大致落在 `127 ± 45`，取 165 大约对应 **15%–18% 的森林覆盖率**。

> ⚠️ **这个数必须实测。** 估算是按"均匀分布加权平均"推的，真实分布不一定对称。**按 §15.1 的流程先量通过率再定值**，不要照抄 165。

> **为什么树木只用湿度推、不看高程。** V1 的设计文档想用「高程 + 湿度」二维分区，结果推出来的林地和草地边界没法看。**一个轴能说清的事不要用两个。** 湿的地方长树，一句话就够，玩家一眼也看得懂。

### 4.4 水体细化（元胞自动机）

★ **必须双缓冲**：读旧图，写新图，一轮结束后整体交换。原地更新会产生**扫描线方向性伪影**（左上角的水会往右下角蔓延），这是这个算法的经典 bug。

```
buffers[0] = 当前地形；buffers[1] = 暂存
重复 4 次：
    for 每一格 (x,y):
        n = 8 邻域里 Terrain.Water 的个数        // 八邻域，这里用八邻域是对的
        if      (n >= 5) 新图[x,y] = Water
        else if (n <= 1) 新图[x,y] = Grass       // 注意：是变成草地，不是"变回原来的"
        else             新图[x,y] = 旧图[x,y]
    交换 buffers
```

> `n <= 1 → Grass` 而不是"保留原值"，是因为原值可能是 Desert/Trees，会让孤立格变成沙漠点或孤树。统一变草地更干净。
> ★ **V2 提醒**：CA 跑在**群系分类之后、`PlaceFarmland` 之前**（§5.2 的顺序），所以这里还见不到 `Farmland`。

### 4.5 河流

```
重复 1~2 次：
    泉眼 = 所有 Trees 格里用 Rng.Range(roll,0,CH_MAP_RIVER,0,count) 挑一个
           （V2：原来是挑 Rock，岩石没了改挑树木——山上长树，树多的地方出水，说得通）
           （没有 Trees 就挑 elev 最高的格）
    visited = 清零
    重复最多 40 步：
        标记当前格为 Water，visited[cur] = 1
        在八邻域里找 elev 最低、且 visited==0、且未出界的格
        没有这样的格 → 停（局部低点，正常结束）
        否则走过去
```

> ⚠️ **河流步数要跟着地图翻倍。** V1 是 40 步、地图 24 宽；V2 地图 48 宽，**40 步的河只有半张图长**。改成 **80 步**。`RIVER_STEPS = 80`。

> ⚠️ **`visited` 不能省。** 没有它，河流会在两个相邻的局部低点之间**来回震荡**，40 步全在打转，画出来是一坨 2 格的墨点。

### 4.6 出生点生成 ★ 设计文档里整段缺失 ★

**关键判断：这是一个「村庄」，不是一个撒豆场。** 村民应该聚成一片，而不是铺满整张图。

```
PlaceSpawn(m, roll):
    // ① 选锚点：可居格里用 Rng 挑一个
    //    偏好草地：先在 Grass 里挑，没挑到再退到全体可居格
    anchor = PickHabitable(roll, CH_MAP_SPAWN, seq=0)

    // ② 抖动网格：5 列 × 4 行 = 20，间距 4 → 覆盖 17×13 格   ★ V2：间距 2 → 4
    for (r = 0; r < 4; r++)
      for (c = 0; c < 5; c++)
        k = r * 5 + c
        jx = Rng.Range(roll,0,CH_MAP_SPAWN, 1000 + k, 0, 3) - 1   // -1..1
        jy = Rng.Range(roll,0,CH_MAP_SPAWN, 2000 + k, 0, 3) - 1
        tx = anchor.x - 8 + c * 4 + jx                             // ★ -4,c*2 → -8,c*4
        ty = anchor.y - 6 + r * 4 + jy                             // ★ -3,r*2 → -6,r*4
        spawn[k] = ClampToBounds(tx, ty) 的线性下标

    // ③ 逐格修复（§5.4 的 R1/R2/R3）
    FixSpawnLegality(m)     // 推到最近可居格
    FixSpawnOverlap(m)      // 按 k 升序，撞了就推到最近的空格
```

**为什么间距从 2 改成 4**：**保持村庄占地图的相对比例不变。**

```
V1   24×16 图，村庄占 10×8  = 42% × 50%
V2   48×32 图，村庄占 17×13 = 35% × 41%     ← 间距 4
     48×32 图，村庄占 10×8  = 21% × 25%     ← 间距 2 的话，村庄缩成一半
```

**间距 2 会让村庄在地图上缩成一个角**，四周全是和玩法无关的空白——**那就白扩了**。间距 4 让村庄在新地图上占的地方和 V1 差不多，多出来的地是**村庄周围的世界**，这才是「不拥挤」要的效果。

**切比雪夫距离 ≥4 时，17×13 的范围能放下 5×4 = 20 个位置**，所以网格本身无重叠，只有抖动 ±1 才可能撞上——§5.4 的 `FixSpawnOverlap` 兜底。

> ⚠️ **间距是 4 还是 6 需要实测。** 4 是按"保持相对比例"推的，但**它同时决定了耕地面积和承载力**（§4.7）。**按 §15.1 先量再定。**

### 4.7 ★ V2 新增：耕地（出生点派生）★

**耕地在群系分类（§4.3）里不出现**，它是**摆完出生点之后**才定的一块地。

```
PlaceFarmland(m):
    box = 所有 spawn 格的包围盒
    box = box 向外扩 FARM_MARGIN 格（初值 3）
    for 每一格 t in box:
        if (m.terrain[t] == Grass)      // 只清草地，不动水/沙/树
            m.terrain[t] = Farmland
```

**三条理由：**

1. **村庄必须挨着自己的田。** 如果耕地由噪声随机分布，会出现"村子周围一片沙漠、粮食在 30 格外"的图——玩家第一眼就觉得不合理。
2. **`Arable` 从此有明确语义**：它 = **这个村庄实际开出来的地**，而不是"地图上叫草地的部分"。
3. **★ 它把承载力从地图尺寸里解耦出来 ★**

**第 3 条最重要，展开说：**

> `FARM_MARGIN` 初值 3，box 17×13 → 耕地候选区 23×19 = 437 格，其中约一半是草地 → **实际耕地 ~200 格**。
>
> **这个数不随地图变大而变大**——因为村子没变大。所以：
>
| > | | V1 | V2 |
| > |---|---|---|
| > | 地图 384 → 1536（**×4**） | — | — |
| > | 耕地 ~190 → **~200（基本不变）** | | |
| > | **承载力的地图方差** | 大（耕地在整张图上浮动） | **小（耕地钉在出生点周围）** |
>
> **这是 V2 白送的一个好处**：§12.1 P0-1「地图的方差会掀翻承载力」**被这条大幅缓解**了。V1 必须给 `REF_ARABLE` 做全分布标定，V2 之后它的分布窄了很多。
>
> ⚠️ **但仍然要重新标定**——缓解不等于消除，耕地格数还是随锚点选在哪而变。

**`FARM_MARGIN` 是承载力的唯一旋钮。** 想调「这个村子能养多少人」，改它。**初值 3 需要实测**（§15.1）。

### 5.3 洪水填充（连通性）

```csharp
// compId / stack 预分配复用，不要每次 new
// 返回分量数；顺带统计每个分量里的出生点数
int FloodFill(GameMap m, int[] compId, int[] stack)
{
    Array.Clear(compId, 0, GameMap.TILES);
    int comps = 0;
    for (int start = 0; start < GameMap.TILES; start++)
    {
        if (!Terrain.Habitable(m.terrain[start]) || compId[start] != 0) continue;
        comps++;
        int sp = 0;
        stack[sp++] = start; compId[start] = comps;

        while (sp > 0)
        {
            int cur = stack[--sp];
            int cx = cur % GameMap.W, cy = cur / GameMap.W;
            for (int k = 0; k < 4; k++)            // ★ 四邻域，不是八邻域
            {
                int nx = cx + DX4[k], ny = cy + DY4[k];
                if (nx < 0 || ny < 0 || nx >= GameMap.W || ny >= GameMap.H) continue;
                int ni = ny * GameMap.W + nx;
                if (!Terrain.Habitable(m.terrain[ni]) || compId[ni] != 0) continue;
                compId[ni] = comps; stack[sp++] = ni;
            }
        }
    }
    return comps;
}
```

**连通性用四邻域，水体元胞自动机用八邻域。** 这不是笔误——八邻域连通会让村民从两个斜对角格子之间"挤过去"，看着像穿墙。

### 5.4 修复函数（每个"最近"都必须全序）

★ **每一步的平局都用「线性下标最小者胜」。** 只用 `<` 不用 `<=`，就自动是它。

```csharp
// R1 / R2 / R3：找一个合法的落点
int FindNearestTile(GameMap m, int from, Func<byte,bool> ok, bool[] occupied)
{
    int best = -1, bestD = int.MaxValue;
    for (int i = 0; i < GameMap.TILES; i++)          // ← 从小到大
    {
        if (!ok(m.terrain[i])) continue;
        if (occupied != null && occupied[i]) continue;
        int d = Dist2(i, from);
        if (d < bestD) { bestD = d; best = i; }      // ← 严格小于 = 平局取小下标
    }
    return best;
}

int Dist2(int a, int b)
{
    int dx = a % GameMap.W - b % GameMap.W;
    int dy = a / GameMap.W - b / GameMap.W;
    return dx * dx + dy * dy;                         // ★ 整数平方距离，不开方
}
```

**搭桥（C8）：**

```csharp
void Bridge(GameMap m, int compA, int compB)
{
    // 取两个分量里线性下标最小的可居格，沿 Bresenham 直线把中间的水改成草地
    // ★ 桥宽 1 格，方向取「两点间最短的那一对格」
    foreach (int t in BresenhamLine(cheapestA, cheapestB))
        if (m.terrain[t] == Terrain.Water) m.terrain[t] = Terrain.Grass;
}
```

**C8 的放行规则（已定：允许分裂）：**
- 分量数 == 1 → 通过
- 分量数 == 2 且 **两个分量的出生点数都 ≥ 4** → 通过（这就是"河东三户、河西十七户"）
- 其余 → 搭桥，把最小分量接到最大分量上

### 6.2 ★ 变体怎么选（这一节是 V2 唯一的新算法）★

**不能逐格独立随机。** 一格格掷骰子选变体，画出来是**满屏噪点**——V1 §6.2 那条「别让每个 8×8 块完全独立随机」的教训在这里一模一样成立。

**做法：变体也走点阵，让相邻格倾向于共用一张图。**

```
VARIANT_LW = 12, VARIANT_LH = 8      // 变体点阵，每个点覆盖 4×4 格
```

```csharp
int VariantAt(GameMap m, int tile)
{
    int tx = tile % GameMap.W, ty = tile / GameMap.W;
    byte t = m.terrain[tile];
    int n = Terrain.VariantCount(t);
    if (n <= 1) return 0;

    // ① 落到变体点阵上的哪个点（48/4 = 12，32/4 = 8）
    int lx = tx >> 2, ly = ty >> 2;
    // ② 每个点、每种地形一条独立随机流（乘 8 是给地形留位）
    int seq = (ly * VARIANT_LW + lx) * 8 + t;
    return Rng.Range(m.usedSeed, 0, Rng.CH_MAP_DETAIL, seq, 0, n);
}
```

**为什么点阵是 12×8 = 每 4×4 格一个变体**：

```
地图 48×32 → 12×8 = 96 个变体点
草地 6 种变体，96 个点 → 每种平均出现 16 次，分布够散
若改成逐格（1536 个点）→ 变体差异变成噪点，看不出"一片草地"
```

> ⚠️ **`VARIANT_LW=12` 是按 V1 的 4×4 块尺寸沿用的**（V1 一格 = 4×4 个块，V2 一个变体点 = 4×4 格，**尺度感一致**）。
> **如果实测觉得变体斑块太大或太小，只调这个点阵的尺寸**，不要去动 `Rng` 的调用方式。

### 6.3 地形边界是硬切（**美术没给过渡图**）

V1 用 Bayer 抖动在两种地形交界处做过渡。**V2 没有过渡图可用**，所以相邻格之间是**硬切**。

**这是可以接受的**：像素风游戏里硬切是主流，而且 32×32 的格子够大，硬边看起来是"地块"而不是"锯齿"。

> ⚠️ **但这一条要跟美术确认。** 如果他们要柔和过渡，需要补**过渡图**（每种地形 × 每种邻居地形，或者简化成 4 方向 × 2 档）。**这是加工作量的事，先别默认要做。**

### 6.4 建筑层叠加

**合成顺序：地形 → 建筑。**

```csharp
void Bake(GameMap m, IBuildingLayer buildings)
{
    for (int tile = 0; tile < GameMap.TILES; tile++)
    {
        Blit(SpriteAt(TerrainOf(m, tile), VariantAt(m, tile)), tile);   // ① 地形
```

### 6.5 烘焙流程

**两种做法，推荐第一种。**

**① Unity Tilemap（推荐）**

### 6.7 ★ V3 新增：水体深浅（water1 是浅色，另外 3 张是深色）★

**美术给的水体 4 张里，只有 `water1` 是浅色的，其余 3 张是深色。** 这不是随便定的——**它就是在告诉你 `water1` 该用在岸边**。

**规则（一行）：**

```
水格如果 4 邻域里有非水格  →  water1（浅水）
否则                      →  从另外 3 张里按变体点阵挑（深水）
```

```csharp
// Game/MapRenderer.cs
byte WaterTile(GameMap m, int tile)
{
    if (m.terrain[tile] != Terrain.Water) return m.terrain[tile];

    // ① 岸圈：4 邻域里有陆地 → 浅水
    if (HasLand4(m, tile)) return WATER_SHALLOW;      // water1

    // ② 内部：深水，从 3 张里挑
    return WATER_DEEP_BASE + VariantAt(m, tile) % 3;
}
```

### 为什么是 **4 邻域**而不是 8 邻域（实测）

| 规则 | 浅水占比 | 深水占比 | 效果 |
|---|---|---|---|
| **4 邻域有陆地 → 浅水** | **82%** | **18%** | ✅ 岸圈清晰，湖心留得住深色 |
| 8 邻域有陆地 → 浅水 | 94% | **6%** | ❌ 太满，**大湖的湖心也被染浅了** |

**实测那个 66 格的水块**：岸圈约 30 格、深色核心约 36 格——**深色湖心比岸圈还大，一眼能看出"这里深"**。

> ⚠️ **用 8 邻域会把深色挤没。** 斜角算邻居等于把岸圈加粗一圈，小湖直接全浅。**这一条要按 4 邻域实现。**

### 三个附带效果

**① 顺带解决了水陆硬边。** V2 说"地形边界是硬切，美术没给过渡图"（§6.3）——**水体是唯一的例外**：`water1` 的浅色岸圈本身就是过渡。**所以陆地和水之间不需要过渡图，只有陆地之间需要。**

**② 河流会整条都是浅色。** 1 格宽的河，每格都 4 邻接陆地 → 全是 `water1`。
**这是对的**，不用改：河水本来就浅，而且**河浅湖深本身就是自然的对比**。

**③ 小水塘全浅。** 中位 3 格的水塘全是岸圈，深水为 0——正确。

### ⚠️ 这一节不碰任何确定性

```
水体的深浅是从 terrain[] 现算的  →  不进 terrain[]、不进 HashState、不进存档
```

**而且水是唯一「游戏开始后永远不变」的地形**（开垦只动草地/荒地，退化只动耕地）。所以：

> **深浅掩码可以在烘焙时算一次就冻结，之后永远不用重算。**

### 6.8 ★ V3 新增：建筑不能和树/水重合 ★

**先说结论：树木是地形，房子粮仓是建筑层，两者不同层——所以"树叠树"这种事不会发生。** 要防的只有三件事。

**建筑层的形状（每格一个值）：**

```csharp
public short[] building;    // TILES，-1 = 没有建筑
```

**这一条就天然保证了「每格最多一个建筑」** —— 不需要额外的重叠检查。房子和粮仓抢同一格时，后写的覆盖先写的，而不是叠在一起。

**三条硬规则：**

| # | 规则 | 为什么 |
|---|---|---|
| **1** | **只能建在 `Habitable(t) && t != Trees && building[tile] == -1` 的格子上** | 水上站不住人；**建在树上会看到房子上面冒出一截树冠** |
| **2** | **开垦（V3）不能开垦有建筑的格子** | 否则"田里长出一栋房子" |
| **3** | **建筑不写回 `terrain[]`** | 写回去就和地形混淆了，而且会让存档和哈希多一份冗余 |

**规则 1 的实现**（放在模拟层的建筑放置处，不在 MapGen 里）：

```csharp
bool CanBuild(GameMap m, short[] building, int tile)
{
    byte t = m.terrain[tile];
    return Terrain.Habitable(t)          // 不是水
        && t != Terrain.Trees            // ★ 不是树
        && building[tile] < 0;           // 该格还没有建筑
}
```

> ★ **`t != Trees` 这一条是这次检查的主要产出。**
> 树木现在是**地形**（V2 起），所以它和房子在**同一个格子上**是必然冲突的——房子会盖在树冠上，或者树冠从房顶冒出来。**必须显式排除。**

**如果你想让村子能建在树林里**，正确的做法是**放置建筑时把那格地形改成 `Grass`**（"清出宅基地"），而不是允许重叠：

```csharp
// 可选：清地建房
if (m.terrain[tile] == Terrain.Trees) m.terrain[tile] = Terrain.Grass;
building[tile] = houseType;
```

> ⚠️ **走这条路的话，地形就多了一个变更来源**（生成 + 开垦 + 退化 + 清地建房），**而每次改 `terrain[]` 都要保证它进了哈希和存档**（见 `荒地与开垦退化-实现方案-给程序.md` §5）。**为了省事，先选"不能建在树上"。**

### 7.1 接缝设计（把对现有代码的破坏降到 0）

**核心原则：`map == null` 时，行为与现在完全一致。** 这样现有 60 条测试**全部保持绿色**，不用改。

```csharp
// World 新增一个可选参数
public World(ulong seed, int[] lawset = null, int[][] presets = null, GameMap map = null)

// 新增实例字段（默认 1/1 = 无影响）
int prodScaleNum = 1, prodScaleDen = 1;
GameMap mapRef;                              // null = 环形拓扑（旧行为）
```

**在 `Tick()` 里，只改这一处：**

```csharp
// 原：int perCapita = PROD_BASE - st.aliveCount * CROWD_K;
int baseScaled = mapRef == null
    ? PROD_BASE
    : PROD_BASE * prodScaleNum / prodScaleDen;
int perCapita = baseScaled - st.aliveCount * CROWD_K;
```

`prodScaleNum/Den` 在构造时算一次：

```csharp
// REF_ARABLE 见 §7.3；MAP_INFLUENCE 见 §12.1
int ratio  = map.arableCount * 1000 / REF_ARABLE;             // 千分点，1000 = 跨种子平均
int damped = 1000 + (ratio - 1000) * MAP_INFLUENCE / 1000;    // ★ 压缩地图方差后再传递
prodScaleNum = damped;
prodScaleDen = 1000;
```

> ★ **必须走 `damped` 这一步，不能直接把 `ratio` 传进去。**
> 原因见 §12.1：你的产出系数可用窗口只有 **±10%**，而地图的可耕地方差有 ±15%。
> 全量传递会让**大部分种子落到窗口外**（不是全灭就是全活），`T05_03 结局梯度` 会红。
> `MAP_INFLUENCE = 400` 只传递 40% 的方差；设成 `0` 就退回"地图纯装饰"。

**模拟用 `map.usedSeed` 当种子**（不是输入 seed）。因为重掷过的图，村民也应该跟着那张图的种子走。

**然后改两个地方：**

### 7.3 ⚠️ 接完之后必须重跑标定

**Tier 1 改变了拓扑密度：** 旧的环形拓扑每人是 2 个邻居（20 条边），新的 `NEI=4` 是 4 个（80 条边）。**恐惧传染变快、互动变密**——你之前扫出来的 `PROD_BASE=1650 / CROWD_K=70 / FEAR_DECAY_DIV=3` **大概率不再是最优**。

**必须做的三件事，顺序不能反：**

1. **先测 `REF_ARABLE`**：跑 2000 个种子，只统计**通过验收的**地图的**耕地格数**均值（★ V2：原来是草地格数，`Arable` 已改指向 `Farmland`）。
   > ★ **基准要在下游测，不能在上游测。** 因为重掷是**条件采样**——你扔掉了所有草地 < 20% 的图，活下来的分布均值一定**高于**原始分布。用原始均值归一化，你的村庄会**系统性地偏富**，而且是静默的。
2. **重跑 `--calib`**：在开了地图（`map != null`）的情况下重新扫 `PROD_BASE × CROWD_K`。
3. **重跑 `_tests`**：T05_03（结局梯度）、T05_04（寄存器方差）、T05_05（八条法承重）这三条**必须重测**，因为拓扑变了。

**这三步加起来大概半天。别跳过第 3 步——那 60 条测试最初的建立过程已经证明过：数值退化是不报错的。**

## 8. 性能预算

| 步骤 | V1 量级 | **V2 量级** | **V2 估算** |
|---|---|---|---|
| 噪声（2 场 × 3 八度） | 384 格 / ~2,300 次插值 | **1536 格 / ~9,200** | < 0.4 ms |
| 元胞自动机（4 轮 × 8 邻域） | ~12,000 次判定 | **~49,000** | < 0.8 ms |
| 洪水填充 | ~1,500 | **~6,000** | < 0.2 ms |
| 出生点 | 20 × 384 | 20 × 1536 | < 0.2 ms |
| 耕地派生（§4.7） | — | **~440 格** | < 0.05 ms |
| **一次生成尝试** | < 0.5 ms | | **< 2 ms** |
| 平均 2 次尝试 | < 1 ms | | **< 4 ms** |
| **贴图烘焙** | 393,216 像素 / **5–20 ms** | **1,572,864 像素** | **20–80 ms** |

**结论：换种子时总耗时目标从 ≤30 ms 放宽到 ≤100 ms。** 仍然是加载期/换种子时的一次性开销，**不是每帧的**。

> ★ **涨的几乎全在贴图那一项**（4 倍像素）。逻辑层涨了 4 倍但绝对值还是微秒级。
>
> **如果实测超过 100 ms**，第一要查的还是 `Apply()`。**第二要看的是有没有必要整张重烘焙**——开局只烘焙一次，更实际的做法是**只在换种子时做，并且给个加载提示**。

> ⚠️ **走 Tilemap（§6.5 做法 ①）的话，这一项的量级完全不同**——Tilemap 不需要 `SetPixels32`，铺 1536 个 tile 通常是 5–15 ms。**这也是推荐它的原因之一。**

> ★★ **V3 之后这一节的性质变了：地图会变（开垦/退化），所以"烘焙一次就完事"不再成立。** ★★
>
> | 做法 | 一次地形变化要付多少 |
> |---|---|
> | **Tilemap（推荐）** | **只改那 1 格** → 微秒级 |
> | 预烘焙贴图（`SetPixels32`） | **整张重烘焙** → 20–80 ms |
>
> **开垦是每 120 tick 一次、退化每 2400 tick 一次**（见独立文档 §0）。按贴图那条路走，**每 0.9 秒就要整张重烘焙一次**——`Apply()` 会把帧率直接打穿。
>
> **所以 V3 之后，Tilemap 从"推荐"变成"几乎是必须的"。** 如果坚持走预烘焙贴图，就必须改成**只重烘焙被改的那几格**（局部 `SetPixels32` + 一次 `Apply`），那是额外工作量。

# 12. 地图接入后的整体审查

> **这一节是全游戏范围的，不只地图。** 按"会不会静默坏掉"排序。
> §12.1 的三条**不处理就会出问题，而且不报错**。

## 12.1 P0 · 会静默破坏现有东西的三处

### P0-1 ★ 地图的方差会掀翻承载力 ★

**这是接入地图之后最大的一个风险。**

你的 `--calib` 扫出来的可用窗口**非常窄**：

| 产出系数 | 平均存活 |
|---|---|
| 0.75 | 0.4 人（全灭） |
| 0.85 | 3.4 人 |
| **0.90** | **8.4 人** ← 可用区 |
| 0.95 | 10–11 人 |
| 1.00 | 12+ 人 |

**可用窗口大约只有 ±10%。**

而地图带来的可耕地比例方差，如果也是 ±15%，**大部分种子会落到窗口外**——不是全灭就是全活。`T05_03 结局梯度` 会直接红。

> ★ **V2 让这条大幅缓解。** V1 的可耕地 = **整张图上所有草地**，方差跟着噪声场走，很大。
> V2 的可耕地 = **出生点周围 `FARM_MARGIN` 格内清出来的地**（§4.7）——**它钉在村庄上，`FARM_MARGIN` 直接决定它有多大。**
>
> 所以 V2 之后：
> - 耕地格数的**方差小得多**（不再跟着整张图的草地比例浮动）
> - 而且它**多了一个确定性的旋钮**：想调承载力，改 `FARM_MARGIN`，不用跟噪声场较劲
>
> ⚠️ **但 `MAP_INFLUENCE` 和 `REF_ARABLE` 仍然要重新标定**——缓解不等于消除，锚点落在哪还是会影响耕地格数。

**修法：把地图的影响压缩后再传进去。**

```
ratio   = arable * 1000 / REF_ARABLE          // 千分点，1000 = 平均
damped  = 1000 + (ratio - 1000) * MAP_INFLUENCE / 1000
baseScaled = PROD_BASE * damped / 1000
```

- `MAP_INFLUENCE` 建议初值 **400**（只传递 40% 的地图方差）
- **然后实测调**：目标是让跨种子的平衡人口 `P*` 的标准差 **≤ 可用窗口宽度的一半**
- 极端情况：`MAP_INFLUENCE = 0` 就退回"地图纯装饰"，`1000` 就是全量传递

**必须新增的测试（在 T09_10 之外）：**
> 跨 200 个种子，`P*` 的标准差 **≤ 5%**。只测均值不够——**均值守住而方差炸掉，照样会有一半种子不可玩。**

### P0-2 ★ 存档里的 seed，会在你改了生成器之后变成另一张图 ★

地图是种子的纯函数。而**你在 jam 期间一定会改生成算法**（调阈值、加地形、修 bug）。

于是：玩家昨天存的档，今天更新后打开——**地图悄悄换了，而且不报错。** 他甚至不知道为什么村子不一样了。

**修法：存档里加一个 `MAPGEN_VERSION`。**

```csharp
const int MAPGEN_VERSION = 3;   // 每次改动生成算法就 +1（V3 当前值）
```

版本不匹配时，**绝不静默重生成**。两个选择：
- 明确提示玩家"本局地图来自旧版本，已重新生成"
- **或者直接作废本局**（18 天的 jam 里，这个更省事也更诚实）

> 存档格式里已经有 CRC 和版本迁移的分层设计，`MAPGEN_VERSION` 挂在同一层就行。

> ★ **V3 补充：这条还不够。** 上面说「地图是种子的纯函数」——**V3 之后不再是**（开垦/退化会改它）。
>
> 所以存档**除了 `MAPGEN_VERSION` 还要存 `terrain[]` 本身**（§2.5）。否则：
> - 版本号相同 → 你以为能重生，其实**已经重不出同一张图了**（玩家的开垦历史丢了）
> - 读档后地形回到开局状态，**而村子还是几十年后的村子**
>
> **两个一起做才成立：`MAPGEN_VERSION` 管"生成器变没变"，`terrain[]` 管"这局的地被改成什么样了"。**

### P0-3 Tier 1 改拓扑 → 必须重跑标定

见 §7.3。这里只做索引：**它是唯一一个会同时影响 `P*` 和互动密度的改动。**

## 12.2 P1 · 结构性的，晚改代价大

### P1-1 关系域有 79% 是死区

`NEI = 4` → 有向边 **80 条**；而村民对总共有 `N(N-1) = 380` 对。

> **79% 的村民对，在整局中永远不构成"邻居"。**

**后果**：如果事件卡的关系域门禁写的是"任意两个人"（`PackPair(a,b)`），那 **300 个目标格永远不可能被触发**——而且不报错。这正是"死信"在关系域上的版本。

**规则（写进卡设计规范）：**
> **关系域卡的门禁必须以「`rel != 0`」或「是邻居」为前提，不能是"任意一对"。**

顺带，定版里"关系域卡 ≤ 5 张"这条限制，现在有了比"性能"更硬的理由：**关系域的绝大部分本来就是不可达的。**

### P1-2 村民的位置：视图层还是模拟层？

**必须现在定**，因为它同时决定 `HashState`、存档体积、和相机。

**推荐方案：**

| 项 | 决定 | 理由 |
|---|---|---|
| 村民位置 | **只在视图层**（steering 是表现） | 不进模拟、不进哈希、不进存档 |
| 邻接表 | **出生时算一次，之后冻结** | 图稳定 → 好推理、好显示、好测试 |

⚠️ **由此产生一条必须写进渲染规格的约束：**

> **steering 必须让村民在自己家周围小范围游荡（半径 ≤ 2 格）。**

否则玩家会看到**两个人明明站在一起，却不是"邻居"**——那是个肉眼可见的逻辑矛盾，而且解释不清。

### P1-3 ★ V2 改判：相机省不掉了 ★

```
V1   24×16 图 =  768×512 像素     "世界"区 568 高（1080 基准）→ 放得下 ✅
V2   48×32 图 = 1536×1024 像素    同上                        → 放不下 ❌
```

**V1 那条「整张图一屏放得下 → 不需要平移、不需要缩放」的结论作废。**

**V2 必须做的**：

- **相机**：平移 + 缩放（V1 说"可以砍掉"的那半天，**现在要花**）
- **`InputLog` 记录相机状态**（V1 说不用的，现在要用）
- **点格高亮的逆变换**：屏幕坐标 → 格坐标，要按当前缩放/平移算

**顺带一个正面影响**：V1 那条「非整数缩放会让纯色块发边缘发软」的担忧**基本消失了**——V2 是 32×32 的**真实拼图**，不是纯色块。缩放发软的观感问题小很多，**但点采样（Filter = Point）仍然必须关掉 mipmap**，否则缩小的时候会糊。

> **这条是 V2 唯一一处净增工时的地方**，大约 **+0.5 天**。

## 12.3 P2 · 白送的收益（几乎零成本）

### P2-1 讣告多了一批地理句子

讣告现在能引用的维度从「死因 + 第几条法 + 个人史」扩到 **+ 地理**：

- 「他家的地在全村最薄的那一块」
- 「他死在河对岸。粮仓在这边。」
- 「他抢的是住在他东边的那一户」

**代价只有模板里多一个槽位**，但拿到的是"玩家能看见的原因"。这类句子直接对应主题判据 5（可读性）。

### P2-2 结算长图加一张死亡分布小图

结算页已经有曲线和"谁最致命"。现在可以把**死亡位置在地图上的分布**画成一张小图——共享出去的传播力比曲线强得多。

成本：一次像素叠加，几乎为零。

### P2-3 事件卡多了一个门禁轴

20 张卡的耦合密度一直是弱点（需要 ~30 处卡间引用，设计里只有 3 处）。**地形给了你一根不需要新标签的门禁轴**：

- 「洪水」：靠近水的格 → 粮仓损失
- 「断路」：与粮仓隔水的村民 → 饥饿上升
- 「开荒」：**耕地格** → 粮仓增加（★ V2）

⚠️ 但**必须仍然遵守原有规则**：每张卡至少读一个标签、写一个标签。地形门禁是**附加**的，不能替代标签——否则你会把已经不够的耦合密度摊得更薄。

# 15. 调参流程与降级路径

## 15.1 调参有依赖顺序，不能乱

```
① 调生成器        →  T09_03 / T09_04 绿（通过率 40–80%，拒绝不集中）
①b ★ V2 标定 TREES_MOIST →  目标森林覆盖 10–25%（T09_16）
①c ★ V2 标定 FARM_MARGIN  →  目标耕地 150–400 格（T09_15）
② 测 REF_ARABLE   →  ★ 必须在"重掷之后"的分布上测（2000 seed，只统计通过验收的）
③ 扫 MAP_INFLUENCE→  从 400 开始，目标是 P* 的跨种子 σ ≤ 5%
④ 重跑 --calib    →  在 map != null 下重新扫 PROD_BASE × CROWD_K
⑤ (M8 之后) 再重跑一次 --calib
```

> ★ **V2 的 ①b / ①c 要排在最前面，而且 ①c 必须在 ② 之前。**
> 因为 `FARM_MARGIN` **直接决定耕地格数**，而 `REF_ARABLE` 就是耕地格数的均值——**先定 `FARM_MARGIN`，再测 `REF_ARABLE`，顺序反了就要测两遍。**

**为什么不能跳②**：重掷是条件采样，活下来的地图平均比原始分布更肥。用原始均值归一化，村庄会**系统性偏富**，且不报错。

**为什么③要在④之前**：`MAP_INFLUENCE` 决定承载力的**方差**，`--calib` 决定它的**均值**。先定方差再定均值，否则你会来回改。

## 15.2 降级路径（时间不够时按此逐级退）

| 级别 | 怎么退 | 代价 | 保住了什么 |
|---|---|---|---|
| **0** | 全做（含 Tier 1） | — | 全部 |
| **1** | 停在 M7（不接 Tier 1） | 「抢最近的邻居」还是环形抽象 | 地图影响承载力——**这是收益最大的那一档** |
| **2** | `MAP_INFLUENCE = 0` | 地图变成纯装饰，模拟完全不受影响 | 视觉上的随机地图 + 每局不同 |
| **3** | 不生成河流 | 少一类地形 | 地图仍然随机 |
| **4** | `map = null` | 完全没有地图 | **完全回到现在的行为，60 条测试全绿** |
| **5** | 手工画 3–5 张固定地图 | 每局不再不同 | 有地图，且 100% 可控、100% 能看 |

> **降级是逐级的，每一级都只有一行改动。** 这是这张表存在的意义——**你不会在最后一天发现"地图做不完所以游戏也没了"**。
>
> 第 5 级（手工地图）**不是失败**：3–5 张手绘地图配上"每局随机抽一张"，对 18 天的 jam 是完全可交付的。
