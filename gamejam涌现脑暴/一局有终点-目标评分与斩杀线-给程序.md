# 一局有终点 · 目标 / 评分 / 斩杀线（合并方案 · 给程序）

> **背景**：我把 10.13 那份构建整个搜了一遍——**没有 game over、没有胜负、没有年限、没有结算**。
> `CountAlive` 只被用来显示和算逻辑，**从来没用来做结束判定**。威信归零只是"法律暂停生效"，不是失败。
>
> 所以现在的状态是：**玩家写法律，村民生死，然后一直这样下去。** 评审玩 10–20 分钟看不到任何结局。
>
> **这三件事（目标 / 评分 / 斩杀线）其实是同一件事**，必须一起做。

---

## 0. 一句话

```
一局跑满 30 年，或者全村死光 —— 然后给玩家两个数字，和一个称号
    存续：你让多少人、活了多久
    治绩：你在这块地上立起了多少威权
```

**两个数字的组合决定称号。不给总分。**

---

## 1. 为什么不给一个总分

把"存续"和"治绩"加权成一个分数，就必须回答"一条人命值几点威信"——**那是个没法辩护的问题**，而且会立刻塌成一种最优解。

拆成两个数字之后：

- 不需要编权重
- **两个数字的组合天生就是四种玩法**（见 §4），重开一局的理由自己就长出来了
- 而且它正好是这个游戏的母题：**仁政还是苛政**

> **分数不审判玩家。审判玩家的是讣告墙。**

---

## 2. 结束条件

```csharp
// SimulateTick 末尾，data.tick = tick + 1 之后
if (CountAlive(data) == 0)                              → 结束，endingKind = 1（村灭）
else if (data.tick >= RunLengthTicks)                    → 结束，endingKind = 2（期满）
```

```csharp
public const int RunYears = 30;
// 一年 = DaysInYear × 8 tick（2920 / 2928），不要写死
// 注意 DaysBeforeYear 返回 long，这里要显式转回 int
public static int RunLengthTicks => (int)(VillageTime.DaysBeforeYear(RunYears) * 8L);
```

> ⚠️ **不要用 `tick % 2920 == 0` 判年**——闰年会让它错位。用 `VillageTime` 现成的 `DaysBeforeYear`。

**为什么是 30 年**：现在所有平衡数据都是在 30 年这个尺度上测的（退化率、开垦、存活分布）。换成别的年数，等于所有数值要重测一遍。

**实时长度**：`TicksPerSecond = 148`、一天 8 tick → 18.5 天/秒。
**30 年 ≈ 9.7 分钟（1x）/ 3.2 分钟（3x）**。玩家可以调速，这个长度是合适的。

---

## 3. 存续：人年，不是年末人口

### ★ 为什么不能用年末存活人数 ★

人口上限是 **80**（`ResolveBirths` 里的 `num2 >= 80`）。一个经营得好的村子**大约第 8–12 年就顶到 80 了**，之后 18 年完全一样。

用年末人口做分，**第 10 年就饱和了**——这正是我之前在"承载力"那轮发现的老问题。

### 改法：累加人年

```csharp
// VillageSaveData
public int personMonths;      // 存续分，单位「人·月」

// SimulateTick 里，每 240 tick（= 30 天 = 一个月）累加一次
if (tick > 0 && tick % 240 == 0)
{
    data.personMonths += CountAlive(data);
}
```

- **整数**、**不饱和**、**单调**，符合确定性整数模拟的要求
- 30 年 × 平均 40 人 ≈ **14,600 人·月**
- 含义直观：**"这一年村里有多少人，全加起来"**

**展示成「平均人口」更好读**：

```
存续    平均 41 人 · 年末 26 人
```

其中 `平均 = personMonths / 12 / 30`（整数除法）。**但象限判定用 `personMonths` 原值，不要用四舍五入后的平均数。**

---

## 4. 治绩：威信

直接用 `save.prestige`（已经是 0–300 的整数）。

**为什么它天然是个好指标**——威信公式本身就是一套"治理效率"：

```csharp
// SimulateTick:5367
int num8 = pop / 4 + Math.Max(0, 30 - fearAvg) / 10;
prestige = prestige - 3 * lawCount + num8;
```

- **装的法越多，威信掉得越快**（`-3 × 法条数`）
- **人口越多、平均恐惧越低，回得越快**
- **→ 它是一个"人口供养得起的法律条数"的预算**

这就是那个张力：**想养活更多人，就得多立法；多立法，威信就撑不住。** 不需要额外设计。

> ⚠️ 威信归零会触发 `prestigeSuspended`（法律暂停生效）。**这已经是现成的软惩罚**，不用改。

---

## 5. 四个结局 + 一个特殊情况

**判定基准取开局值**，玩家从第一秒就知道自己在跟什么比：

| | 存续（`personMonths`）| 治绩（`prestige`）|
|---|---|---|
| 高 | ≥ 开局人数(24) × 12 × 30 = **8,640 人·月** | ≥ **100** |
| 低 | < 8,640 | < 100 |

```
存续高 · 治绩高   →  盛世    你让村子富庶，也让你自己有了分量
存续高 · 治绩低   →  安居    他们活着，但你什么都没立起来
存续低 · 治绩高   →  苛政    你立起了威权，代价是人
存续低 · 治绩低   →  荒村    你写的法，一条都没兑现
村灭（全灭）      →  村灭    优先级最高，盖过上面四个
```

**「村灭」优先**：不管人年多少，只要最后一个人也是死在你手上的，就是村灭。

> **名字随便改**，这四个只是占位。真正要保的是**四象限这个结构**。

## 7. 斩杀线：结束之后存档怎么办

### 存什么

```csharp
// VillageSaveData —— 只存三个字段，其余全部现算
public bool ended;          // 是否已终结
public int  endingKind;     // 1 = 村灭, 2 = 期满
public int  endTick;        // 终结时的 tick（用于展示）
public int  personMonths;   // ★ 这个必须存——它是累加量，算不回来
```

**其余（称号、致死榜、抽中的讣告）全部是派生量，不存，打开结算时现算。** 和产出/消耗那三个字段一个道理。

### 已终结的存档

- `VillageSaveMetadata` 加一个 `ended` 字段
- **主菜单存档卡**上要显示：`第三十年 · 苛政 · 讣告 37`
- **点进去只能看结算画面**，不能再继续推进模拟；给一个"再开一局"
- 底部按钮：`[重看结算] [再开一局] [主菜单]`

### 游戏内要有进度

HUD 现在已经显示年月了（`dayValue`）。**改成**：

```
第 12 年 / 共 30 年
```

> **这条不能省。** 没有进度条，玩家不知道自己在往哪跑，就不会为"第 30 年"调整策略——评分系统的一半作用就没了。

## 8. 技术要点

### 8.1 确定性

- `personMonths` **是模拟状态**：参与累加、进存档
- 结束判定只依赖 `tick` 和 `CountAlive`，**本身是确定的**
- 称号 / 致死榜 / 抽签 **全是派生量，不进存档、不进哈希**

### 8.2 存档版本

```
VillageSaveData.CurrentVersion: 9 → 10
```

`Normalize` 里按现有模式补：`personMonths` 旧档没有 → **只能补 0**（算不回来）。旧档读进来会是"存续 0"，落进「荒村」。
**这可以接受**——旧档本来就是测试档，不是玩家的真实存档。

> ⚠️ 如果《修bug方案》§5（讣告法名快照）也一起做了，两边版本号要对齐，别撞车。

### 8.3 ★ 结束判定必须在 `SimulateTick` 的最后

```csharp
// SimulateTick 现在的结尾
data.tick = tick + 1;
if (report.deaths > 0 || report.births > 0) { ...事件文本... }
// ★ 新增：判定放这之后，保证用到的 tick / alive 是最新的
CheckRunEnd(data, ref report);
```

**不能放在中间**——那会让同 tick 里后面的法律读到已经结束的状态。

### 8.4 结算画面在哪个场景

复用现有的游戏内 HUD 覆盖层（像设置面板那样），**不新开场景**。存档读进来时如果 `ended == true`，直接把它打开。

## 9. 验收

**基本**
- [ ] 跑满 30 年自动结束，弹出结算
- [ ] 中途全灭立刻结束，称号是「村灭」
- [ ] 存档卡上显示结局称号
- [ ] 已终结的存档读进去只能看结算，不能再推进
- [ ] HUD 显示「第 N 年 / 共 30 年」

**数**
- [ ] `personMonths` 每 240 tick 稳定累加，30 年后约等于 `平均人口 × 360`
- [ ] 同一局反复打开结算，**抽中的讣告是同一篇**（确定性）
- [ ] 不同局抽中的讣告不同

**★ 标定（这条最重要，没做等于没做）★**

- [ ] **跑 120 局**（不同种子 × 不同法条组），统计四个象限的分布
- [ ] **目标：每个象限 ≥ 15%**，且没有任何一个 > 45%
- [ ] 如果塌成两个象限 → **是平衡没调好，不是评分写错了**，回 §10 去调
- [ ] 顺手记录：平均人年、平均威信、以及各个数值的分布——**这份分布就是后面所有平衡改动的仪表盘**

## 10. ★ 风险：必须先做粮食平衡 ★

**评分系统测出来的第一个结果，很可能是"所有局都活得很滋润"。**

因为按现在的数值：

- 粮食收支容差只有约 **4%**（产出 `4×人口` vs 真实消耗 `≈3.83×人口`）
- 而**饥饿实际上永远不会到 99**——只要粮仓高于 40，村民就被补满，饥饿每次 −5，永远压在地板上
- 于是「饥饿致死」这条路径基本不触发，存活率会普遍偏高 → **全部落进「盛世/安居」**

**所以顺序是：**

```
《修bug方案》§1 钳位 → §6 粮食收支重调 → 再回来标定评分
```

> **反过来也成立：评分是调平衡的仪表盘。**
> 先有分数，才能知道调没调对。所以这两件事**要连着做，不要分给两个人**。
