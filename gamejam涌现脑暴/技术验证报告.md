## 1. 五个必修 bug —— 已修，附修法

这五个都是把文档里的代码原样抄进 .NET **实测跑出来的**，不是推断。

### Bug 1 ★致命★ `Slot()` 必越界 —— `IndexOutOfRangeException`

`NumTargets = 1 + N + N(N-1)` 预留的是**压缩后**的关系槽，而朴素的 `PackPair(a,b) = a*N+b` 最大到 `N²-2`，比 `N(N-1)-1` 大了整整 `N-1`。

```
实测：N=12 → 合法下标 0..144，朴素最大 155 @(11,10) → 越界
      N=20 → 合法下标 0..400，朴素最大 419 @(19,18) → 越界
```

**N≥3 就崩，N=20 时最多溢出 19 个下标。**

```csharp
// ✅ 修法：正确的双射（实测满射、零冲突）
public static int PackPair(int a, int b, int n) {
    int m = n - 1;
    return a * m + (b < a ? b : b - 1);
}
```

**自检 G2 已覆盖**（N=5/12/20，验证双射 + 槽位不越界）。

### Bug 2 ★严重★ `RngFor` 没有 `seq` —— 同一 tick 内复用同一个 roll

原设计 `RngFor(seed, tick, channel)` 是纯函数，同一 tick 内每次调用返回**完全相同**的值。

```
实测：同一 tick 内 8 个优先级段，原设计只能产出 1 个不同值；加 seq 后 8/8。
```

后果不是崩溃，是**静默的行为退化**：抽卡在各段之间完全相关，加权随机退化成"高权重卡被系统性同向偏好"。而且立宪候选靠 `CH_CONSTITUTION` 和 `CH_CONSTITUTION+1` 硬凑两个数——那是**拿 channel 号当计数器用**，而 channel 号是有语义的。

```csharp
// ✅ 修法：加 seq，channel 有语义永不复用，seq 才是计数器
public static ulong For(ulong seed, int tick, int channel, int seq)
{
    unchecked
    {
        ulong h = Mix64(seed ^ ((ulong)(uint)tick * 0x100000001B3UL));
        h = Mix64(h ^ ((ulong)(uint)channel << 48) ^ ((ulong)(uint)seq << 16));
        return h;
    }
}
```

### Bug 3 ★严重★ `File.Replace` 首次保存必抛异常

```
实测：首次保存（目标不存在）→ 抛 FileNotFoundException: Unable to find the specified file.
```

`File.Replace` 要求 destination **已存在**。没被 try/catch 包住就是**新玩家第一次退出就崩**。

```csharp
// ✅ 修法：不存在时退化为 Move
File.WriteAllText(tmp, content);
if (!File.Exists(path)) { File.Move(tmp, path); return; }
try { File.Replace(tmp, path, bak); }
catch (IOException) { /* 退化为 备份 + 覆盖 */ }
```

**自检 G3 已覆盖**（首次/二次/三次保存 + 坏档回落）。

### Bug 4 ★严重★ `TagBits` 扩 16 位后编译不过

```csharp
public const byte Coward = 1 << 0;   // 原设计
public const byte X = 1 << 8;        // ❌ CS0031：常量 256 无法转换为 byte
v.tags &= (byte)~(1 << bit);         // ❌ 16 位下会把高 8 位整个抹掉
```

**修法**：全部改 `ushort`，并把掩码运算收敛到唯一一处 `ApplyRemoveTag`。

**自检 G4 已覆盖**（16 位可用 + 伤疤不可清 + 性格可清）。

### Bug 5 ★可控★ `hitsTotal` 双主

`LawSlot.hitsTotal` 与 `LawRuntime.hitsTotal` 都标了 `[哈希]`，而疲劳逻辑读后者。两个字段漂移后**哈希和玩法说的不是一回事**，且不报错，只让重放静默分叉。

**修法**：`hitsTotal` 只留一个主（`Law`），`LawRuntimeView` 降级为本 tick 只读视图，不进哈希、不进存档。

**自检 G5 已覆盖**（累计命中与疲劳判定同源）。

### 附带：推翻一处范围矛盾

定版已砍掉关键帧环，那么规格里整套「重放内核」（`SnapshotAt` / `RestoreInto` / worker 线程 / 分帧 / 进度上报）**已经没有任何消费者**。整块删掉，省 16h 和一大片风险面。

## 2. 最重要的一节：数值必然会崩，以及修法

**五个 bug 修完，游戏仍然不能玩。** 这一节是八轮实验一路钻下去的结果，也是本报告最有价值的部分。

### 2.1 症状链（四层递进）

**第一层 · 村庄直接死光。** 无粮食生产时 500 seed 里 **92.4% 全灭**（平均死 18.5/20）。

**第二层 · 活着但什么都不发生。** 加上粮仓后，平均终局存活 18.6/20，但"判活率"是 **0.0%**。

**第三层 · 所有寄存器收敛到边界。**

```
tick   均金币   均饥饿   均恐惧   存活
   1     12      15       6     20/20
 481     99       31       0     20/20     ← 金币顶到天花板
 961     99       31       0     20/20     ← 恐惧归零并锁死
2400     99       30       0     20/20     ← 饥饿夹在 30 不动
```

**第四层 · 律法条件全部失效。** 10 个条件里只有 **2 个可用**：

| 条件 | 触发率 | 评价 |
|---|---|---|
| 饥饿 > 20 / > 40 | 40% / 20% | ✅ 可用 |
| **饥饿 > 60** | **0%** | ❌ 死条件，法永不触发 |
| **金币 < 10 / < 30** | **0%** | ❌ 死条件 |
| 金币 > 50 | 100% | ❌ 恒真，无区分度 |
| **恐惧 > 20 / > 50** | **0%** | ❌ 死条件 |
| **有伤疤** | **0%** | ❌ 死条件 |
| 有性格 | 100% | ❌ 恒真 |

**这就是 D5 gate 失败的精确病理**：玩家贴了 5 条法，其中大部分的条件在这个村庄里永远不会被满足——**不是村庄死了，是村庄活着但无事发生**。比全灭更隐蔽，也更致命：它不会被你注意到，只会让玩家觉得"这游戏没反应"。

### 2.2 根因：两个结构性的不对称

**① 金币只进不出，必然全员顶格。** 实测总量从 332 → 1962（涨 6 倍）后锁死，均金币 98 而 **σ 只有 1.4**。设计里金币只在村民之间转移（抢/税/赠），**没有销毁途径**——守恒量的必然归宿就是边界。

**② 恐惧有汇无源，必然归零。** 规格写恐惧 −5/tick（半衰期 14 tick），而来源全是律法效果；但恐惧条件是死条件 → 法不触发 → 恐惧继续归零。**闭环死锁。**

### 2.3 最反直觉的一刀

以为解法是"加正反馈制造分化"。**实测完全相反**：

| 配置 | σ(金币) | 可用条件 |
|---|---|---|
| **纯负反馈**（只有衰减） | **10.6** | **5/10** |
| 加正反馈（马太效应） | **0.0** | 2/10 |

> **正反馈把所有人推到钳位边界上、全部压平。硬钳位 `clamp(v,0,99)` 本身就是方差的杀手——任何推向边界的机制，最终都会把方差抹成 0。**

### 2.4 真正有效的修法（参考实现已验证）

**决定性的一刀是：让性格标签调制每个村民的动力学参数，而不是只当门的开关。**

| | σ(金币) | 可用条件 | 50 seed 终局形态 |
|---|---|---|---|
| 病灶版（同质个体） | 3.7 | 3/10 | 均一稳定 **49/50** |
| **修正版（性格调制动力学）** | **27.7** | **5/10** | **丰富且分化 49/50** |

一个改动，49/50 从"死水"翻成"活的"。原因：**性格标签既是最强的耦合点，又是系统里唯一的异质性来源**。

### 2.5 五条配平（参考实现里的实现方式）

| # | 规则 | 病灶 | 实现 |
|---|---|---|---|
| ① | **硬钳位 → 软回拉** | 推向边界就抹平方差 | `if (gold > 80) gold -= (gold-80)/3 + 1;` |
| ② | **性格调制动力学** | 同质个体 + 全局动力学 → 全员同值 | 贪婪 → 生产概率 +15；勤勉 → 产出 +10 吃得省；怯懦 → 恐惧基线 +12；病弱 → 产出 −10 |
| ③ | **随机项受状态调制** | 纯确定 → 无个体差异 | 生产/消耗/恐惧都带 `Rng.Chance(..., 系数 + 偏置)` |
| ④ | **恐惧向性格基线回归 + 事件冲击** | 固定 −5/tick → 必归零；固定源 → 必饱和 | 基线 = `8 + 性格 + 饥饿/贫穷压力 + 个人历史`；事件（被抢 +18、有人死 +12）把它顶上去，再回归 |
| ⑤ | **阈值设在实测可用区** | 照抄 0–99 直觉 → 全是死条件 | 饥饿 20–60、金币 5–60、恐惧 8–60 |

**④ 还有一个额外的关键点：个人历史要写进基线。** `setpoint += 被抢次数×3 + 被税次数 − 被喂次数×2`（钳位 ±14）。这一条既提供了**同一时刻村民之间的差异**（σ 从 3.7 涨到 5.5），又是**路径依赖**——被抢过的人一辈子更难安心。**这是本作"涌现"在数值层的落点。**

### 2.6 ⚠️ 必须写进代码注释的警告

**"源/汇不配平"这一类 bug 在本次验证中出现了四次：**

1. 金币只进不出 → 全员顶格
2. 恐惧只有汇没有源 → 恒为 0
3. 加正反馈 → 反而全员顶格（与 1 同型）
4. 恐惧源太强 + 衰减太慢 → 全部饱和在 87（与 2 反向同型）

**同样的症状（σ→0）由完全相反的参数引起。** 任何新加寄存器、任何新加的源或汇，**都必须立刻用 G8 检查 σ**，而不是等到"看起来不好玩"再回头找。

## 4. 性能实测

**先纠一个算术错误**：规格里 `150,000 ÷ 100,000,000 = 0.15ms` 是错的，正确是 **1.5ms**（差 10 倍）。连带"整局 0.36s"应按 3.6s 估。

**但重算之后结论反而更稳**（两路独立实测）：

| 来源 | 测法 | 结果 |
|---|---|---|
| 本报告实验 | 20 卡 × 401 目标 = 8,020 判定/tick | **27.2 µs**（x64）→ 推算 ARM **272 µs** |
| 参考实现 | 20 卡 + 8 法 + 20 人，完整 tick | **5.1 µs**（x64）→ 推算 ARM **77 µs** |
| Unity 专项排查 | 3.8 亿次整数比较 | **0.072 s**（x64，约 5.3e9 次/秒） |

按最保守的 ARM 15–30 倍折价：**单 tick 0.2–0.6 ms**，而 1x 速度下每 tick 有 **1000ms** 墙钟预算 → **占 0.05%**。3x 下 0.15%。

**但有两条必须写进卡设计规范的约束：**

1. **性能风险不在算术，在容器。** 上述预算的前提是「扁平数组 + 无分配 + 无 LINQ」。用 `List<Cand>` + lambda 排序 + `foreach` 装箱，**实测会立刻膨胀 50–100 倍**。
2. **关系域卡的数量是内容约束，不是代码约束。** 如果所有卡都写成关系域（380 个目标），操作数会到 30 万/tick → 整局 3.6 秒。**卡尽量用 `Villager` 或 `Village` 域，关系域卡控制在 ~5 张以内。**

## 5. Unity 特有的坑

### 5.1 确定性：17 条坑里最要命的三条

1. **`float→int` 越界转换是规范未定义的** —— x86 给 `int.MinValue`，**ARM64 给 `int.MaxValue`（饱和）**。这是**唯一真正跨架构不一致**的地方。sim 里永不出现 float 就自然规避。
2. **有符号数的 `>>`** —— `-8>>1 = -4`（算术右移），`((uint)-8)>>1 = 2147483644`（逻辑右移）。**从 JS 的 `>>>` 翻译过来必错**，这是自写 PRNG 的第一号错误来源。
3. **`Array.Sort`/`List.Sort` 是不稳定排序** —— 比较器不是全序时，同一集合因插入顺序不同给出不同结果。**比较器必须四个键全参与**（`Priority, CardId, t0, t1`）。

其余：`struct.GetHashCode()` 在 Mono 与 CoreCLR 上实现不同（**永不拿它做哈希**）、`HashCode.Combine` 有每进程随机盐、`CultureInfo` 影响 `ToString`、`Marshal.SizeOf`/`unsafe`/`BinaryWriter` 直写 struct 跨架构不保证一致。

### 5.2 UGUI：杀手不是"每 tick"，是"每帧"

205 个 Graphic 重建只要 0.5–2ms，1x 下占 0.2% CPU，**完全没事**。真正的杀手是三种"每帧"的东西：

- 动态容器上挂 `LayoutGroup` / `ContentSizeFitter`（layout rebuild 比 vert rebuild 贵得多，某些配置下**每帧都脏**）
- 审议进度环每帧改 `fillAmount` → **每帧重建它所在的整个 Canvas**
- `ScrollRect` 用 `Instantiate` 加行

**拆分方案（4 个 Canvas）**，最关键的一刀：**把"头像+姓名 / 律法槽名称"放进一个永不被脏的静态 Canvas**。村民条的 100 个元素里只有 60 个数值条会变，这一刀让每次 rebuild 从 100 降到 60。

| Canvas | 内容 | 谁在什么时候 dirty |
|---|---|---|
| `Canvas_Static` | 底板/边框、20 个头像 + 20 个姓名、律法槽名称 | **只有死亡状态变化时**（一场 ≤20 次） |
| `Canvas_Hud` | 威信数字 + 净速率 + 命中数 + 状态徽章 | 每 tick 一次，**带值判脏** |
| `Canvas_Dock` | 20 格 × 3 条数值条 | 每 tick，带值判脏 |
| `Canvas_FX` | 审议进度环、命中闪烁、停摆滤镜、字幕 | **允许每帧** |
| `Canvas_Modal` | 讣告 / 村民卡 / 结算 | 打开时一次性构建 |

### 5.3 TapPlay：P1 只可能来自四件事

| 级别 | 最可能触发 | 规避 |
|---|---|---|
| **P1** | ① 冷启动 ANR<br>② IL2CPP 剥离导致 `MissingMethodException`<br>③ 首帧 IO 到不可写路径<br>④ Vulkan 黑屏 | **这四件 D1 一个下午能全堵上** |
| **P2** | ① 存档损坏 → 卡在加载页<br>② 切后台回来异常<br>③ `ReadPixels` 时机错 → 空纹理<br>④ 内存不足被杀 | ① 坏档分级兜底**必须真写**<br>③ 必须 `WaitForEndOfFrame` 之后再 `ReadPixels`，且**渲染完立刻 `Destroy(rt)`**（写成 `try/finally`） |

⚠️ **最难查的一条**：Android 上**协程里的未捕获异常会静默杀掉该协程**——如果 tick 循环跑在协程里，一次异常 = **游戏永久卡住但不崩溃**，用户报"卡死"你查不到堆栈。**tick 循环外面必须包 try/catch + 把异常打到屏幕可见横幅。**（参考实现里 tick 驱动用的是同步调用，不依赖协程。）

## 6. AI 能写什么、不能写什么

一句话判据：**AI 能写"算法"，不能写"纪律"。**

| 类别 | AI 表现 | 对策 |
|---|---|---|
| 确定性 PRNG | **能写对**（高频语料），错在漏 `unchecked`、`>>` 落到有符号数、种子 0 自锁、**接口少 seq**（正是 Bug 2） | 把 `Rng.cs` 作为唯一入口贴进项目，**禁止它自写 PRNG** |
| 整数模拟主循环 | **骨架能写对，细节崩溃**（用 Dictionary、排序比较器不全序、算百分比用 float、每 tick `new List`、**PackPair 越界**） | asmdef + 把纪律写进 `CLAUDE.md` |
| **UGUI 布局** | **写不对——最大的失败区** | **禁止 AI 生成 UI 布局代码**；你手写 RectTransform 位置表，AI 只填内容逻辑 |
| 存档序列化 | **看起来能跑，静默出错**（`JsonUtility` 用在 `Dictionary` 上会安静地存成 `{}`；`ValueTuple` 存成空；`File.Replace` 首存崩） | 手写 `SaveCodec.cs`，AI 只许改 DTO 字段定义 |
| 纹理写入 | 写不对（`SetPixel` 而非 `SetPixels32`、忘 `Apply()`、**y 轴翻转**、`ReadPixels` 时机、忘 `Destroy` → 每次存图泄漏 16MB） | 手写 `MapRenderer` / `LongImageExporter` |
| 协程与生命周期 | 基本用法能写对，错在边界（`SetActive(false)` 上静默不执行、**异常静默杀协程**、重复 `StartCoroutine` 导致双速） | tick 驱动不用协程，用累加器 + `bool _running` 守卫 |

**建议**：仓库根放一份 `CLAUDE.md`，把这些写成硬约束（AI 每次都会忘）：

```
- Sim 层禁 float/double/Mathf/Math./System.Linq/Time./UnityEngine.Random
- 所有溢出算术显式 unchecked
- 随机只用 Rng.For / Rng.Range，禁自写 PRNG、禁 System.Random
- 遍历只用定长数组和 List<T>，禁 Dictionary/HashSet 迭代
- 排序必须给全序比较器（四个键都要比）
- UGUI 禁 LayoutGroup / ContentSizeFitter / ScrollRect / Instantiate 进列表
- 存档只用 JsonUtility 泛型重载；禁 Dictionary、ValueTuple、属性、二进制
- 新增任何 Sim 字段，必须显式声明是否进 HashState
```

| 时段 | 干的事 | 产出 |
|---|---|---|
| **D1 上午** | 工程 + `noEngineReferences` asmdef + 双 Build Profile + **双端空包真机 + TapPlay 五条自检** | 空包不崩；知道这个环境能不能持久化 |
| **D1 下午** | 把 `refimpl/Sim/` 拷进项目；跑 `SelfTest` 的 G1–G5 | 同 seed 两遍一致；五个 bug 确认已修 |
| **D2 上午** | 假负载 + Bench | **真机的 ms/tick 和 GC/tick 数字** |
| **D2 下午** | 出 Android ARM64 IL2CPP 包 → 三端哈希比对 | **跨端确定性的最终裁决** |
| **D3 上午** | `DiversityProbe`（G6–G8） | **500 seed 形态数 + 反事实分岔 + 寄存器健康度** |
| **D3 下午** | InputLog 重放比对 | **三条技术裁决全出** |

**可自动跑的断言门槛**（不再是"看看活没活"这种主观判断）：

| 指标 | ✅ 通过 | ❌ 当场改方案 |
|---|---|---|
| 同设备两遍一致 | 无差异行 | 有差异 → 查静态状态，先别管跨端 |
| 三端六行哈希 | 全字节相同 | 不同 → grep float / 迭代顺序（半天能定位） |
| 单 tick（低端真机） | **< 0.5 ms** | **> 3 ms** → 减关系域卡数 |
| 稳态 GC Alloc/tick | **0 B** | > 4 KB → 有 `new List`/字符串没清 |
| **500 seed 形态数** | **≥ 3 类** | **< 2 类 → 立刻改方案，别写那 20 张卡** |
| **反事实分岔** | 必须分岔 | 不分岔 → **给评委的核心证明拿不出来** |
| **三寄存器 σ** | 金币 > 8、饥饿 > 5、恐惧 > 3 | **σ ≈ 0 → 该寄存器已死，所有相关条件变成死条件** |

> 最后三条是本报告新增的，也是最重要的。**"形态数"和"σ"这两条能在 D3 就告诉你 20 张卡写完也救不回来**——那时候改方案只要 1 天，D8 之后改就是重做。
