## 1. 威信 Authority

### 1.1 公式（每 tick，整数）

```
upkeep = UPKEEP_PER_LAW * activeSlots            // activeSlots = state!=Empty 且 非停摆 的槽数
regen  = (pop * REGEN_POP_NUM / REGEN_POP_DEN)                     // 人口项
       + (max(0, REGEN_CALM_FEAR - avgFear) / REGEN_FEAR_DIV)      // 低恐惧项
auth   = clamp(auth - upkeep + regen, 0, AUTH_MAX)
```

- `pop` 与 `avgFear` 取**本 tick 重算后的派生值**（`RecomputeDerived` 之后）。
- `avgFear = sumFear / aliveCount`，`aliveCount==0` 时该项为 0。
- 全程整数除（正数向下取整），无累积余数、无浮点。
- 「每 20 tick 扣 1 点」与「每 tick 扣 5 厘点」完全等价（20×5=100 厘点=1 点），后者精度更高，采用后者。

### 1.2 系数推导（可写进策划案）

单条法维持成本 = 5 厘点/tick。**纯消耗、零回复**时：`10000 / (5×5) = 400 tick` —— 这就是「满配 5 条撑 400 tick」的严格出处，它是**下限**。

回复项的设计目标：让「理想村庄正好养得起 2 条法」，让「恐惧/死亡会吃掉你的收入」（这是死亡螺旋的传导路径）。

| 村庄状态 | pop | avgFear | regen | 5法净速率 | 5法续航 | 3法续航 | 2法 |
|---|---|---|---|---|---|---|---|
| 理想（立国期） | 20 | 5 | 8+5=13 | −12 | 833 tick | 无限（−2，极慢） | +3 |
| 典型 | 20 | 15 | 8+3=11 | −14 | 714 tick | 无限（0） | +1 |
| 紧张 | 16 | 40 | 6+0=6 | −19 | 526 tick | 1111 tick | −4（2500） |
| 危机 | 12 | 60 | 4+0=4 | −21 | 476 tick | 909 tick | −6（1666） |
| **零回复（危机极限）** | — | — | **0** | **−25** | **400 tick** | 667 | 1000 |

**结论**：400 是下限，实际观测区间 400–830。一局 2400 tick，所以「5 条法」**永远只能是冲刺，不可能是常态**——设计目标达成。而 2 条法在理想态可长期维持，给玩家一个「退守安全线」，避免必败。

### 1.3 第一幕预算自检（验证「tick 0–400 写满 3 条」是否可行）

稳健节奏：L1@t20、L2@t150、L3@t300。

```
立法成本  3 × 3000                       = 9000 厘点 = 90 点
维持成本  5×(380 + 250 + 100) tick        = 3650 厘点 = 36.5 点
回复      ~11 厘点/tick × 400 tick        = 4400 厘点 = 44 点
期末 = 100 − 90 − 36.5 + 44               = 17.5 点   ← 紧张但可行
```

抢节奏（t0 连立 3 条）：维持 60 点 → 总支出 150 点 > 100 + 44 ⇒ **破产，触发停摆**。这正是想要的张力：**稳健可行，抢跑被罚**。

### 1.4 威信 = 0 时会发生什么

- **停摆（SUSPENDED）**：当 `auth` 在扣费后 == 0，所有**非宪法**在册法置 `flags.SUSPENDED`。停摆期间：不参与求值、不计命中、**不计维持费**（这是回复能爬起来的唯一原因）。
- **恢复迟滞**：`auth >= RESUME_AUTH (1000)` 时统一清 `SUSPENDED`。迟滞是必须的，否则「0→回复1厘点→开法→扣费→0」会每 tick 抖。
- 停摆期间村庄退回**基础物理**（饥饿 +8/tick、恐惧 −5/tick、关系 ×0.98 回归），日志大声播报：「**你的法已经没人听了。**」
- **宪法法永不停摆、永不疲劳、维持费为 0、不可废**（见 §8 立宪）。

> 从 0 恢复到 1000 厘点，典型态约 91 tick（`1000/11`）。威信枯竭的惩罚是「村庄无法治状态运行约 1.5 分钟」，戏剧性强且自愈，不软锁。

## 2. 立 / 废 / 调 / 赦免 的代价与冷却

| 动作 | 代价 | 冷却 | 是否走审议 | 可被阻塞？ |
|---|---|---|---|---|
| 立法 Enact | −3000 厘点 | 60 tick（**全局**，非每槽） | 否，立即入册 | 是（不足则禁用按钮） |
| 废法 Repeal | −2500 厘点 | 30 tick | 否 | **否，永不阻塞** |
| 调参 Amend | −300 × 档数 | 无冷却 | **是，40 tick** | 是 |
| 赦免 Amnesty | −4000 厘点 | 120 tick | 否 | 是（且全局 ≤3 次） |
| 排序 Sort | 0 | 20 tick | 否，立即生效 | — |
| 临时法令 Decree | −1500 厘点 | 60 tick | 否 | 是 |

**三条硬规则（防死锁，缺一必卡）**：

1. **只有「积极动作」需要足额威信**（立法/调参/赦免/临时法令）。`auth < cost` 时按钮置灰。
2. **废法豁免**：你永远可以「停止做一件事」。`auth < 2500` 时废法仍然允许，扣到 0 为止。否则玩家在威信枯竭时无法甩掉包袱，只能挂机等回复，节奏死掉。
3. **不可逆点的强制废法，代价豁免**（见 §8）。防止 tick 600 时威信不足导致流程卡死。

冷却语义：`lastEnactTick` 是**单个全局变量**（不是每槽），含义是「国会在休会」——同一时间只能推一部法，两法之间必须隔 60 tick。压住「一口气立 5 条」的爆发。

## 3. 制度疲劳

### 3.1 先纠一个数：×3 不合理

原文「累计命中 > 总人口 ×3」。按 20 人算阈值 = 60。而一条常开法在 20 人村庄里**几乎每 tick 都有 2–8 人命中**，60 次命中在 **tick 10–30** 就到了。也就是开局 15 秒所有法集体疲劳，「他们不怕了」的台词会在玩家还没搞懂规则时刷屏。**×3 与「逼玩家轮换」的目标不匹配，必须放大。**

### 3.2 修正公式

```
hitsThisTick = 该法本 tick 命中的村民数（已有字段）
hitsTotal   += hitsThisTick                       // 自入册起累计，repeal/重新立法清零
threshold    = popPeak * FATIGUE_K                // FATIGUE_K = 100
if (!Fatigued && hitsTotal > threshold) → 锁存 Fatigued，写 Chronicle，日志「他们已经不怕这条法了」
```

`popPeak` = 历史最高存活数（单调不减，每 tick `popPeak = max(popPeak, aliveCount)`）。

**为什么是 ×100**：读法是「**每个人平均被这条法收拾过 100 次，就皮了**」。一个常开法约 5 村民命中/tick，`2000/5 = 400 tick` 触发，正好落在「第二幕中段」——玩家刚吃完自己立法的红利，就要开始轮换。这是把 ×3 按「触发时点反解」出来的系数。

| K | 阈值 | 5命中/tick 下触发 | 2命中/tick 下触发 | 评 |
|---|---|---|---|---|
| 3（原案） | 60 | 12 tick | 30 tick | 太早，机制退化成噪声 |
| 50 | 1000 | 200 tick | 500 tick | 偏早 |
| **100（推荐）** | **2000** | **400 tick** | 1000 tick | 命中第二幕，逼迫轮换 |
| 200 | 4000 | 800 tick | 2000 tick | 太晚，多数局触发不了 |

**自平衡的副产品（值得写进宣传）**：`福利[无→每人+X金币]` 这种**全体命中**的法每 tick 命中 20 人，100 tick 就疲劳；而 `私刑[恐惧>X且有邻→攻击邻]` 条件窄，可能 2000 tick 才疲劳。**普惠法先失效，针对性法活得久**——这是法规政治学里非常真实的行为，且是纯涌现出来的，没人写死。

### 3.3 疲劳到底减什么（关键，别做错）

- **只减数值效果，不减二值效果**。`IsNumericEffect(effType)` 为真（金币/饥饿/恐惧/关系增量）时 `mag' = mag / 2`（整数向下取整）；`AddTag / RemoveTag / Kill / Flee` 等二值效果**不打折**。否则疲劳会悄悄让「打标签」失效，伤疤系统跟着崩。
- **不减条件阈值**。阈值若被减半，命中的**人变少**，那是反方向（法变得更温和地"少管人"），不是「他们不怕」。疲劳必须是「同一批人，但你打不动他们了」。
- **`mag==1` 的法，半衰后 `0`**，法变成纯维持费的空壳。这是**故意**的：它给玩家一个「这条法已经废了，废掉它」的强信号。配合「废法永不阻塞」不会死锁。
- **跨阈当 tick 仍按全效结算**，锁存后从**下一 tick** 起半效。
- 疲劳是**锁存**，不会自己恢复。唯一「刷新」路径：废掉（−25）→ 等冷却 → 重新立法（−30）→ `hitsTotal=0`。**刷新一条法的真实价格是 55 威信 + 90 tick**。这条经济闭环把 §2 和 §3 焊在一起。
- 宪法法免疫疲劳。

## 4. 伤疤 Scar

### 4.1 8 位标签位图（统一定义，零新系统）

```csharp
public static class TagBits {
    public const byte Coward   = 1 << 0;  // 怯懦  性格
    public const byte Greedy   = 1 << 1;  // 贪婪  性格
    public const byte Diligent = 1 << 2;  // 勤勉  性格
    public const byte Sickly   = 1 << 3;  // 病弱  性格
    public const byte Bandit   = 1 << 4;  // 劫匪  伤疤
    public const byte Debtor   = 1 << 5;  // 负债  伤疤
    public const byte Deserter = 1 << 6;  // 逃兵  伤疤
    public const byte Accused  = 1 << 7;  // 受审  伤疤
    public const byte TRAIT_MASK = Coward|Greedy|Diligent|Sickly; // 0x0F，可被 RemoveTag
    public const byte SCAR_MASK  = Bandit|Debtor|Deserter|Accused; // 0xF0，不可被 RemoveTag
}
```

**低 4 位 = 性格**（卡可以增删，制造短期分岔）；**高 4 位 = 伤疤**（律法打上，终身）。

### 4.2 伤疤不可清除的机械保证（3 行代码）

```csharp
void ApplyRemoveTag(Villager v, int bit) {
    if ((TagBits.SCAR_MASK & (1 << bit)) != 0) return;  // ← 伤疤免疫清除
    v.tags &= (byte)~(1 << bit);
}
```

废法路径里**根本不存在**任何「回滚标签」的代码——这正是「废法 = 止血，不是撤销」的实现方式：不是「记得不要清」，而是**从来没有清的地方**。这句话要写进代码注释，防止后来者（或 AI）「顺手加上清理逻辑」。

### 4.3 打伤疤的完整链路

```csharp
v.tags |= scarBit;
AddEvent(v, EvType.SCARRED, actorId: -1, targetId: -1,
         value: scarBit, cause: EvCause.LAW, lawIndex: slot);
```

- 该村民**从此**满足所有 `SelfHasTag(劫匪)` 门禁（事件卡自动被改写，零改动）。
- 讣告可以写「他变成劫匪，是你的第 2 条法」。
- 该村民**不满足** `SelfLacksTag(劫匪)` 门禁 —— 「清白」类卡对他永久关闭。

### 4.4 伤疤 × 事件卡 gate 的交互

| 交互点 | 行为 | 需要改的代码 |
|---|---|---|
| 卡的 `SelfHasTag/SelfLacksTag` | 直接读 `v.tags & bit`，**零改动** | 无 |
| 卡的 `RemoveTag` 效果 | 命中 SCAR_MASK 时**静默跳过** | §4.2 一行 |
| 卡想制造新伤疤 | 用新效果 `AddScar(bit)`（等价 AddTag，但写 SCARRED 事件 + 强制置 SCAR_MASK 位） | 新 EffKind，5 行 |
| 废法后的世界状态 | `v.tags` 一字不变；槽位清空。**「法没了，人还是劫匪」自动成立** | 无（结构使然） |
| 讣告 | 读最终 `v.tags` 的疤位 + `Chronicle` 里该法的 `REPEALED` 记录 → 「你早就废了那条法，可他到死都还是劫匪。」 | 讣告新增 1 个句式槽 |

**唯一能去除伤疤的东西是赦免**（全局 3 次）。救赎必须比系统性修复更难，这是主题的落点。

## 5. 状态机 A：审议中（调参延迟）

```csharp
public enum LawState : byte { Empty = 0, Enacted = 1, Deliberating = 2 }
```

| 问题 | 规格 |
|---|---|
| 用旧值还是新值？ | **旧值**（`condThreshold`/`effMagnitude` 不动），`pending*` 只是寄存 |
| 旧值还在杀人吗？ | **在**。这是「你的修正会迟到」的全部来源 |
| 审议期间能再次调参吗？ | 能。**替换 pending 值，计时器重置为 40，再扣一次 −3/档** |
| 审议期间能废法吗？ | 能。pending 丢弃，已付威信不退，疤痕保留 |
| 冷却 / 维持费怎么算？ | 按 `Enacted` 计（法还在册） |
| 能同时审议多条法吗？ | 能，各槽独立计时 |
| 倒计时用什么推进？ | **只认 sim tick**。绝不能用 `Time.deltaTime` |
| 停在 `deliberateEndTick` 的那一刻 | `condThreshold = pendingThreshold; effMagnitude = pendingMagnitude;` 写 Chronicle(`AMENDED`)，日志「**新法即日生效**」 |

**为什么是 40 tick**：一局里两次死亡的典型间隔在第二幕约 60–120 tick。40 意味着**约一半的修正会迟到**（人在你签字前就死了），另一半能救到。若实测死亡间隔 >150 tick，把 40 提到 60。

**UI 语义**：进度环 40→0 + 文案「旧参数 60 → 新参数 75（还有 23 秒生效）」+ 一行红字「**旧参数仍在杀人**」。没有这行红字，机制就变成「改了就生效」的错觉，戏剧性全丢。

## 6. 状态机 B：死刑节拍

```csharp
public enum SimFlow : byte { Running = 0, DeathPause = 1, DecisionPause = 2 }
```

**铁律：`SimFlow != Running` 时，`Tick()` 根本不被调用。** tick 计数器冻结 ⇒ 审议倒计时冻结、维持费冻结、世界冻结。暂停是**输入层的门**，不是模拟层的状态 ⇒ 对确定性零影响。

```
1. DeathResolution 收集本 tick 全部死亡 → List<DeathRecord>，逐人生成讣告
2. SimFlow = DeathPause
3. UI 弹讣告模态：
   - 1 人死亡 → 单篇讣告（默认展开）
   - ≥2 人同 tick 死 → 一篇「名单」模态，每篇可展开；标题「本日，他们死了。」
4. 模态内提供「修订法律」按钮 → 直接打开律法面板（不关闭模态，面板叠在上面）
5. 「继续」按钮 realTime 禁用 5.0s（Time.unscaledTime 计时），倒计时可见
6. 点击 → SimFlow = Running，从下一 tick 继续
```

**批量降级**：同一 tick 死亡 ≥3 人时，5s 门降到 1.5s，模态改为列表式；提供无障碍开关「老练模式：已读讣告 1.5s 自动跳过」。此开关**纯 UI**，不进哈希、不进存档。

**离线快进**：`min(离线秒数×speed, 600 tick)` 期间**不触发任何死亡暂停**；回来后弹一张汇总卡「你不在时，死了 4 个人」，可逐篇读。必须写死，否则离线回来会被 20 个暂停卡住。

**暂停期间的输入**：玩家可以在 DeathPause 内立法/废法/调参。命令立即写入 `PolityState`，但**对世界的作用发生在恢复后的第一个 tick**；审议计时从恢复 tick 起算。**输入必须记进输入日志**，否则重放会分叉。

**DecisionPause（不可逆点）**：
- `POINT1`（tick 600）：模态「**裂痕已经太深。你必须废除一条法。**」玩家必须选一条废掉（代价**豁免**）。手上 0 条法 → 跳过。
- `POINT2`（tick 1500）：模态「**立宪。最后两条候选法，只能留一条，永久写入。**」候选生成见 §8。可用候选 <2 → 从 12 预设确定性补足，**永不卡死**。

## 7. 七个动词（含一个节拍）

| # | 动词 | 输入形态 | 代价 | 冷却 | 审议 | 效果 |
|---|---|---|---|---|---|---|
| 1 | **立法** | 从 12 预设选 1 → 放入空槽 | −30 | 60 tick | 否 | 槽位 `Enacted`，`hitsTotal=0`，写 Chronicle(`ENACT`) |
| 2 | **废法** | 选一个在册槽 | −25（不足清零） | 30 tick | 否 | 槽位 `Empty`。**标签一字不动**。宪法不可选 |
| 3 | **调参** | 拖档，确认 | −3/档 | 无 | **是，40 tick** | 见 §5 |
| 4 | **排序** | 拖拽槽位 | 0 | 20 tick | 否，**立即** | 交换 slot 内容 ⇒ 改变「自上而下首个命中」的赢家 |
| 5 | **赦免** | 选一名村民 | −40 | 120 tick | 否 | 清该村民**全部伤疤位**、`fear -= 30`、写 `PARDONED`。≤3 次 |
| 6 | **命名 / 标记关注** | 输入名字 / 点星 | 0 | 无 | 否 | 纯呈现层：名字进存档，**不进哈希** |
| 7 | **临时法令** | 选预设 → 放入空槽 | −15 | 60 tick | 否 | `flags.Temp=1, expiryTick = tick + 200`，**占 1 个常驻槽**。到期自动清槽 |
| — | **村议**（节拍） | — | — | — | — | DeathPause + DecisionPause，见 §6 |

**排序不收费的理由**：排序是玩家的「方向盘」，收费会让游戏感觉迟滞；但若完全免费且瞬时，玩家会逐 tick 微操优先级来「点射」每条法——违背「你不操作村民」的立意。折中：**免费 + 20 tick 冷却 + 瞬时生效**。若实测仍有微操，加 −5 威信。

**临时法令的设计意图**：它是 5 槽压力下的**泄压阀**。约束在于它**占常驻槽**，所以 5 法满配时你根本塞不进去；只有在第二幕废法后（≤4 法）才有余量。这让「废法」在体感上不只是损失，也是**腾出战术空间**。

## 8. 四幕结构

| 幕 | tick | 机制职责 | 张力来源 |
|---|---|---|---|
| 一 立国 | 0–400 | 回复满速（pop 20、恐惧低），玩家从 0 写到 3 条法 | 威信预算刚好够（§1.3） |
| 二 裂痕 | 400–1200 | `ActAtLeast(2)` 解锁「民怨」系卡；**POINT1 @600 强制废一条** | 疲劳开始咬人 + 强制减法 |
| 三 崩塌或稳 | 1200–2000 | `ActAtLeast(3)` 解锁「立宪」系卡；**POINT2 @1500 立宪** | 永久锁死一条法 = 锁死一个结局族 |
| 四 清算 | 2000–2400 | 无新解锁，纯结算 | 结局面板 + 全部讣告可回看 |

### 8.1 立宪的确定性规则（防死锁）

```
候选池生成（tick == POINT2 时执行一次，写进 decisionPending 的载荷）：
  ① 取玩家当前所有非宪法在册法，按 slot 升序 → 若 ≥2 条，取前 2 条为候选
  ② 若 <2 条，用确定性补足：
       idx0 = (int)(RngFor(seed, POINT2, CH_CONSTITUTION) % 12)
       idx1 = (idx0 + 1 + (int)(RngFor(seed, POINT2, CH_CONSTITUTION+1) % 11)) % 12
       候选 = PRESET[idx0], PRESET[idx1]
```

选中的法写入一个槽并置 `flags.Constitutional = 1`：

- 维持费 **0**、**免疫疲劳**、**不可废**、效果照常参与求值、抢优先级
- **决定结局族**：结束时的 4 档判定读 `Constitutional.defId` 的**效果族**决定叙事结局（福利/济贫 → 仁政；私刑/恐惧蔓延 → 猎巫；逃难 → 空村；耕作/繁育 → 粮荒）

**这才是「立宪」有分量的原因：你把一个永久、免费、不可撤销的规则钉进了世界，而它只解决了你一半的问题。**

## 10. 与现有系统的接口

### 10.1 新 tick 循环（加粗为新增步骤）

```
void Tick(Village v) {
    if (flow != SimFlow.Running) return;          // ★ 暂停门：不推进模拟
 1. ResolvePendingDecisions(v);                   // ★ 立宪/强制废法的等待（正常时为 no-op）
 2. AdvanceDeliberations(v);                      // ★ 审议倒计时 → 到期提交 pending
 3. ExpireTempDecrees(v);                         // ★ 临时法令到期 → 清槽（不退款）
 4. RecomputeLawRuntime(v);                       // 现有：清 hitsThisTick、建 effectFirstSlot
 5. RecomputeDerived(v);                          // 现有：均值、存活数、popPeak
 6. ApplyAuthorityUpkeepAndRegen(v);              // ★ 威信结算 + 停摆/恢复判定
 7. RunLawDSL(v);                                 // 现有：连续演化
       ↳ 内嵌：hitsTotal 累加 + 疲劳检查 + 半效折扣 + SCARRED 事件
 8. EvaluateStorylets(v);                         // 现有：卡候选池
 9. ApplyCard(v);                                 // 现有：卡写入（可读写威信/伤疤）
10. DeathResolution(v);                           // ★ 收集本 tick 死亡
       ↳ 若有死亡 → flow = DeathPause，生成 DeathRecord 队列（不推进 tick）
11. v.tick++; v.hash = HashState(v);              // 现有
}
```

**顺序理由**：
- 威信结算在 `RecomputeDerived` 之后 —— 用**本 tick 的**人口/均值，逻辑直白且可复现。
- 审议/到期在律法求值**之前** —— 保证「第 40 tick 生效」就是那一 tick 生效。
- 疲劳在 `RunLawDSL` **内部** —— 避免再扫一遍全村民。
- 死亡判定在**卡之后** —— 让本 tick 的卡也有机会造成死亡。

### 10.2 事件卡的新接口

```
// —— 新 CondKind（卡的门禁可读）——
Auth / AuthRatePerTick / SlotsUsed / AmnestyLeft / AnyLawSuspended
ActAtLeast(n) / LawFatigued(sel) / LawState(sel) / LawDeliberating(sel)
LawHitsTotal(sel) / LawIsConstitutional(sel)
SelfHasScar / SelfScarCount
// 复用既有的 LawHitsThisTick / LawLastHitTick / ResolveLaw(sel)

// —— 新 EffKind（卡可写）——

SuspendLaw(sel, n)      // 让某法停摆 n tick（民怨）

AddScar(bit) / Pardon(targetId) / ClearFatigue(sel)
```

**关键纪律**：`AmendNow` 是**卡专用通道**。玩家的调参**必须**走 40 tick 审议。若卡也能瞬时改玩家法的参数，玩家会失去「修正会迟到」的核心体验；写代码时应在 `AmendNow` 上打注释禁止从玩家输入路径调用。

**随机通道**：卡的威信写入若带随机，用新 channel `CH_AUTH = 4`；立宪候选用 `CH_CONSTITUTION = 5`。**不得复用 `CH_DEAL`**。

### 10.3 伤疤 × 位图 × gate 的完整交互路径

```
律法命中 → ApplyEffect(AddTag(scarBit))
   → v.tags |= scarBit
   → AddEvent(SCARRED, cause=LAW, lawIndex=slot)      // 因果父指针
   → 该村民此后对所有 SelfHasTag(劫匪) 门禁为真       // 卡自动改写，零代码
        → 劫掠卡权重上升 → 更可能再犯 → 更深的疤     // 涌现
   → 废法：slots[i] = Empty，v.tags 不变               // 止血
   → 唯一出口：玩家的赦免（≤3 次）或极稀有的 Pardon 卡
```

## 11. 确定性逐条检查

| # | 机制 | 浮点？ | 哈希顺序依赖？ | 结论 |
|---|---|---|---|---|
| 1 | 威信结算 | 无，全整数厘点 | 无 | 安全（`aliveCount==0` 需守卫） |
| 2 | 代价/冷却 | 无 | 无 | 安全 |
| 3 | 疲劳 | 无，整数比较 + `/2` | 无（`popPeak` 单调） | 安全 |
| 4 | 伤疤 | 无，位运算 | **无（位图天然无序）** | 安全 |
| 5 | 审议 | 无 | 无 | ★ **倒计时必须用 sim tick，禁用 `Time.deltaTime`** |
| 6 | 死刑节拍 | 5s 门用 `Time.unscaledTime` | 无 | ★ **5s 门与 `SimFlow` 绝不进模拟、不进哈希**；离线快进禁用暂停 |
| 7 | 动词 | 无 | 无 | ★ 暂停期的命令必须记入 `journal` |
| 8 | 立宪候选 | 无，`RngFor` 取模 | 无 | 安全 |
| 9 | 事件卡写威信 | 无 | 无 | 需用新 channel `CH_AUTH`/`CH_CONSTITUTION` |
| 10 | 槽位遍历 | 无 | 无 | 安全（定长数组，不引入 Dictionary） |

**三个必须写单测的点**：
1. `LawSlot` 含两个 `int` 与一个 `byte`，序列化时 padding 可能不同 → **存档一律 `JsonUtility`**。
2. `HashState` 新增字段的**写入顺序必须固定**（建议：`authorityCenti → popPeak → act → decisionPending → amnestyUsed → 每槽按字段声明序`）。
3. 一个「暂停 30 秒后恢复」的回归用例：断言暂停前后 tick 数不变、审议倒计时不变、hash 不变。

## 12. 平衡风险（每一处最可能调崩的地方）

| # | 机制 | 最可能崩的方式 | 缓解 |
|---|---|---|---|
| 1 | 威信 | **回复过强 → 5 法变常态** | 回复上限被「2 条法」锚死；若实测 5 法能撑 >1200 tick，把 `REGEN_FEAR_DIV` 从 5 提到 8 |
| 2 | 威信 | **回复过弱 → 立不起 3 条** | §1.3 预算自检；停摆机制兜底不软锁 |
| 3 | 威信 | **停摆被误当成 bug** | 必须有**全屏级别视觉**（灰度 + 大字「你的法已经没人听了」） |
| 4 | 疲劳 | **K 太小 → 开局 15 秒全部疲劳** | 已从 3 改 100。**这是原案最危险的一个数** |
| 5 | 疲劳 | **锁存后无法恢复 → 第四幕空转** | 刷新闭环（废+立 = 55 威信）；宪法免疲劳；条件阈值不减半 |
| 6 | 疲劳 | **mag==1 半衰成 0 → 纯维持费空壳** | 故意保留，但 UI 必须显式标红「已失效·建议废除」，且废法永不阻塞 |
| 7 | 伤疤 | **4 位疤打满 → 村民失去区分度** | 预设法最多各打 1 位；赦免 3 次；把疤当「身份」写进讣告语料 |
| 8 | 伤疤 | **疤 → 更凶的卡 → 死亡螺旋** | 卡池保留 `AllLawsSilent` 类安全网卡；疤门的卡权重设低 |
| 9 | 审议 | **看着人被旧参数杀死 → 怒退** | 这是**设计要的情绪**；但 UI 必须提前告知「旧参数仍在杀人」 |
| 10 | 死刑节拍 | **屠杀 → 8 篇讣告连弹** | ≥3 人降级列表 + 5s→1.5s；提供「老练模式」 |
| 11 | 死刑节拍 | **8x 速度下频繁暂停** | 死亡暂停不受倍速影响（是设计）；但给「自动继续」无障碍选项 |
| 12 | 不可逆点 | **tick 600 手上 0 条法** | 0 条法时跳过该点 |
| 13 | 立宪 | **只有 1 条法凑不出 2 个候选** | §8.1 确定性补足分支，候选恒为 2 |
| 14 | 立宪 | **宪法效果族太弱 → 第四幕无存在感** | 宪法免维持费 + 免疲劳 = 后期唯一稳定器；需实测 |
| 15 | 临时法令 | **5 法满配时无处可放** | 这是**故意**的：泄压阀只在废法后可用的 |
| 16 | 排序 | **免费+瞬时 → 逐 tick 点射微操** | 20 tick 冷却；若仍有微操 → 加 −5 威信 |

**最该盯的三个回归指标**（自动跑 500 seed × 2400 tick）：
1. 第一幕结束时在册法数分布 —— 目标中位数 = 3，若 <2 说明威信太紧。
2. 5 条法状态的**平均持续时间** —— 目标 300–600 tick，>1200 说明回复过强、<150 说明过紧。
3. 疲劳触发次数分布 —— 若 90% 的局里某条法从未疲劳，把 K 降到 60；若每次开局 60 秒内全疲劳，K 升到 150。

> 所有字段名沿用 `事件卡机制规格.md` §1 的 C# 结构体（`LifeEvent.CauseLawSlot / ParentEventId / CauseDepth / Ordinal`、`LawRuntime.VictimsTotal / HitsThisTick / Voided`、`Village.Hash / LastFired / TriggerCount`、`RngFor(seed,tick,channel)`）。

## 0. 必须先拍死的三个对齐决定

### 0.1 横屏 vs 竖屏 —— 结论：横屏

理由：核心画面是 24×16 格地图（内容长宽比 1.5:1，本身就是横的）+ 20 个小人。横屏还顺带解决一件事：**底部一整条拇指带可以横跨全屏宽**，比竖屏更容易把「时间轴 / 村民条 / 律法槽」三簇全塞进拇指区。

| 项 | 总纲（竖屏） | 本作（横屏） |
|---|---|---|
| Reference Resolution | 1080×1920 | **1920×1080** |
| Match | 1（按高度匹配） | **1（仍按高度匹配）** |

- Match=1 意味着：1080 高时坞 = 280px；1440 高（PC）时坞按比例 = 373px。拇指热区比例恒定。
- **竖屏窄窗（PC 窗口被拖成竖的，宽高比 < 1.2）**：内容按 1920×1080 等比缩放居中，上下 letterbox。**不重排布局**——重排等于做第二个游戏。
- **超宽屏（宽高比 > 2.2）**：把世界两侧的**只读 HUD 栏**从窄变宽，仅此一处。

### 0.2 人数 20 vs 12 —— 按 20 做，但一个优化从「可选」升级为「必须」

1. **快照体积按 N² 涨**。`LastFired` / `TriggerCount` 的长度是 `cardId × NumTargets`，而 `NumTargets = 1 + N + N(N-1)`：N=12 时 145，N=20 时 **401（2.8 倍）**。按 80 张卡算，朴素全量快照 = 约 **199KB/张**。这直接判死「每 tick 存快照」。
   → **结论：§2 的稀疏编码快照从「优化」变成「强制」**（把 199KB 压到 ~12KB）。
2. **AI 头像撞脸**。20 张脸 AI 生成必然撞。反撞脸工艺见 §3.1，不是"注意一下"，是要写进生成脚本的硬约束。

### 0.3 玩家动词从 1 个扩到 3 个 —— 全部必须进输入日志

> **任何会改变模拟状态的玩家输入，落点必须是「tick 序号 + 槽位 + 新值」三元组，追加进 `InputLog`。**

因为 #3 倒回去 / #6 回放 / #9 反事实重放全部依赖「seed + InputLog 可完整复现本局」。输入日志一旦漏记一类输入（最容易漏的是吊销和听证答复），这三个功能会**静默错位**——不报错，只是重放出来的世界和刚玩的不一样。**这是本规格里最容易踩、最难查的坑。**

40 tick 延迟对确定性的影响：**无**。延迟是模拟内部的纯函数行为，重放时同 tick 施加同一输入，延迟自然复现。不要把 `effectiveTick` 写进日志，只写 `pressedTick`。

## 2. 确定性重放内核（#3 / #6 / #9 的共同地基）

**这是本次最高优先级的一件事，且它必须落在 D2/D3，不能后补。** 输入日志和快照钩子如果没在确定性脊柱落地时就埋进去，事后补等于把 D2 的哈希回归测试全部重跑，且极可能漏记录某类输入。

### 2.1 输入日志 `InputLog`

```csharp
struct InputEntry { int Tick; byte Kind; byte Slot; int Value; }
// Kind: ApplyLaw / AdjustParam / VoidLaw / HearingReply / SetSpeed(不入模拟)
// 只记会改变模拟状态的输入。速度/暂停/相机是表现层，不进日志。
List<InputEntry> InputLog;   // 一局 ≤ 200 条，<4KB
```

### 2.2 快照：稀疏编码 + 30 tick 关键帧

| 组成 | 朴素 | 稀疏后 | 说明 |
|---|---|---|---|
| 20 × `Villager` 定长部分 | 1.3 KB | 1.3 KB | 含 Faith[5]、TagBits、ExemptMask |
| `Rel` / `Wound` / `Ledger` (3×400 int) | 4.8 KB | 4.8 KB | 变化密集，不稀疏 |
| `LastFired` + `TriggerCount` | 192 KB | **~4 KB** | 只存**非默认槽**——这是把 199KB 打到 12KB 的唯一一刀 |
| `Laws[5]` + Flags + Seed | ~0.4 KB | 0.4 KB | |
| **合计** | **199 KB** | **≈ 12 KB** | |

- **关键帧环**：全程每 30 tick 一张，2400 tick → 80 张 × 12KB = **960 KB**。
- **不存逐 tick 快照。** 任意 tick T = 取 ≤T 最近关键帧 + 前向重放 ≤30 tick。

### 2.3 重放 API

```csharp
Village SnapshotAt(int tick);          // 关键帧 + 前向 ≤30 tick，纯函数，无 Unity 依赖
void    RestoreInto(Village live, int tick);
void    ReplayFrom(int fromTick, InputLog log, Action<int> onTick); // 供 #9 分帧/后台用
```

### 2.4 成本核算（所有性能结论的算尺）

单 tick 主要开销是 `EvaluateStorylets`：deck 80 张卡、N=20 时 `NumTargets=401` → 80×401 = **32,080 次 `Passes()`** → 约 **15 万次整数比较/tick**。

- 低端 ARM（IL2CPP，保守按 1 亿次整数操作/秒）：单 tick ≈ **0.15ms**，2400 tick 整局 ≈ **0.36s**
- 中端机：≈ 0.15s；PC：< 0.1s

由此推出：
- **关键帧前向重放 ≤30 tick = ≤4.5ms**（低端机）。拖动时间轴时每帧 ≤0.5ms，**60fps 下 CPU 占用 < 5%**。
- **#9 反事实重算一局 = 0.36–1.5s（低端机）**。

### 2.5 内存总账

| 项 | 体积 |
|---|---|
| 关键帧环（全程） | 960 KB |
| 事件日志（~3000 条 LifeEvent × 48B） | 144 KB |
| InputLog | <4 KB |
| 村民/律法/关系 活状态 | ~20 KB |
| **小计** | **≈ 1.15 MB** |

**结论：手机可行，余量很大。** 降级方案不必启用。

### 2.6 双端一致性校验

- 每 30 tick 打关键帧时顺带存 `Hash`；**重放到该关键帧时重算 Hash 并比对**，不一致 → dev build red screen 报「重放漂移 @tick N」。
- 这同时是双端 diff 工具：两端同 seed 同 InputLog 各录一份关键帧 Hash 序列，第一处不同即 bug 位置。

## 3. 逐项规格 #1–#9

> 工时口径：单人 + AI 辅助，单位小时；已含自测，不含美术出图时间。

### 3.1 #1 给 20 个村民写脸

- **D2 村民条** 2×10 恒定显示：头像 + 姓名（20px）+ 状态环（外圈=健康，色相随 Hunger 从赭→朱）。**姓名常显是最关键的一条**——不靠 hover。
- 已死者：头像去饱和 + 30% 明度 + 右下角一个朱色小十字；仍可点，点开是该村民的讣告。
- **数据**：20 × (姓名 + 1 怪癖 + 1 关系) = 60 个词，编译期常量表（`VillagerDef[]`），**进 `Village.Hash`**。生成器：Editor 脚本或外部 Python，从词表按 `seed` 确定性组合，输出 `villagers.json`，diff 友好。
- 关系是**有向的**。**注意既有 `Villager` 里已有 `Spouse/Bond`，新的"母亲/债主/情人"应作为关系初值写入 `Rel/Wound/Ledger` 而不是新增字段**，否则哈希要动。
- **反撞脸工艺（必须写进生成脚本）**：① 统一「剪影 + 一个特征物」构图，特征物 = 该村民的怪癖，**怪癖直接画进头像**；② 全 20 张限定 **12 色调色板**，色相错开，两两轮廓/主色至少差 2 档；③ 出图后跑**感知哈希去重**（pHash 汉明距离 < 8 判撞），撞了重生成 —— 20 张里必撞 2–3 对。

**工时：6h**

### 3.3 #3 倒回去

- **D1 左簇时间轴** = 横贯 450px 的 scrubber，显示**最近 60 tick**（可继续左拖到全程）。轴上标点：**朱点=死亡**、**朱圈=律法首次在该村民身上触发**、赭点=关系突变。数据直接来自 `LifeEvent`。
- **拖动 → 世界进入只读回放态**（画面降饱和 60% + 顶部横幅「回看 第 07:14 / 现在 07:32」），松开即停在该 tick。
- 停在某一 tick 时，**死亡村民身上拉出一条朱色连线连到他 `CauseLawSlot` 对应的律法槽**（D3 对应槽同时高亮）—— 这就是"是谁先动的手"的答案。
- 三个按钮：**「回到现在」** · **「从此处继续」**（仅 dev/自由模式，主流程不开放，因为它会改写 InputLog） · **「钉住对比」**。
- 手机：双指捏合改时间轴缩放（**全局唯一允许的手势**，且只作用于 D1 区域）；PC：滚轮微调 ±1 tick。

**确定性实现**：拖到 tick T = `SnapshotAt(T)`。**这是确定性模拟白送的能力，不需要录像。** 滚动优化：维持 `scrubCursor`，连续拖动只做增量前/后步。**死亡后自动预置**：讣告弹出时后台已把 `[死亡tick-30, 死亡tick]` 预热，玩家一按立刻有位。
**性能**：单次 seek ≤4.5ms，拖动每帧 ≤0.5ms。
**降级**：低端机拖动时改**离散跳变**（每 5 tick 跳一次），松手后再精算。
**工时：8h**

### 3.4 #4 吊销正在杀人的法

**两个入口，同一动作**：
1. **讣告纸底部（主入口，情绪最高点）**：讣告正文写完「他死于你的第 2 条法《仓廪令》」之后，正下方就是朱色按钮 **「吊销《仓廪令》」**。→ 二次确认 → 执行。
2. **D3 律法槽长按**：展开详情卡，底部有「吊销」+「移除出 5 槽」。

**区分两个动作**：
- **吊销（VoidLaw）**：法还在槽里但被架空（`LawRuntime.Voided = true`），不再命中——**保留"它曾经杀过人"的历史**（`VictimsTotal` 不清零）。
- **拿掉（RemoveSlot）**：清空槽位，可贴新法。**只允许在暂停态做**。

**确定性实现（最关键）**：吊销/移除**都是玩家输入，必须写进 `InputLog`**。**漏记这一条，#3/#6/#9 全部静默错位。** 吊销**不产生新的随机流**，只翻转一个 bool，不触碰 `RngFor` 任何 channel —— 不会扰动 `CH_DEAL`。

**工时：6h**（含 2h 重跑哈希回归，省不掉）

### 3.5 #5 导播镜头

- **顶栏开关**：`[导播 ●]`（默认开）。关掉后镜头静止全景，一切自动化停止——**给想自己看的人留门，也是性能兜底开关**。
- **评分函数**（每 tick 扫描新增 `LifeEvent`，纯整数打分）：

| 事件 | 分 | 冷却 |
|---|---|---|
| 死亡（`DIED_*`） | 100 | 必切，无冷却 |
| 某条法**首次**命中某人 | 60 | 同法 12s |
| 濒死（`Hunger ≥ 阈值 且 无粮`） | 30 | 同目标 8s |
| 抢劫 / 冲突 | 20 | 同对 6s |
| 关系突变（`Rel` 单跳 ≥ 30） | 10 | 同对 6s |
| 出生 / 结盟 | 15 | — |

- **全局冷却 3s**（防镜头癫痫）。同 tick 多事件取最高分。
- **执行三件事**：① 相机 0.4s SmoothDamp 推近（全景 → 约 9×6 格，2.5×）；② 时间降到 **0.5×，持续 1.5s 真人时间**；③ C 字幕条出一行字 + `[看]` 按钮。
- **"重播"**：字幕条在 B2 留最近 20 条，点任一条 = 跳到那一刻（复用 #3）。

**确定性**：**慢镜不破坏确定性**——确定性是逐 tick 的；慢镜只改变"一 tick 占多少墙钟时间"，是**表现层时钟**。导播**不写任何模拟状态**。它自己的抖动若需随机，**必须用 `RngFor(seed, tick, CH_PRESENTATION)`**，**绝不复用 `CH_DEAL`**。镜头是 float 插值但只活表现层，不进 `Village.Hash`。

**降级（三档）**：① 关掉慢镜，只推镜头；② 慢镜改为**推近后停 1s**；③ 只保留字幕条一行字 + 目标头顶闪一下，相机不动（**"被喂食"的最小可行形态**）。
**工时：12h**

### 3.6 #6 回放（把归因从"读"改成"看"）

- **讣告纸底部第二颗按钮**：`[回放]`。仅当这次死亡属于**"名场面"**才亮起；普通死亡置灰。
- 按下 → 全屏回放态：**镜头飞到死者身边**，把他一生的 **3 个关键事件**在地图上慢镜重演（每段 4–6s，可跳过）。
- 每段画面旁浮出一行**带箭头的归因**：**「这是你的第 2 条法 ·《仓廪令》」**（取 `LifeEvent.CauseLawSlot`，`-1` 时显示「不是哪条法，是他自己」）。
- 三段播完 → 停在一张"定格判决卡"：死者头像 + 三段因果链 + `[存图]`。
- **名场面判定（纯数据）**：首次死亡 / **连锁 ≥3 跳**（`CauseDepth >= 3`）/ 稀有死法 / 一条法单局 `VictimsTotal >= 5`。

**确定性**：回放 = 对 3 个 tick 各做一次 `SnapshotAt`，**不录像、不额外存储**。**这是把关键帧做成"全程"而非"最近 N tick"的唯一理由**——如果只做最近 60 tick 的滚动窗口，#6 就废了。
**降级**：低端机把回放从"3 段动态重演"降为"3 张定格画面 + 归因箭头"。
**工时：10h**

### 3.7 #7 因果连线图 / 判决书长图

- 结算页 `[生成长图]` → 预览 → **`[存到相册]`** + **`[复制文案]`**。
- 版式：**左列 = 你写的 5 条法（玩家原文）**，**右列 = 死者头像 / 姓名 / 死因 / 死于第几 tick**，**中间用贝塞尔曲线连线**，底部一行**史官评语**。
- **两版同时出**：9:16（1080×1920）+ 1:1（1080×1080）。

**联网约束下的"分享"**：
- 官方禁止联网 → **不能调起微博/小红书 SDK，不能上传**。
- 因此「自动带话题标签与水印」= **画进图里** + **把 `#立法村 #他们死于你写的法律 #涌现` 与一段文案复制进剪贴板**（用 `systemCopyBuffer`）。
- 结算页要有一行提示：「图已存相册，文案已复制，去发帖吧」——**不说这句，玩家不知道怎么发，传播链断在这里。**

**确定性**：连线数据 = 对每个死亡跑 `AttributeDeath`（沿 `ParentEventId` 上溯取最近 `CauseLawSlot`），再加 `CountEventsPerLaw` 做**多法协同归因**（一条命可以被两条法同时解释——这正是"涌现"最好看的地方，长图上要画成两条箭头汇入同一个头像）。

**性能**：UI Canvas → `RenderTexture(1080×1920)` → `ReadPixels` → `EncodeToPNG`。峰值内存 **16.6MB 瞬时**，**必须渲染完立刻释放 RT**。PNG 编码走 `Task.Run` 后台线程，**0.3–1s**。
**降级**：降到 720×1280（峰值 7.4MB）+ 只出 9:16。
**工时：12h**
**双端差异**：**写入相册是唯一需要分端的代码**——Android 走 MediaStore（API 29+ 免权限）/ `WRITE_EXTERNAL_STORAGE`（API 28-）。包在 `IPhotoSaver` 接口后，两端都实现。

### 3.8 #8 「最致命的法」

- **结算页常驻一行**：大号字 `你的一条法《仓廪令》杀了 11 人`，下面一行小字 `本机最好成绩：14 人`。旁边 `[生成分享图]`。
- **确定性实现 —— 白送**：`LawRuntime.VictimsTotal` 已在每 tick 维护，**直接 `argmax`，零新计算、零新字段、零新 UI 数据源**。
- **本机记录存储**：存档加 `List<(int LawTextHash, int KillCount)>`，取 max 展示。
- **工时：3h**

### 3.9 #9 反事实重放

- **结算页主按钮**（最大、最显眼）：`「如果第 3 条《仓廪令》的阈值是 80 呢？」`（按钮文案由本局最致命的那条法**动态生成**）。
- 按 → 参数步进器（只允许调**一个**参数）→ `[开始重算]` → 全屏进度环 + `正在重算 1,240 / 2,400 秒`（数字实时跳动，本身就是一个"它在认真算"的说服）+ `[取消]`。
- 完成 → **左右分屏对照**：上=两个世界的缩略地图并排（死者朱色叉）；中=**20 人一一对应的存活对照表**（差异行整行高亮）；下=**差异结论一行**：`少死 4 人 —— 但第 7 个村民在 320 秒时就死了（原世界活到最后）`；一条**同步时间轴**，拖动 = 两个世界同时回放。

**后台分帧的具体做法（本项核心）**：
1. **不从 seed 重跑，从分岔点重跑**。分岔 tick `Tb` = 玩家改参数那次输入的 `pressedTick`。取 `SnapshotAt(Tb - 40)`，**只重算 `[Tb, 2400]`**，前缀直接复用原世界。这一刀砍掉最多 40% 的工作量。
2. **放 worker 线程，不做主线程分帧**。确定性纪律（零浮点 + 自写 PRNG + 扁平数组 + `unchecked`）让模拟**天然线程安全、零 Unity 依赖**，可以 `Task.Run` 全速跑。
   - **为什么不做"每帧 4ms 分帧"**：低端机全速跑完剩余 ~1400 tick 约 **0.6–1.5s**；按每帧 4ms 切片要切成 **150–400 帧 = 2.5–6.5 秒墙钟**，**反而更慢**。**worker 线程全速 + 主线程只读进度**是唯一正确解。
3. **进度上报**：worker 每 N tick 写一个 `volatile int progressTick`，主线程读它刷进度条。**不用锁、不用队列**。
4. **结果存储**：新世界只需 `(存活/死亡, 死亡tick)` 20 条 + 差异列表 → 几百字节。若要"双世界同步回放"，再存新世界关键帧（960KB）。
5. **`[取消]`**：`CancellationToken`，worker 每 tick 检查一次。
6. **切后台**：重算中切后台 → **取消并丢弃**（因为 ≤1.5s，重来一次成本可接受）。**不要在后台续跑**。回来时按钮还在。

**降级（三档）**：① 只算"谁死谁活"的存活对照，**不做双世界同步拖动**（省掉 960KB 和一半 UI，几乎不损失说服力）；② 只对比**最致命的那一条法**；③ 极限：把反事实结果**预算好 3 组**（阈值 ±20），结算时直接播预置结果，**零实时计算**。
**工时：18h**
**美术**：约 0 张新图（复用 #7 的头像与底板）。

## 0. 三条硬约束对各改动的裁决（先说结论）

| 4 本地通知 | 是 | 极低 | **砍** |
| 5 墓碑园/年鉴/图鉴 | 是 | 低 | 可做，但手游下退化 |

**最重要的两个判断**：
1. **周解锁千万不要做成"相对首次启动日"**。评审期是固定窗口，用 `weekIndex = clamp((今天 - 2026-10-25).天数 / 7, 0, 5)` 即可。这样解锁进度**不需要任何存档**，存档被清空也不回退，双端自动同步，论坛话题自然对齐。
2. **手游的留存不能押在依赖持久化的功能上**。请愿信红点、周解锁、暴君模式三者才是不怕沙盒被清的留存骨架。

## 1. 存档架构

### 1.1 分层与文件清单（全部位于 `Application.persistentDataPath`）

| 文件 | 内容 | 进哈希？ | 写入频率 |
|---|---|---|---|
| `sim.json` | 当前局 `SimState` | **是** | 每 tick 可选、退出必写 |
| `sim.bak` | 原子写备份 | — | 与 sim 同步 |
| `meta.json` | 跨局元数据（祖制/年鉴/墓碑园/图鉴） | **否** | 局结束 + 死亡事件（debounce 5s） |
| `meta.bak` | meta 备份 | — | 同 meta |
| `prefs.json` | 时间戳/解锁/设置/热座/沙盒 flag | **否** | 退出 + 关键操作 |

`LifeEvent` 表放在 `sim.json` 而不是 meta：因为事件卡门禁会读历史，所以它必须进哈希、必须确定性。

### 1.2 关键字段

**`sim.json`（▲ 为新增）**：`seed / tick / day▲ / villagers[] / laws[] / lawRuntime[] / lastFired[] / triggerCount[] / rngState / hash`。`day` 由推演推进，**进哈希**（否则双端 day 会不同）。

**`meta.json`（全新）**：
```
v / runsPlayed / totalDeaths / deathsByTemplate[12] / graves[] / codexCombos[] / obituaryRead[] / legacy[] / petitionReadBits
```
容量上限：`graves` 512 条（超出淘汰 deathDay 最早的）；`codexCombos` 4096；`obituaryRead` 1024。

**`prefs.json`（全新）**：`v / lastExitUtcMs / firstLaunchUtcMs / clockTamperCount / notifAsked / hotseat{} / sandboxMode / settings{}`。注意 `unlockedWeek` **不存**——每次从系统日期现算。

### 1.3 版本号与坏档兜底

**文件头统一**：`{"_v":1,"crc":<int>,"payload":{...}}`，crc 为 payload 序列化字节的 CRC32。

读取流程：解析头 → 校验 `_v`（新版拒绝加载，旧版跑迁移链）→ 校验 CRC → 失败读 `.bak` → 两者都失败则**分级兜底**：
- `sim.json` 坏 → 当前局作废，用默认初始状态开新局；**但 meta 能独立读出来就保留**（墓碑园/年鉴/祖制不能因为一次 sim 坏档全丢）。
- `meta.json` 坏 → 重置为空 meta，**不阻塞开局**；给一次提示"档案损毁，史书从这一页重写"。
- `prefs.json` 坏 → 时间戳归零 → 触发"无 lastExitUtcMs"分支（不推演、不报错）。

**原子写**：写 `x.tmp` → `File.Replace(tmp, x, x.bak)`。

### 1.4 确定性隔离规则（必须写进代码注释）

1. `HashState()` **只**吃 `SimState` 的模拟字段。
2. 元数据写入**永不在 tick 循环内**：先入内存 dirty 队列，debounce 5s 或退出时批量落盘。
3. 新增 `sim.json` 字段时，**必须显式决定是否进哈希**并在代码里注释；默认不进。
4. **祖制影响初始态的正确姿势**：开局时先 `SimState init = InitFrom(seed, LegacyProjection)`，**从 init 起**才哈希。
5. ⚠️ **分享码冲突（必处理）**：若祖制改变初始态，光有 seed 复现不了。推荐 **(b) 分享码一律用"无祖制标准初始态"复现**，并在分享页注明"你的祖制不会跟着分享码走"。零额外工时。

## 2. 逐项规格

### 2.1 跨局祖制继承

**存哪**：`meta.json` 的 `legacy[]`（最多 8 条，取最近 3 局的法）。

**继承不是直接复制法条**——法是玩家下一局自己选的。祖制影响的是**新村的初始状态**，用一张硬编码 12 行映射表投影：

```
LegacyProjection {
  int popBonus;    // 初始人口偏移 [-3,+3]
  int foodBonus;   // 粮仓初值偏移 [-30,+30]
  int fearBase;    // 初始恐惧偏移 [-20,+20]
  int goldBias;    // 初始金币偏移 [-10,+10]
  uint preTagMask; // 预置标签
}
```
映射表是内容，手写 12 行（如 `模板3 饥则抢 → foodBonus-20, preTagMask|=劫匪`）。**这是新增内容量，别漏算工时。**

**开局 UI**：新局第 1 天弹一次卡片：「上一局的第 {slotIdx+1} 条法（{模板名}）已成为本村的祖制」。仅一次，可跳过。
**工时**：2.5 天。**影响**：次留强、人均局数强、下载量弱。

### 2.2 离线续演

**核心设计（避开 tick 膨胀）**：不要让"现实秒 × tick 率"等价换算——那会一次补算 86400 tick。改为 **"1 现实天 = 1 村庄天 = 跑一局"**：
- 离线 N 天 → 循环 N 次 `SimRunner.RunSilent(sim, TICKS_PER_DAY_MAX=120, out evts)`，**与在线 tick 同一函数** → 结果与"在线看着它跑"完全一致。
- 单次预算：120 tick × 0.2ms ≈ 24ms。**分帧**：内部每 40 tick `yield`，一天 3 帧。N=14 → 42 帧 ≈ 0.7s，顶部进度条"正在结算第 N 天…"。**总计 1680 tick ≈ 336ms CPU，绝无 ANR 风险。**
- 村庄灭绝 → 立即停推。

**上限与防作弊**：
```
elapsed = nowUtcMs - lastExitUtcMs
回拨 >5min  → tamperCount++, elapsed=0，不推进、不报错
前跳 >30 天 → tamperCount++（仍按 14 天上限推演）
offlineDays = clamp(elapsed/86400000, 0, 14)
tamperCount >= 3 → offlineDays = min(offlineDays, 1)
缺 lastExitUtcMs → 不推演，直接进当前局
```
不做惩罚性封禁——单人游戏惩罚作弊无意义。

**日报**：`OfflineReport{ days, goodEvents[], badEvents[], popDelta, foodDelta, deaths, extinctAt }`。**必须同时有一好一坏**：若真实推演全好或全坏，从另一池**用真实模拟再跑一次筛选**注入一条，不硬编。

**工时**：3 天。**影响**：次留强、人均局数中。**但手游 TapPlay 下大概率失效。**

### 2.3 未读请愿信（本批最高 ROI）

**生成是确定性的，已读是非确定性的——必须分开存**：
- `sim.json`：`petitions:[{id, day, kind, signers[], topicTemplateId, stance, textTemplateId, textArgs[]}]`，**进哈希**。`id` 派生自 `(runIndex, day, seq)`，稳定。
- `meta.json.petitionReadBits`：按 `id` 索引的位图，**不进哈希**。

**红点** = `petitions.Count - popcount(readBits)`，HUD 常驻，退出时保持未读。
**请愿 = 议程**：点开信 → 底部「就此立法」→ 跳到立法 UI 并预填 `topicTemplateId`。**这一步把"读信"焊到核心动词上。**

**工时**：3 天。**影响**：次留强、人均局数强、下载量中。**且不依赖持久化，TapPlay 下 100% 可用。**

### 2.4 本地通知

**平台现实**：本项目**只交 Android + Windows**，不做 iOS。Windows 无推送需求。所以**只需 Android 一种实现**。

**Unity 做法**：官方包 `com.unity.mobile.notifications`。
- `AndroidNotificationCenter.SendNotification`，需建 `NotificationChannel`。
- Android 13+ 需 `POST_NOTIFICATIONS` 运行时权限。
- **权限申请时机**：不在启动弹。在"玩家首次看到日报之后"或"首次切后台时"。

**内容用"预测推演"生成**（很漂亮的一点）：退出时深拷贝 sim → `RunSilent(predict, 3×120)` 预演 3 天 → 因为玩家离线不干预，**预测结果 = 玩家回来时的实际结果** → 通知文案是真的：
```
"你的村庄第 {day+2} 天，粮仓见底了。"
"第 {day+1} 天，又有人死在你写的第 {i+1} 条法律下。"
"村口压着一封没拆的联名信。"
```
一次性排 3 条，延迟 22h / 46h / 70h。预测跑 360 tick ≈ 72ms，在退出回调（5s 预算）内安全。

**TapPlay 限制（直说）**：免安装环境的 app 身份/包名注册可能不完整，**本地通知大概率不可用（估 <30%）**。
**工时**：2 天。**影响**：次留在 TapPlay 下打折到接近 0。**建议砍。**

### 2.5 墓碑园 + 年鉴 + 图鉴

全在 `meta.json`，**不进哈希**。
- `graves[]`：名字用 `nameSeed` 生成**不存字符串**；墓碑坐标**不存**，按 `hash(charSeed)` 确定性摆放。
- 年鉴：`runsPlayed / totalDeaths / deathsByTemplate` 求 argmax = 最常死因。
- 图鉴：`codexCombos` 存 5 元组 hash，显示"已见 X 种"（不给分母，避免暴露 N 算不准）。

**工时**：2.5 天（**美术是瓶颈**）。**影响**：次留弱、人均局数强、下载量无。

### 2.6 41 天评审期周解锁

**不存**。每次现算：
```
weekIndex = clamp((本地日期 - 2026-10-25).Days / 7, 0, 5)  // 6 周
```
用**本地日期**（`DateTime.Now.Date`），不用 UTC。
- 若玩家改时间回拨，`weekIndex` 会退，但**只影响锁，不删已解锁内容**。
- 兜底：玩家 12 月才下 → `weekIndex` 直接 = 5，全解锁。**绝不能出现"过了评审期就玩不到内容"。**
- 6 周各解锁一套法条 + 一个村庄结构（粮荒/宗教/矿区/瘟疫/…），并弹「本周新法」卡片。

**工时**：1.5 天。**影响**：次留弱、人均局数中、**第 7/14/28 天留存强**、**论坛热度强**。**本批唯一不怕沙盒被清的核心节奏机制。**

### 2.7 本地热座 2–4 人

`prefs.json.hotseat{enabled,players,current}`，**会话内为主**。同一设备轮流写一条法，全部写完一起开跑看结果。
**工时**：1.5 天。**影响**：次留无、人均局数无、**下载量/论坛热度中**（零联网条件下唯一的社交补丁）。

### 2.8 暴君/实验模式

`prefs.json.sandboxMode:bool`。`isSandbox=true` 时**屏蔽一切 meta 写入**，UI 明示"不计入史书"。
**工时**：0.5 天。**影响**：次留无、人均局数弱、**下载量中**。极廉价，**必做**。

## 3. TapPlay 免安装环境存储兜底（专项）

### 3.1 现实评估（直说）

| 功能 | 手游 TapPlay 可靠性 | 理由 |
|---|---|---|
| 祖制继承 | **30–50%** | 跨会话需 meta 存活；会话内 100% |
| 离线续演 | **30–50%** | 跨会话需 sim + lastExitUtcMs 同时存活 |
| 墓碑园/年鉴/图鉴 | **30–50%** | 跨会话需 meta 存活 |
| 通知 | **<30%** | 跨会话排程 + 权限，双重不确定 |
| 请愿信 / 周解锁 / 暴君 / 热座 | **100%** | 不依赖持久化 |

**结论：手游的留存骨架只能是"不怕被清"的那四项。**

### 3.2 兜底策略（三层）

**第一层 · 多路写入**
- 主：`Application.persistentDataPath/x.json`
- 副：**Android SharedPreferences**（把 `meta.json` + `prefs.json` 的压缩串塞进一个 key）。SharedPreferences 位于 app 私有目录，在多数沙盒策略下比普通文件目录更可能保留。
- 三：`Application.temporaryCachePath` 只作同会话热备。
- 合并读：三处任一处能解出 CRC 正确的档即用；多份冲突时取 `lastExitUtcMs` 更新者。

**第二层 · 启动探针（D3 前必须验证）**
```
if (probeExists && probeContent == expected) persistentAcrossSessions = true;
else persistentAcrossSessions = false;
写一个带当前时间戳的探针文件，下次启动比对
```
**这是整个方案的地基假设，必须在 D1–D3 真机实测**（写探针 → 杀进程 → 重开读）。不验证就是在赌博。

**第三层 · 降级运行**
- 检测到不持久化 → 静默切"会话内模式"：
  - 祖制继承：**在同一会话内**保留（内存 meta，连开多局照样继承）——玩家一晚上连开 3 局时钩子完全成立，这是手游真正能拿到的价值。
  - 离线续演：退化为**"后台假离线"**（进程存活时切出去再回来能推演）。
  - 墓碑园/年鉴/图鉴：同会话内累积。
- 绝不向玩家报错，最多在设置页写一句"本设备可能不会保存你的史书"。

### 3.3 最坏情况

- **离线续演**：手游砍（PC 保留），用"后台假离线"顶上。
- **祖制继承**：会话内继承保留，跨会话放弃。
- **合规性**：官方"两端同一内容"指**内容/功能一致**，不是存档同步。所以不能让手游少一个**功能入口**。做法：祖制/续演的代码与 UI 两端都在，只在手游标记"本环境不保证保存"。

## 4. 时间戳推演算法（专项）

```
long now  = DateTimeOffset.UtcNow.ToUnixTimeMilliseconds();
long last = prefs.lastExitUtcMs;
if (last == 0) { goto 正常开局; }
long el = now - last;
bool backward = el < -5*60*1000;   bool forward = el > 30L*24*3600*1000;
if (backward) { prefs.clockTamperCount++; el = 0; }
if (forward)  { prefs.clockTamperCount++; }
int days = (int)Math.Min(el / 86_400_000L, MAX_OFFLINE_DAYS);   // MAX = 14
if (prefs.clockTamperCount >= 3) days = Math.Min(days, 1);

IEnumerator RunOffline(int days) {
    var rep = new OfflineReport();
    for (int d = 0; d < days; d++) {
        if (sim.aliveCount < EXTINCT_THRESHOLD) { rep.extinctAt = d; break; }
        yield return StartCoroutine(SimRunner.RunSilentCo(sim, 120, rep)); // 内部每 40 tick yield
        sim.day++;
        ShowProgress(d + 1, days);
    }
    meta.Flush(); prefs.Flush();
    ShowDailyReport(rep);
}
```

**防 ANR 硬数字**：单日 ≤120 tick；每 40 tick yield（单帧 ≤8ms）；总上限 14 天 = 1680 tick ≈ 336ms CPU。**任何情况下不出现单帧 >16ms 的推演。**

**退出时（供通知用）**：
```
OnApplicationPause(true) / OnApplicationQuit:
    SimState predict = sim.DeepClone();               // ★ 深拷贝，不改 sim 本体
    SimRunner.RunSilent(predict, 3 * 120, futureEvts);// ≤72ms
    ScheduleNotifications(futureEvts, baseMs: now);
    prefs.lastExitUtcMs = now;  sim.Save();  meta.Flush();  prefs.Flush();
```
