# 冠军方案与收尾分析

> **立法城市（系统层）× 讣告生成器（输出层）** —— TapTap 聚光灯第三届 · 涌现主题 · 单人 / Unity / AI 美术 / 双端 / 18 天

## 一、冠军方案（独立版）

### 立法城市 · 涌现 —— TapTap 聚光灯第三届「最佳双端游戏奖」单人 18 天开工方案

**你不操作任何村民，只往世界里贴 5 条律法，剩 32 个村民按律法自己决定命运——你写下的第 4 条法，可能把村子变成一片废墟。**

**Unity 技术栈**：

【引擎】Unity 2022.3 LTS。理由：TapPlay 支持最成熟、中文教程最多、AI 生成代码命中率最高；不用 2023/6，避免新 API 与包版本坑。

【渲染管线】URP（2D Renderer 模板）。这是 Unity 新建 2D 工程的默认路径，教程与 AI 覆盖最全；本作只需要极简 2D 光照（恐惧/夜晚的整体色调）。若构建遇管线问题，可整体降级到 Built-in 2D，玩法代码零改动——因为不写任何依赖 URP 的着色器。

【UI 框架】UGUI + TextMeshPro。不用 UI Toolkit：UGUI 中文教程量级高一个数量级，AI 写 UGUI 明显更稳，移动端 Canvas 性能可预期。

【关键架构决策：整个世界用 UGUI 画（Screen Space - Camera）】
地图格、村民、法卡、曲线、结算界面全部是 UI 元素（RectTransform + Image / 自定义 MaskableGraphic）。
收益：1) 输入全部走 EventSystem，双端零差异，不写任何世界坐标射线检测；2) 分辨率与宽高比自适应由 CanvasScaler 免费拿到，双端适配工作量近乎归零；3) 点村民 = 点法卡，同一套代码。
代价与对策：UGUI 元素变化触发 Canvas 重建，所以拆两个 Canvas——静态层（背景/地图格/法卡/面板）与动态层（村民/曲线）。并且模拟按固定 tick（默认 4 tick/秒）推进，只在 tick 后更新一次 UI，不做每帧插值移动，Canvas 重建频率降到 4Hz。

【数据层】纯 C# 类 + Newtonsoft JSON（com.unity.nuget.newtonsoft-json）。关卡定义、法卡模板、标签表全部是 json，放 StreamingAssets。不用 ScriptableObject 做主数据——json 更适合 AI 批量生成、手改、版本对比，也不会产生 .asset 合并冲突。

【输入】旧 Input Manager，不用新 Input System。本作只需要「点」和「单指拖」两种手势，而旧 Input 在真机上会把单指触摸自动映射成鼠标，Input.GetMouseButton(0) 与 Input.mousePosition 两端跑同一份代码。新 Input System 的 action asset / control scheme 是 AI 出错重灾区，收益为零、风险为正。

【第三方包】除 Newtonsoft 外不装任何插件。不装 DOTween（用 30 行协程做插值），不装任何寻路/行为树/AI 包。包越少，IL2CPP 裁剪与 TapPlay 审核越安全。

【明确不用的东西】不做 A* / NavMesh（用 8 方向贪心移动 + 一格避让）；不做物理引擎；不做粒子与后处理；不做 Addressables / AssetBundle（全放 Resources + Sprite Atlas）；不接任何联网 SDK（TapTap 登录 SDK 也不接，因为无联网是硬约束）。

**要做（18 天内）**：

18 天内明确要交付的内容边界（照着做，多出来的都不做）：

1. 固定 tick 核心模拟：32 村民 × 12×12 格地图 × 5 条法，双缓冲求值（读 old 快照、写 new 缓冲）。

3. 自指层：法可以读「另一条法本 tick 是否触发过」、可以改「另一条法的数值参数」、可以交换「两条法的优先级」。
4. 编辑 UI：点选条件、点选效果、滑参数、拖拽排序、开跑按钮；开跑后仍可实时滑参数（30 秒闭环）。

11. 两个构建：Android（IL2CPP / ARM64 / TapPlay）+ Windows（IL2CPP / x64），同一工程同一内容，只切 Build Target。

**明确不做**：

防膨胀清单（以下内容一律不做，做任何一条都是从别处偷时间）：

- 任何联网功能：服务器、实时多人、云存档、在线排行榜、在线 API、在线 LLM、局域网联机。包括 TapTap 登录 SDK。
- 寻路（A* / NavMesh / 流场）、物理引擎、复杂光照、骨骼动画、粒子系统、后处理特效。
- 剧情、台词、对话树、任务文本、配音——一行都不写。（写台词的那一刻它就假了。）
- 自由文本法律 / 自然语言解析。（法律必须是固定的条件–效果选择器，否则无法组合、无法预测、无法调试。）
- 可拖动的逐回合时间轴回放——这是原案「立法城市」的重量级功能，直接砍。只保留结果结算 + 大事记文本流。
- 程序化生成地图或关卡。（会被评审当成假涌现。）
- 自动聚类 / 形状识别 / 任何形式的机器学习 / 遗传算法 / 变异搜索。（这些是「参数瘟疫」「唯一解不存在」的坑，本作不需要，也没时间做。）
- 成就系统、内购、广告、排行榜。
- 12 条预设法律模板库（原案的内容量炸弹）——改成条件表 × 效果表的自由组合，由表本身提供组合空间。
- 多语言（先只做简体中文，文案写在 json 里但只填中文）。
- 竖屏适配（只做横屏）。
- iOS（只交 Android + Windows 两端）。
- 音效系统（1 首循环 BGM + ≤8 个 UI 音效封顶，来不及就全砍，不影响四要素）。
- 超过 5 条法的编组 / 嵌套 / 宏 / 法律继承。
- 一切为「最佳视听奖」做的视觉大场面（该奖项 AI 美术占比 ≥50% 不可参评，已放弃）。

**核心系统与代码量**：

系统清单、预估代码量、谁写。总计约 3700 行有效代码；加上调试与返工，实际落地 5000–6000 行。诚实预期：AI 生成的部分约有 25% 需要返工。

【我亲自写，不给 AI】（合计约 300 行，两个最难、最容易出错的地方）
1. 自指层求值（约 150 行）：法是 struct，改参数/换优先级涉及写回数组与引用语义，AI 极易写成「改了副本没生效」或「跨 tick 发散」。我手写 + 手写 6 个故意找死循环的单元测试。
2. 输入抽象层（约 150 行）：双端命门，见 dualPlatform。手写并两端真机验证。

【AI 写 + 我审 + 我调参】（合计约 3400 行）
3. 数据模型（Villager / Law / World 三个 struct + json schema）：约 300 行。
4. Tick 引擎（双缓冲求值主循环）：约 400 行。AI 写主体，重点审「快照 vs 写缓冲」有没有混用。
5. 条件表 / 效果表求值（9 条件 + 11 效果）：约 500 行。纯 switch，AI 写对率高。
6. 标签系统（8 个标签的位图读写）：约 80 行。

8. 离线快进（时间戳 + 分帧跑 ≤600 tick + 摘要生成）：约 150 行。
9. UGUI 地图 + 村民渲染 + 对象池：约 400 行。对象池是 AI 熟模板。
10. 曲线图（自定义 MaskableGraphic，自绘 3 条折线）：约 120 行。AI 写对率中等，有大量现成教程，写完必须看 GC。
11. 法卡编辑 UI（选条件/效果、滑条、拖排序）：约 600 行。最大的一块，AI 写 UGUI 稳。
12. 选中高亮 + 命中计数：约 100 行。
13. 结局判定 + 大事记 + 结算界面：约 250 行。
14. 关卡与教程关数据 + 引导逻辑：约 200 行。
15. 分享码编解码（5 条法 → base32 短串）：约 100 行。

【明确点名：本作不碰任何自研算法。若某处看起来需要，用廉价替代】
- 需要寻路 → 砍，改 8 方向贪心移动 + 一格避让。
- 需要数值稳定（经济崩坏）→ 砍，全部用 int，所有数值钳位 [0,99]，每 tick 单变量变化量封顶 ±20（世界物理层强制，法律改不动它）。
- 需要曲线平滑 → 砍，直接画原始值；实在难看用 3 点移动平均，不引入任何滤波库。
- 需要「自动判断玩家这一局好不好」→ 砍，只做 4 档硬阈值判定。
- 需要「自动发现玩家没见过的现象」→ 砍，这是「参数瘟疫」的自动聚类路线，本作改为「把现象画出来让人自己看见」。

§0 三者合成（明确的取舍）

取「立法城市」（lens-10 previousKilled）：
 - 世界观与叙事（你是唯一立法者、5 条法、村民自己活、天堂或内战）
 - 「不是他们蠢，是你的法律蠢」这个叙事转换——把简陋重构成卖点
 - 开跑后仍能实时滑参数（=30 秒闭环，lens-13 准则 5）
 - 离线回来看到灾变的钩子
弃「立法城市」：
 - 12 条预设法律模板库（内容量炸弹）→ 换成条件表 × 效果表
 - 可拖动逐回合时间轴回放（重量级功能）→ 砍，只留结算 + 大事记
 - 4 种结局的复杂判定 → 收成 4 档硬阈值
 - 纯数值加减的法律（这是它「一眼假」的病根）→ 换成标签耦合 + 阈值相变 + 自指
 - agent 从 20 提到 32 不是加内容，是加样本，让统计曲线稳定可读

取「立法者沙盒」（lens-13 ideas，rank 2）：
 - 5 张硬上限的律法卡（有限法槽 = 想加就得删 = 张力来源）
 - 「悬停某条法 → 场上正在执行它的个体闪烁」这个白箱化命门（我做成：选中高亮 + 命中人数计数）
 - 「少量规则 × 多个体 = 组合爆炸」这条核心判据
 - 用「目标关」把沙盒逼成谜题，而不是放任自流的玩具
弃「立法者沙盒」：
 - 200 只网格虫子（手机渲染与玩家可读性都不友好）
 - 纯空间视角的 unit（没有经济与叙事的抓手，30 秒看不懂）
 - 自由拼 IF→THEN（太抽象）→ 改成 4 类固定的条件/效果选择器 + 参数滑条，降低理解成本

取「自指律法」（lens-10 ideas）：
 - 自指闭环：规则本身就是被规则处理的数据；存在「重写砖」能改写别的规则砖
 - 移植成「自指律法」：法可以读别的法是否触发过、可以改别的法的参数、可以换别的法的优先级
 - 这是本作组合爆炸的第二根支柱，也是让「第 4 条法把村子变废墟」在数据结构上唯一能成立的办法
弃「自指律法」：
 - 把它做成空间网格里的规则砖游戏（那是另一款游戏）
 - 图灵完备的野心（不需要，只要有限、有界、可调试的自指）

────────────────────────────────
§1 唯一的共享耦合点

lens-13 的铁律：涌现住在耦合点上，不在个体里。本作只有一个耦合点——「标签位图 tags（byte，8 位）」。

关键设计：8 个标签是「开发者没有赋予任何含义的记号」。标签的语义完全由「读它的那条法」定义，而「写它的那条法」可以是另一条。
开发者只写了「某个标签可以被写、可以被读」，从没写「劫匪会导致雪崩」。雪崩是两条法通过这个 byte 耦合出来的动力学。

8 个标签：劫匪、税民、逃兵、信徒、病人、守卫、粮民、罪人。
它们只是名字，含义是空的。玩家可以推出完全出乎设计的用法（例如用「信徒」当「已免疫者」用，用「罪人」当「高危人群」用）。

§2 律法的数据结构（可直接抄）

public struct Villager { // 32 个
 public int hunger; // 0..99
 public int wealth; // 0..99
 public int fear; // 0..99
 public byte pos; // 0..143 格索引
 public byte tags; // 8 位标签位图
 public bool alive;
}

public struct Law { // 5 条
 public int whenId; // 1..9 条件
 public int whenParam; // 0..99 条件参数
 public int refLawA; // 自指：引用第几条法 (0..4)，C8/C9/E9/E10 用
 public int refParam; // 自指：引用该法的哪个参数 (0..1)，C9/E9 用
 public int thenId; // 1..11 效果
 public int thenParam; // 0..99 效果参数
 public int refLawB; // 自指：E10 用
 public byte tag; // C7/E7/E8 用
 public byte priority; // 0..4 执行顺序
 public int lastHit; // 上一 tick 命中人数（给 UI 显示 + 给 C8 读）
 public bool fired; // 上一 tick 是否触发过
}
（注意：Law 用 class，或用数组元素写回，别踩 C# struct 拷贝改不到原值的坑——这是 AI 最常见的错。）

public struct World {
 public Villager[] v; // 长度 32，预分配
 public Law[] laws; // 长度 5，预分配
 public int tick;
 public int aliveCount, totalWealth, sumFear;
}

§3 条件表 / 效果表 / 标签表

条件表 WHEN（每条法选 1 个 + 1 个数值参数）：
C1 饥饿 > N 参数 0..99
C2 财富 < N 参数 0..99
C3 恐惧 > N 参数 0..99
C4 邻近村民数 ≥ N 参数 0..8（半径 1 格，8 邻域）
C5 离最近粮仓距离 > N 参数 0..16
C6 我的财富 − 邻居中位财富 > N 参数 0..99（关系型条件）
C7 我带有标签 [X] X ∈ 8 个标签
C8 律法 [L] 本 tick 已触发 L ∈ 5 条法 → 自指
C9 律法 [L] 的参数 [P] > N L × P + 参数 → 自指

效果表 THEN（每条法选 1 个 + 1 个数值参数）：
E1 获得金币 N 1..50
E2 失去金币 N 1..50
E3 饥饿 ± N 1..50（正负由参数编码）
E4 恐惧 ± N 1..50
E5 移动到最近的 [粮仓 / 金币堆 / 邻居] —
E6 抢邻居 N 金币 1..50
E7 贴上标签 [X] X ∈ 8 个标签 → 写耦合点
E8 撕下标签 [X] X ∈ 8 个标签 → 写耦合点
E9 修改律法 [L] 的参数 [P] ± N 自指
E10 交换律法 [A] 与 [B] 的优先级 自指
E11 死亡 —（硬结局）

参数空间上限：9 条件 × 11 效果 × 100 参数 × 5 优先级 × 5! 排序 ≈ 10^13 量级的法的组合空间；再乘 32 个村民 × 5 个数值，世界状态空间 10^90+。
但要诚实：这个数字是宣传，真正让「你没写过的后果」成立的是 §5 的结构性论证，不是这个数字。

§4 执行模型（可照抄的伪代码，这是命门）

Tick(World w):
 old = w.v // 只读快照（预分配，不 new）
 nw = w.v 的副本 // 只写缓冲（预分配）
 fired[0..4] = false // 预分配

 order = 按 priority 排序的法的下标列表
 for k in 0..4:
 idx = order[k]
 L = w.laws[idx]
 hit = 0
 for i in 0..31:
 if !old[i].alive: continue
 if EvalWhen(L, old, i, fired): // 读 old + fired
 ApplyThen(L, nw, i, w) // 写 nw；自指效果直接改 w.laws，立即生效
 hit++
 w.laws[idx].lastHit = hit
 w.laws[idx].fired = (hit > 0)
 fired[idx] = (hit > 0)

 // 世界物理（法律改不动，硬编码）
 for i in 0..31:
 new[i].hunger += 1; new[i].fear -= 2
 所有数值钳位 [0,99]
 死于 饥饿 ≥ 100

 w.v = nw; w.tick++
 if w.tick > 500: 强制结束

四条铁边界（缺一条就会在手机上出 ANR 或黑白屏）：
1. 每 tick 每条法最多触发一次（不是每个目标一次——是「这条法这一 tick 只算一轮」）。
2. 参数钳位 [0,99]；优先级永远是 5 个槽的排列，交换 = 交换数组位置，永不越界。
3. 全局 tick 上限 500；离线快进上限 600 tick。
4. 双缓冲：条件永远读 old，效果永远写 nw，自指效果写到 w.laws 并在本 tick 后续法中立即生效。C8 引用「优先级更靠后的法」时，读到的是上一 tick 的 fired 值——这是确定性的，不是 bug，要在 UI 上说清楚。

────────────────────────────────
§5 组合爆炸从哪来（四根支柱，这是全作成败的唯一命门）

支柱一：复合函数。
世界下一状态 = F5 ∘ F4 ∘ F3 ∘ F2 ∘ F1 (世界)。
每个 Fi 是不到 20 行的局部小函数，但它们的复合体没有任何人的表示——开发者没写「雪崩」，玩家没写「雪崩」，雪崩是复合体的不动点。
「两条法叠加出开发者没写的后果」在这里的严格含义是：复合函数的表示长度远大于各分部长度之和，且没有任何一行代码描述复合体的行为。

支柱二：标签（耦合点）。
标签是没有内置语义的记号。写标签的法与读标签的法互不知情，通过同一个 byte 耦合。这是「A × B = 你没写过的 C」最直接的数据结构实现。

支柱三：自指。
法的参数与优先级本身是被法处理的数据。系统因此能在运行中修改自己的行为，长出开发者没写的极限环（振荡）与相变。
具体推演：法3 的 when 是 C8「法1 本 tick 触发过」，then 是 E9「改法2 的参数 +1」。于是「法1 触发得越频繁 → 法2 越猛」。玩家写下的是一条关于另一条法的行为的法。三层引用链（法3 读 法1 的触发标志 → 写法2 的参数 → 法4 读 法2 的参数）是完全合法的，且它的后果（恐惧封顶后全村逃亡，或触发法5）玩家心算不出来。

支柱四：阈值相变。
数值连续变化穿过某条法的阈值时，那条法的激活集突变，系统行为整体跳变。玩家滑一个数字，世界换一种命运。这就是「参数瘟疫」的相变边界，被搬到了法律参数上，而且成本近乎为零。

【完整推演：两条中性法如何变成雪崩】
法1：C1 饥饿>50 → E7 贴[劫匪]
法2：C7 有[劫匪] → E6 抢邻居 20
玩家以为：饿了的人变劫匪，然后抢人。
实际耦合（每一条都是上面三条规则的必然结果）：
 t0：少数人饥饿>50 → 变[劫匪]
 t1：劫匪抢走邻居 20 金 → 邻居财富掉
 t2：邻居财富<10 → 买不起粮 → 饥饿↑（这是世界物理，不是法）
 t3：邻居饥饿>50 → 也变[劫匪]
 t4：劫匪数正反馈增长 → 全村互相抢 → 粮仓被搬空 → 废墟
「正反馈增长」没有任何一行代码写。它是 法1 + 法2 + 世界物理（财富→饥饿）三者耦合出的动力学。雪崩的生命周期（慢启动→加速→饱和→崩塌）是 logistic 曲线，是系统的性质而非一段动画。
自检（lens-13 三把尺子）：删掉法1，现象消失 → 说明耦合成立；删掉法2，现象也消失 → 说明不是单条法的效果。任一条单独存在时都不产生雪崩。

【第二次推演：自指的不可预测】
法1：C2 财富<10 → E9 改 法2 的参数 +2
法2：C1 饥饿>40 → E4 恐惧 +5（作用对象=所有触发者）
法3：C9「法2 参数 > 60」→ E3 饥饿 +10（作用对象=所有触发者）
玩家写的是「穷的人让法2 更狠」，看到的是：前期一切平稳，某个 tick 之后全村恐惧飙升、饥饿飙升，然后连锁崩塌。相变点在哪，玩家算不出来，开发者也没写过。

§6 关键参数初始值

村民数 32；地图 12×12 = 144 格；粮仓 2 个；食物点 4 个。

饥饿：每 tick +1，初始 10±10，≥100 死亡。
财富：初始 20±10，钳位 [0,99]。
恐惧：每 tick 自然 −2，钳位 [0,99]。
食物消耗：财富 < 10 时无法进食（这是「财富→饥饿」的那条世界物理，是雪崩的第二根引线，务必保留）。
结局阈值（按 120 tick 时的存活人口比例 + 贫富差）：
 存活 ≥ 60% 且 贫富差 < 40 → 盛世
 存活 ≥ 60% → 平庸
 存活 20%–60% → 衰败
 存活 < 20% → 废墟
离线快进：tick 数 = min(离线秒数 × 4, 600)，分帧执行，每帧时间预算 4ms，附「时间流逝」动画。

**手机性能预算**：

【目标机型下限】骁龙 665 / 4GB RAM 级（TapPlay 上最常见的中低端机）。

【硬性预算】
- 帧率：稳定 30 FPS 为底线，争取 60 FPS。本作不是动作游戏，30 FPS 完全可接受。
- Draw Call：≤ 40。靠 Sprite Atlas 合批 + 两个 Canvas 分离。
- 三角面：< 5k（12×12 地图格 + 32 村民 + UI，全是 quad，远低于上限）。
- 内存峰值：< 250 MB。TapPlay 单实例有内存上限，超了会被杀进程。
- 安装包：< 60 MB，目标 < 40 MB（80 张 AI 图压缩后约 15–25 MB，加 IL2CPP 运行时的 15–20 MB）。
- 纹理：单图 ≤ 1024×1024；Android 压缩 ASTC 6×6，PC 压缩 BC7/DXT5；全部关闭 Generate Mip Maps（2D UI 用不上，省 33% 显存）。
- 启动时间：冷启动到可交互 < 3 秒。单场景，无场景切换，无 AssetBundle 加载。
- 模拟开销：每 tick ≤ 2ms（32 村民 × 5 法 × 约 6 次查询 = 960 次判定）。即使 8 tick/秒也只占用 1.6% 的帧预算。
- UI 重建：模拟只在 tick 后更新一次 UI（默认 4Hz），不做每帧移动插值 → Canvas 重建频率 4Hz 而非 60Hz。这是移动端最大的性能保险。

【GC 与 ANR（TapPlay 稳定性检测的头号杀手）】
- 零每 tick 分配：村民数组、写缓冲、fired 数组全部在 Awake 预分配并复用。禁止在 tick 循环里 new List / new Vector3[] / LINQ。
- 禁止 foreach 遍历 Dictionary（会装箱）；用数组 + 计数下标。
- 字符串拼接走 StringBuilder 或 TextMeshPro 的 SetText(char[], ...)；曲线和命中计数每 0.25 秒才刷新一次文本。
- 所有协程必须有退出条件或超时，禁止 while(true) 无 yield。
- 离线快进必须分帧（每帧 4ms 预算），绝不在启动时同步跑 600 tick。

【TapPlay 稳定性检测（P1 必现崩溃/ANR/黑白屏 = 禁止上线）的对策】
- 单场景 + 单 Canvas 根 + 无远程资源 → 无黑屏风险。
- 不申请任何敏感权限：不联网、不读通讯录、不读外部存储；存档用 Application.persistentDataPath，不需要权限。
- 全程 SafeArea 适配，避免刘海/挖孔遮挡法卡与按钮。
- 不调用 Application.Quit / System.Exit / Process.Kill（TapPlay 环境里这些是禁忌）。
- 存档用原子写：先写 save.json.tmp，成功后 File.Replace 覆盖 → 中途被杀不会留下损坏存档。读档失败必须能回退到默认世界而不是抛异常崩溃。
- 断网无关（本来就不联网），但要测「飞行模式 + 切后台 + 低电量模式 + 低内存」四种环境。
- 真机实测清单（D13 与 D16 各跑一遍）：连续玩 30 分钟不崩、切后台 10 分钟再回来状态正确、离线 3 小时后回来快进正常、反复开关 20 次不泄漏内存。

**双端方案**：

【核心原则】同一 Unity 工程、同一份代码、同一份内容、同一个关卡数据，只切 Build Target。不做两套内容，不做 PC 专属关卡。

【输入抽象方案（双端唯一的差异点，我手写，约 150 行）】
封一层 InputRouter，暴露三种事件，两端共用：
 OnTap(worldPos) // 按下并抬起在同一元素上
 OnDragStart/Drag/End // 单指拖动
 OnFocusEnter/Exit(worldPos) // 悬停（仅 PC 有；触屏上不触发）

具体映射：
- 法卡（选条件/选效果/点选激活）：PC = 单击选中 + 悬停预览高亮；触屏 = 单击选中（选中即高亮，替代悬停）。EventSystem 的 IPointerClickHandler 两端都触发，IPointerEnterHandler 在触屏上等价于点按下——所以「悬停高亮」在触屏上自然退化为「点一下高亮」，不需要分支代码。
- 参数滑条：PC = 拖动滑块 + 左右方向键微调（±1，长按加速）；触屏 = 拖动滑块。用 UGUI Slider，两端天然一致。微调键是 PC 专属的加分项，不做也能玩。
- 拖拽排序法卡：PC = 按住拖 + 上下键；触屏 = 按住拖。用 UGUI 的 IDragHandler，一致。
- 地图点村民查看详情：PC = 悬停显示 + 点击锁定；触屏 = 点一下显示，点空白关闭。
- 相机/地图缩放平移：地图固定 12×12 一屏放下，不需要平移缩放 → 直接砍掉这个需求，省一整套手势代码。
- 键盘快捷键（PC 专属，可选）：空格 = 开跑/暂停，1–5 = 选中第 N 条法，Tab = 循环速度。触屏没有对应，不影响任何玩法。

【分辨率与宽高比】
- 一律横屏（Landscape）。理由：需要同时容纳「地图 + 5 张法卡 + 曲线」，竖屏三者放不下。
- CanvasScaler：Scale With Screen Size，参考分辨率 1920×1080，Match = 0.5。
- 锚点策略：地图锚左下（12×12 方格等比例缩放）、法卡栏锚右侧竖排、曲线锚底部横条、顶部状态栏锚上边。极端比例下（21:9 / 4:3）只是留白变化，元素不重叠。
- 手机 20:9（2400×1080）与 PC 21:9、16:9、16:10、4:3 五档，D14 逐一实机/窗口验证。

【构建配置】
- Android：IL2CPP 脚本后端 + ARM64（TapTap/TapPlay 强制 64 位）；Managed Stripping Level = Low（AI 生成的代码常有反射/序列化路径，High 会裁出错）；Target API Level 按 TapTap 当年要求；关闭 Auto Graphics API，只留 OpenGLES3（兼容性最好）。
- Windows：IL2CPP + x64；分辨率默认窗口化 1600×900，可全屏。
- 两端共用同一个 PlayerSettings 内容：同一 Product Name、同一版本号、同一图标。
- 在 TapTap 后台把两个包关联为「同一款游戏」（官方要求双端为同一内容、数据合并计算），提审时按官方指引填报。

【存档路径】
- 统一用 Application.persistentDataPath + /save.json + /settings.json。
- Android 落在应用内部存储（无需权限），Windows 落在 %USERPROFILE%/AppData/LocalLow/<公司>/<产品>/。
- 两端存档格式必须完全一致（同一份序列化代码）。不要求互通（无联网无法同步），但格式一致意味着玩家可以在 PC 上导出分享码、手抄到手机上——这就是无联网条件下的「跨端分享」。
- 存档版本号字段 + 向后兼容读取，避免更新后老存档崩溃。

【测试与增量工时】
- 每 3 天做一次两端构建冒烟（D1 就先把两端空包打通，避免最后才发现构建问题）。
- 增量工时约 2.5 天：构建配置与首次打通 1 天；输入抽象层 0.5 天；分辨率/宽高比适配 0.5 天；两轮真机 + 真机测试（D13、D14、D16）约 1.5 天。注意 3 天里有部分与主线重叠，净增约 2.5 天，已排进 dayPlan。
- D14 的验收标准：两端各完整通关一次（写完 5 条法 → 开跑 → 出结局 → 离线快进回来），且截图对比内容完全一致。

**AI 美术管线**：

【工具】优先国内工具，中文提示词友好、访问稳定：即梦 / 通义万相 / 可灵（任选其一，全程只用同一个，避免风格漂移）。备用：Stable Diffusion 本地（但配置成本高，不推荐学生用）。游戏内不联网是硬约束，但开发期用 AI 生成美术完全合规。

【风格统一（这是最容易翻车的地方，D11 上午必须卡死）】
- 定一句话风格锚，例如：「扁平矢量插画，低饱和土黄配灰蓝，粗深色描边，等距俯视，无文字，无阴影渐变，透明背景」。
- 再固定一张参考图，后续所有生成都用它做垫图 / img2img，保证同一套色板与线宽。
- 强制流程：先只生成 3 张（1 村民 + 1 建筑 + 1 地面砖），肉眼确认三张是同一个世界，再批量生成。这一步省不得——风格漂移是 AI 美术最常见的死法。
- 提示词里每次都带上「no text, no watermark, plain background, transparent」。
- 生成后统一调色：在同一个工具或 Photoshop/GIMP 里套同一组色阶，把饱和度与明度拉到一致。

【张数与规格（总计 70–80 张，全部 AI 生成 + 抠图）】
- 村民 sprite：64×64，8–12 种（用颜色 + 帽子区分身份，用叠加的小图标区分饥饿/恐惧状态），约 20 张。
- 建筑与人造物：128×128，约 15 张（粮仓、房屋、水井、围墙、集市等）。
- 地面 tile：64×64，约 8 张，可平铺（草地、土路、耕地、荒地）。
- 法卡底框 / 按钮 / 面板：九宫格（sliced sprite），约 10 张。
- 图标：64×64，约 20 张（9 个条件 + 11 个效果各一个图标，外加 8 个标签图标可裁剪复用）。图标用纯色 + 简单几何，AI 生成后必须手工抠一遍（AI 图标几乎都带背景和杂边，抠比生成还慢，要算进工时）。
- 标题图 / 商店图：1920×1080，约 4 张。
- 音效不在此列：1 首循环 BGM（可找免费素材）+ ≤8 个 UI 音效（点击、开跑、阈值触发、结局）。

【导入 Unity 注意事项】
- Sprite Mode = Single；Pixels Per Unit = 64（与 64×64 的村民规格对齐）；Filter Mode = Bilinear；Compression = ASTC 6×6（Android）/ BC7（PC）；关闭 Generate Mip Maps。
- 尺寸统一到 2 的幂（64 / 128 / 256），否则图集打包会出现空隙浪费。
- 全部打进 Sprite Atlas（Unity 官方 Sprite Atlas 包），减少 Draw Call；动态层的村民图集与静态层的 UI 图集分开打。
- 去背景要透明：AI 出的图常带白底、格子底、伪透明棋盘底，逐张检查并抠干净。这一步最容易漏，漏了在游戏里就是一块白方块。
- 文件名用英文小写 + 下划线，统一命名规范（villager_01、tile_grass、icon_c1 等），方便 json 引用与 AI 批量替换。

【工时预算】定风格锚 + 3 张测试图 0.5 天（D11 上午）；批量生成 70–80 张 1 天；抠图 + 统一调色 0.5 天；导入 + 图集 + 替换占位图 0.5 天。合计 2.5 天，已排进 D11–D12。

【占位图优先】D6 起的 UI 全部先用纯色矩形 + 文字占位。美术必须晚于玩法（lens-13 准则 8：美术别超过 20%），否则玩法没时间调。】

**四要素落地**：

【目标】
每关给一个「城邦愿景」，即一个可判定的目标函数，但完全不提示怎么做。
教程关：无目标，只有引导（把第 3 条法的阈值从 60 滑到 30，看世界变形）。
挑战关示例：
 关卡 2「温饱」：让 60% 的人活过 120 tick。
 关卡 3「均富」：活过 120 tick 且贫富差 < 40。
 关卡 4「铁律」：只允许改 2 条法，让存活率 ≥ 80%。
 关卡 5「自指」：必须使用至少 1 条引用另一条法的法，活过 120 tick。
目标必须是「一句愿景 + 一个数字」，绝不写实现步骤。

【规则】
- 世界的规则：32 村民，每人有饥饿 / 财富 / 恐惧三个数值和 8 位标签；每 tick 饥饿 +1、恐惧 −2；财富 < 10 无法进食；饥饿 ≥ 100 死亡。这是不可改的世界物理。
- 玩家的规则：只有 5 个法槽。每条法 = 一个条件 + 一个效果 + 一个参数 + 一个优先级。想加第 6 条，必须先删一条。
- 法律的规则：法可以通过标签互相耦合；法可以引用另一条法是否触发过、改另一条法的参数、换另一条法的优先级。
- 边界规则：每条法每 tick 最多触发一次；参数钳位 [0,99]；单局 500 tick 上限。

【挑战】
1. 法槽有限（5 条），想加就得删 —— 每一次「修 bug」都可能长出新 bug，这是核心张力。
2. 阈值相变：滑一个数字就可能让系统整体行为跳变，玩家无法靠心算预测，必须试。
3. 法的互相干扰：两条各自中性的法叠加后产生雪崩（见 emergenceCore 的推演），玩家会经历「我明明没写这个」的瞬间。
4. 自指：法能改法，产生极限环与不可预测的相变。
5. 实时滑参数（开跑后仍可改法）意味着玩家要一边观察一边调，类似驾驶而不是做题。

【反馈（每条都必须有，缺一条就变成黑箱）】
- 3 条实时曲线：人口、平均财富、平均恐惧。曲线的形状本身就是反馈。
- 地图热力：村民颜色 = 财富（红→绿）；头顶小图标 = 饥饿 / 恐惧；带标签的人身上有颜色描边。
- 选中某条法：场上所有正在执行它的村民闪烁一下（这是「立法者沙盒」的白箱化命门，不可省）。
- 每条法旁边显示「本 tick 命中人数」，数字为零的法一眼可见是死法。
- 大事记：tick 级的异动文本流（「t47：村里出现了第一个劫匪」「t83：粮仓被搬空」），把涌现讲成一个能读的故事。
- 结局结算：4 档判定 + 一句总结（「不是他们蠢，是你的法蠢」）。
- 离线快进回来弹「你不在时发生了什么」摘要。
- 音效：阈值触发时的一声提示音，让玩家用耳朵也能感知相变。【这是全作四要素中最重要的一项：涌现必须看得见。】

**最容易翻车**：

【最容易翻车的三处】

第一处：涌现做假 —— 只做数值加减的法律。
症状：法1 每人 +5 金、法2 抢钱、法3 收税，玩家第 1 天就看穿「这 NPC 蠢死了」，涌现感当场崩掉。这正是原案「立法城市」被砍的直接原因。
对策（三件必须齐上，且必须在 D3–D5 就做实，不能留到最后）：
 1) 标签耦合（写标签的法与读标签的法互不知情，通过一个 byte 焊在一起）；
 2) 阈值相变（数值穿过阈值时激活集突变，玩家滑一个数字世界换一种命运）；
 3) 自指层（法能读别的法是否触发、能改别的法的参数、能换别的法的优先级）。
自检（lens-13 三把尺子）：删掉法 A，现象还在不在？在 = 耦合成立；不在 = 那只是法 A 的效果，是假涌现，要重做。

第二处：可读性地狱 —— 5 条法的交互变成黑箱，30 秒内看不懂就死。
症状：玩家看到小人乱跑，分不清哪条法在起作用，5 分钟后关掉。这是这类游戏的头号死因（「立法者沙盒」「学舌之村」都死在这条）。
对策：三层白箱化——(a) 选中某条法时，场上所有正在执行它的村民闪烁 + 显示命中人数；(b) 3 条实时曲线让形状本身说话；(c) 大事记把涌现变成一个能读的故事流。外加一个硬编码的教程关，保证 30 秒内必出一次啊哈。这条不做，前面全白做。
次要风险：AI 美术风格漂移同样是「看不懂」的一种。对策是 D11 上午先用 3 张测试图卡死风格锚，不统一就重来。

第三处：自指系统与移动端稳定性
症状：法改法极易跨 tick 发散或死循环；在手机上表现为卡顿、ANR、甚至黑白屏，而 TapPlay 的稳定性检测是「P1 必现即禁止上线」。
对策（四条铁边界，一条都不能少）：每 tick 每条法最多触发一次；参数永远钳位 [0,99]；全局 tick 上限 500、离线快进上限 600；双缓冲（条件读 old、效果写 new）。再加零每 tick 内存分配（预分配数组 + 对象池 + 禁止 LINQ）与分帧离线快进。D5 专门写 6 个「故意找死循环」的单元测试。

## 二、冠军方案（合并版：立法城市 × 讣告生成器）

### 《立法村》（TapTap 上架名，宣传语「他们死于你写的法律」；备选《五条法律》《讣告村》）

**你一个村民都不操作，只往村里贴 5 条法律；20 个村民按你的法律自己活、自己死；系统用他这一生真实发生过的事，自动给他写一篇讣告——玩法是「看它长成什么样」，留存是「读完他们每个人的一生」。立法城市给深度，讣告生成器给传播，两层焊在一条事件流上。**

**Unity 技术栈**：

【Unity 2022.3 LTS + 2D 模板 + Built-in 渲染管线】不选 URP：本作无 2D 光照需求，URP 只会多出 shader/渲染器配置这个会翻车的变量；Built-in 包最小、AI 训练数据最多、出错率最低、TapTap 打包教程最多。Unity 6 LTS (6000.0.x) 也可，但没必要、不冒险。
【输入】旧 Input Manager 统一处理：Input.GetMouseButton(0) 在 Editor、PC 鼠标、手机触摸上都能用。本作只有「点选 / 拖动 / 捏合」三种语义，不需要 Input System 的复杂绑定；新旧输入系统混用是 AI 最常犯的错，直接锁死旧系统，再用一个 InputAdapter 把两端事件归一。
【UI】uGUI (Canvas) + TextMeshPro，不用 UI Toolkit（移动端 runtime 不成熟、AI 错误率高）。讣告正文必须用 TMP 富文本（逐字浮现 + 清晰缩放）。
【网格】单个 Tilemap (com.unity.2d.tilemap) + 一张 bool[,] 占用位图。禁止「每格一个 GameObject」。村民走开阔地，不做 A*（直线 steering + 到达判定即可）——这是相对讣告战棋方案省下的最大一块工时，也是本作能压进 18 天的关键。
【动画】DOTween 免费版：文字逐字浮现、移动缓动、死亡慢镜、飘字。
【存档】JsonUtility + Application.persistentDataPath，不引任何第三方 Save 插件。
【相机】手写约 60 行 CameraController（单指拖动平移、双指捏合缩放、PC 滚轮缩放 + 右键拖屏）。不用 Cinemachine。
【明确不引】DOTS/Jobs/Burst、Addressables、Netcode 及任何网络包（硬约束一）、Easy Save、Odin、任何物理依赖。
【质量设置 D1 锁死】vSyncCount=0；Application.targetFrameRate=60；Physics2D Simulation Mode=Script（等于关物理）；Managed Stripping Level=High；Graphics API 只留一个（OpenGLES3 或 Vulkan，别两个都留）；Shader Stripping 全开。
【中文字体 D1 必做】TMP Font Asset Creator 从思源宋体（讣告正文）/思源黑体（UI）生成；字符集用 Custom Characters 手动粘入本项目全部文案用字 + 常用 3500 字；备一个 fallback Font Asset 防漏字。不做这步，D6 全屏讣告会全是方块。

**要做（18 天内）**：

结论先行：18 天做得完，但只有一条路——两层都保留，靠「模板化 + 内容与代码分离」把量压到甜区；一旦法律 DSL 滑向自由文本、或讣告改动联网生成，立刻做不完。系统总量约 2500-2700 行，比原讣告战棋方案更轻（删掉了 A*、回合战斗、敌人 AI、程序化关卡）。村庄模拟比战斗模拟便宜得多，这是合并反而更好做的证据。

18 天内明确交付：
1. 内容量：1 张固定村庄地图（24x16 格，可平移缩放）+ 1 个 90 秒教学关（内建必死村民）+ 6 个正式关（纯 JSON preset）+ 1 个无限沙盒（传播素材产地）。共 9 个入口，实为同一套内核换 preset。
2. 村民 20（教学关 12），代码硬上限 40；地标：粮仓/房屋/井/围墙/老槐树/集市/墓地。
3. 12 条法律模板（条件→效果两段式），每局玩家选 5 条并调参。
4. 确定性 tick 模拟：1 tick = 1 秒，可 1x/2x/4x，可暂停/单步；同一（法条+seed）必产出同一村庄故事。
5. 事件系统：15 种 LifeEvent struct + 每个村民一生事件表（容量 12）+ 关系表（±100，有向）+ 三共享变量（金币/饥饿/恐惧）。
6. 讣告生成器：6 段骨架 x 模板池 30 + 语料 150 + 数值→措辞映射表 + 一生统计标签 + 废话过滤 + 人工兜底模板。
7. 全屏讣告页 + 事件时间线对照 + 本地讣告图鉴（按死法稀有度排列）。
8. 仪表盘：人口/财富/恐惧三条曲线 + 可滚动事件日志列表（不做逐帧时间轴拖动）。
9. 分享码（5 法条 + seed 文本编码，走剪贴板，无联网）。
10. 元系统：存档（图鉴+进度）、主菜单、4 种结局页、墓志铭输入框。
11. 双端构建（Android + Windows）、TapPlay 稳定性达标、5 篇日志、10.18 提审。

**明确不做**：

防膨胀清单，以下一律不做：
- 任何联网：服务器、实时多人、排行榜、云存档、在线 API、在线 LLM、局域网。讣告 100% 本地生成。
- 自由文本 / 自然语言法律输入。法律必须是模板（条件→效果两段式），否则 AI 写不动、逻辑不可枚举、玩家写不出。
- 寻路 A*、行为树、敌人 FSM、多 AI 状态。村庄是开阔地，直线 steering 足够。
- 程序化地图生成、地图编辑器、多套地图美术。
- 村民骨骼/逐帧动画：无行走帧、无劳作帧，用位移 + 缩放 + 头顶图标 + DOTween 代替。
- 3D、URP 2D 光照、粒子系统、后处理栈。
- 可拖动逐帧时间轴回看（原立法城市方案里最贵的一项）。只做事件日志列表 + 讣告，够讲因果。
- 村民真 AI / 真寻路决策：他们就是「机械但诚实的 if-else」，叙事重心压在「不是他们蠢，是你的法蠢」。
- 多语言、成就、内购、签到等运营壳；真人美术/配乐（明确放弃最佳视听奖）。

=== 一、两层的接口（合并成败的关键）===
唯一接口 = 每个村民的 List<LifeEvent>（一生事件表）+ 一份 VillageSnapshot（关系表 + 村庄统计）。生产者是 SimCore，消费者是 ObituaryForge，两者之间只有这一个数据契约，ObituaryForge 不读 SimCore 任何运行时状态——因此讣告可在编辑器里离线批量重放、可单测、可从存档重新生成。

事件结构（落盘 = 内存，约 20 字节）：
public enum EvType : byte { BORN, ATE, STARVED, EARNED, ROBBED, TAXED, GIFTED, BUILT, FEARED, ACCUSED, FLED, DIED_STARVE, DIED_KILLED, DIED_SICK, DIED_OLD }
public enum EvCause : byte { NATURAL, LAW, OTHER, DISASTER }
[Serializable] public struct LifeEvent {
 public int tick; // 第几回合，0=出生
 public byte type; // EvType
 public short actorId; // 谁
 public short targetId; // 对谁，-1=无
 public int value; // 数值：金币/伤害/情绪
 public byte cause; // EvCause
 public byte lawIndex; // 0-4 触发它的法律槽位，255=非法（这是合并版的命门字段）
 public short ctx0, ctx1;// 事件发生时的上下文数值（挨饿时的饥饿值、被抢时的金币等）
 public byte tile; // 地标 id（粮仓/井/围墙外/老槐树…）
}
关键三点：
(a) cause + lawIndex = 「讣告复述你的法律」钩子。任何致死事件都标注是哪条法造成的，这是全作最强 aha，等价于讣告战棋里 ORDERED_INTO_DANGER + cause=ORDER 的地位，但更强，因为它指向一条你亲手写的、全局生效的规则。
(b) 讣告只吃事件、不吃「村民当前数值」。数值会变，事件不会；事件在产生时已把当时的上下文冻结进 ctx0/ctx1 和 value。讣告讲的是「他这一生发生过什么」，不是「他死时有多少钱」。
(c) 死亡是特殊事件：村民死亡时生成 DIED_* 事件（含 killerId / cause / lawIndex），冻结其事件表与 deathTick，推入 Cemetery。单位 id 永久回收（D10 专项），绝不复用——否则新村民会继承旧村民的记忆，讣告张冠李戴，这是必现坑。
落盘：VillageSave { VillagerSave[] villagers; }，VillagerSave { LifeEvent[] log; ... }。20 人 x 12 条 = 240 条，JsonUtility 秒存。内存里每 20 人 x 12 条 x 20B = 4.8KB，无压力。

=== 二、讣告「读起来像真的」五件套（不碰 LLM）===
1) 句式骨架（6 段固定槽位）：{生卒行}{死因句}{一生句}{记忆句}{关系句}{立法句}。每段背后是一个模板池（各 20-30 条变体），避免「一眼看穿是填空」。
2) 事件筛选（哪条记忆值得进讣告）：score = 1.0*(是否死因相关) + 0.5*(|emotion|/100) + 0.6*(cause==LAW) + 0.2*(时间新近度) + 0.3*(与死因共享 actor/target/tile)。取 top 3（不含死因本身）按 tick 正序拼接。过滤：与死因无任何 actor/target/tile 交集且 |emotion|<20 → 丢弃（这就是防废话的闸）。立法相关权重故意给到 0.6，因为「是你的法」是传播钩子。
3) 数值→措辞映射（表驱动，读起来像真的第一大来源，见 emergenceCore）。
4) 一生统计标签（比单条事件更强，因为它是跨事件总结）：「被抢次数>=4 → 村里人人都抢过他」「赠予次数>=5 → 最肯帮人的那个」「生育数>=2 → 留了一屋子孩子」「挨饿回合数 top1 → 这辈子没吃过几顿饱饭」。讣告像不像人话，一半靠它。
5) 一致性与兜底：同一事件不出现两次；关系句里的名字必须真实存在过；死因句的凶手必须等于 DIED_* 事件的 targetId；素材不足（幼儿夭折）走人工兜底句「他还太年轻，没来得及做什么。」
最后保险三件套：具体数字（第 37 回合 → 入村第 37 天）+ 真实人名 + 因果链。讣告页顶部放一张事件时间线小图（几个点），点开可看原始事件——诚实展示来源反而更可信，也是 lens-13 要求的「给涌现装仪表盘」。

**涌现的种子（命门）**：

【12 条法律模板（条件→效果，玩家选 5 条并调参）】
条件池：无 / 饥饿>X / 金币<X / 金币>X / 恐惧>X / 近邻 X 格内有村民 / 本村人口<X / 昨天有人死（丧钟）
效果池：得 X 金币 / 交税 X / 抢最近邻居 X / 吃饭(饥饿-X，耗粮仓) / 去耕作(X 回合后粮仓+Y) / 向邻居传播恐惧(邻+恐惧) / 赠予最近邻居 X / 逃离村庄 / 攻击最近邻居 / 生育(人口+1，耗粮仓)
十二条预设卡：
1 福利[无→每人+X金币] 2 税收[金币>X→交税Y] 3 饥则抢[饥饿>X→抢邻居] 4 均贫[金币>X→超出部分给最穷者] 5 互助[饥饿>X且有邻→邻赠食物] 6 耕作[无→去耕作] 7 恐惧蔓延[有人死→向邻传播恐惧] 8 逃难[恐惧>X→逃离] 9 私刑[恐惧>X且有邻→攻击邻] 10 繁育[金币>X→生育] 11 济贫[无→给最穷者X] 12 囤积[饥饿<X→多余食物入仓]
执行：每 tick，全体村民按法律优先级自上而下检查 5 条，首个命中生效（顺序即玩家排布的先后，顺序本身是玩法）。

【组合爆炸从哪来】C(12,5)=792 种选法 x 5!=120 种执行顺序 ≈ 9.5 万种法集，再乘每条 1-2 个参数区间 → 百万级。再叠 20 个村民的两两关系图（20x19 有向边）与三共享变量的耦合。涌现住在耦合点上：金钱是「福利/税收/抢劫/赠予」的共享变量，恐惧是「恐惧蔓延/逃难/私刑」的共享变量，饥饿是「饥则抢/吃饭/耕作/囤积」的共享变量。删掉任何一条法，现象随之变形——这就是可证伪性。
典型自发政权：福利(1)+饥则抢(3)→通胀后全民互抢（立法城市原 aha）；税收(2)+济贫(11)→均富乌托邦；恐惧蔓延(7)+私刑(9)→猎巫内乱；耕作(6)+繁育(10)→人口爆炸→粮荒→灭绝；逃难(8)→人口流失→村庄消亡。

【关键参数初始值（照抄）】村民 20（教学 12）；粮仓初始 100；金币初始每人 10-30；饥饿每 tick +8，进食 -60；饥饿>60 触发「饥」类条件；恐惧每 tick 自然 -5（回落，防锁死成全村同态）；恐惧>60 触发「恐」类条件；关系 ±100 初始 0，每 tick x0.98 回归；救人阈值 +60，私刑阈值 -60；tick=1s；每关目标回合 60。

【数值→措辞映射表（节选，D7 扩充）】
饥饿 ctx0：70-84「常常饿着肚子」/85-94「饿得只剩皮包骨」/95-99「整天在等下一口饭」/100「饿死」
金币 ctx0：<5「一贫如洗」/5-30「勉强糊口」/30-100「手头还算宽裕」/100-300「攒下了一笔钱」/>300「是村里最有钱的人之一」
恐惧 ctx0：50-69「开始夜里睡不着」/70-89「整日闭门不出」/>=90「已经不太敢出门了」
被抢次数(一生)：1「被抢过一次」/2-3「三番两次被抢」/>=4「村里人人都抢过他」
立法句：死因事件 cause==LAW → 「——这是你的第 {n} 条法律。」

【讣告排序权重（必须手调）】见 coreSystems 第 2 点五件套；w1=1.0 死因 / w2=0.5 情绪 / w3=0.6 出自法律 / w4=0.2 新近度 / w5=0.3 与死因同源。

【样例（全部字段来自真实事件，无一字策划写死）】
「阿禾，农夫，入村第 12 天，死于入村第 47 天。他死在围墙外，是赵四动的手。他这辈子最怕的就是饿肚子。入村第 31 天，他抢了赵四家仅有的一袋米——那时候全村都在挨饿。而前一天，赵四刚把最后一碗粥分给了他。——这是你的第 2 条法律。」
拆解：死因句=DIE_KILLED(targetId=赵四,tile=围墙外)；一生句=统计标签(挨饿回合 top1)；记忆句=ROBBED(ctx0=饥饿>60,tick31)；关系句=GIFTED(赵四→阿禾,前一天)；立法句=DIED_KILLED.lawIndex=1。

**手机性能预算**：

【目标】60 FPS（模拟推进/UI 动画期间），最低不破 30。离散 tick + 20-30 个精灵 = 性能压力天生比实时游戏低，但 GC 与 drawcall 仍必须归零/压低。
【格与屏】1 格 = 1 世界单位；地表贴图 128x128，PPU=100。相机默认短边横跨 12 格；1080p 上 1 格 ≈ 90 物理像素。点击吸附到格中心，有效点选范围一格，>=90px 足够舒服。双指捏合可放大到短边 8 格供细看。按钮一律 >=48dp ≈ 126 物理像素。
【实体硬上限（写进代码断言）】村民 <=40（关卡实际 20-30）；地标/建筑 <=60；飘字池 20；同屏总 Sprite <=120。
【tick 频率】无每帧模拟逻辑：模拟走固定计时器（默认 1s 一 tick，倍速即改计时器）；渲染只做 DOTween 补间。村民决策 = 遍历 5 条法律模板（固定 12 条内的查表），一次全模拟 30 村民 x 5 法 < 0.2ms。绝不在 Update 里遍历法律或重算。
【内存/包体预算】运行时峰值 <150MB（TapPlay 试玩包常卡 200-300MB，留余量）；纹理 <=40MB（全部打进 1-2 张 1024/2048 Sprite Atlas，ASTC 6x6，关 Mip Maps）；音频 <=8MB（单声道 OGG）；APK <60MB（保守目标 50MB）；drawcall <40（Tilemap 1-2 + Atlas 1-2 + Canvas 3-5）。
【GC 杀手】战斗中禁 LINQ（OrderBy/Where 会分配）、禁 new List、禁字符串拼接——讣告生成全程 StringBuilder，且**分帧生成**（逐段 yield）避免一次性长文本触发 GC spike。对象池：飘字/死亡特效/讣告卡复用一个，不 Instantiate/Destroy 循环。
【TapPlay 稳定性检测（保守工程目标，以官方文档为准）】崩溃率 <1%、无 ANR、首帧启动 <3s；启动不一次性加载全部资源、场景切换前 yield；targetFrameRate=60、vSyncCount=0；真机必覆盖至少 1 台中端（骁龙 6/7 系）+ 1 台低端，别只在高配机测；上线前跑 TapTap 自检工具。四道红线（P1 崩溃/ANR/黑白屏）任何一条不过 = 直接出局，优先级高于一切玩法打磨。

**双端方案**：

官方要求双端同一内容、数据合并计算，正好与本作天然契合：不存在平台独占内容，同一份关卡/语料/美术/代码，只切构建目标。
【输入抽象】一个 InputAdapter 把两端归一为三个语义事件：Tap(pos) / Drag(delta) / Zoom(delta)，外加 Detail(长按或右键=查看事件详情)。游戏逻辑只订阅语义事件，永不直接读 Input。手机分支用 Input.touches（单指=Tap 或 Drag，双指=Zoom）；PC 分支用 Input.GetMouseButton(0)（点击=Tap，拖动=Drag，滚轮=Zoom，右键=Detail）。旧 Input Manager 一套搞定，逻辑零分叉。
【分辨率与宽高比】统一横屏（手机横屏 + PC 横屏，同一布局，避免维护两套）。Canvas Scaler = Scale With Screen Size，ref 1920x1080，match 0.5；SafeArea 脚本处理刘海/挖孔。相机用固定 orthoSize（短边跨 12 格），所有分辨率下格子像素数自动适配。
【构建配置】同一工程两个 Build Profile：Android（IL2CPP，只留 ARM64 减包体，portrait 关掉锁横屏）+ Windows x64。Player Settings 两套（默认分辨率、图形质量档、图标、包名、签名）。内容零差异，只切平台。
【存档路径】Application.persistentDataPath，双端各自独立（无云同步，硬约束一）。分享码 = 文本（法条 id + 参数 + seed，Base64 短串），走 GUIUtility.systemCopyBuffer 复制，玩家手动贴到论坛——不需要任何联网。
【测试与增量工时】D14 双端各跑一遍全流程（手机中端 + 低端真机 + PC）；TapPlay 自检工具过一遍。增量工时 = 输入抽象 0.5 天（并入 D2）+ 双端适配 1 天（D13）+ 双端压测 0.5 天（D14）+ 两次打包 0.5 天（D18），约 +2 天，已含在 18 天里。相对讣告战棋方案，双端成本不增（同样只有点选/拖动）。

**四要素落地**：

【目标 Goal】
硬目标（每关一个，阈值判定）：活过 60 回合 / 让全村人人吃饱 / 最富与最穷差距 <30 / 人口达到 30 / 恐惧峰值 <60 / 撑过灾年。沙盒模式无硬目标。
软目标（真正驱动回访的）：填满讣告图鉴、收集稀有死法。一句话告诉玩家：「你想让他们活着，因为死了就没故事了。」
【规则 Rules】
- 你只能立法：5 条「条件→效果」模板，可调参、可排序、过程中随时改。
- 村民按 tig 严格机械执行你的法（他们不聪明，法才重要）。
- 三共享变量（金币/饥饿/恐惧）+ 有向关系表耦合全体村民。
- 死亡永久，不可复活；tick 确定性，同 (法条+seed) 复现同一故事。
- 无随机 miss、无随机事件表：所有现象必须可归因到某条法或某个行为。
【挑战 Challenge】
- 有限回合内达成目标；法律互相冲突 → 你不自觉写出灾难（「你写的 bug 变成了剧情」）。
- 资源有限（食物/金币），饥饿与恐惧会传染，一个失误可在全村长成雪崩。
- 隐忧（必防）：如果只看着它跑太无聊，玩家不会为讣告留下——所以 D8/D9/D15 共约 2.5 天专做「看得见的反馈」与教学钩子。
【反馈 Feedback】
- 讣告文本（核心奖励）。
- 仪表盘三条曲线（人口/财富/恐惧）实时变形 + 可滚动事件日志。
- 村民头顶状态图标（饿/怕/富）；死亡时全屏讣告页弹出 + 死亡慢镜。
- 结局页（乌托邦/平庸/内乱/灭绝）+ 墓志铭（玩家手写一句，作为「事实」传给下一局，亲手喂料给涌现引擎）。
- 讣告图鉴（本地累积，按死法稀有度排列）——「第二天还想再开一次」的硬逻辑。
【前 3 分钟钩子（生死线）】唯一死穴：如果没人死，玩家看到的只是一个平淡的推演动画，第 2 分钟就退。对策：教学关内建一个「老村长」，开局 60-90 秒内因你的第一条法必然触发一次死亡，立刻弹出第一篇讣告并点名「这是你的第 1 条法律」。教学即钩子——新玩家 90 秒内必须读到第一封讣告。

**最容易翻车**：

翻车点 1（最大，也是合并特有的）：村民看起来「蠢」，涌现感当场崩掉。这是立法城市被砍的原始死因——20 个 agent 就是「条件→效果」的 if-else，玩家一眼看穿。合并的解毒剂恰恰是讣告层：它把一行 if-else 读回成一段人生。守则：(a) 叙事重心永远压在「不是他们蠢，是你的法蠢」；(b) 必须给每个村民一个可读的名字 + 一条统计标签，让人格化成立；(c) 关系值/恐惧必须可视化（箭头/图标），让「他自己决定的」看得见。若这条不成立，整个合并的价值就没了。
翻车点 2：讣告读起来像废话，玩家第二天就免疫。模板太少 → 一眼看穿是填空；记忆槽与死因之间会生成「语法通顺但没意义」的句子。守则：死因权重最高(w1=1.0)；加废话过滤（与死因无交集且 |emotion|<20 直接丢弃）；数值→措辞映射 + 一生统计标签（这两条是「像人话」的最大来源）；预置人工兜底模板；D11 找 3 个外人读一遍。隐藏子坑（必现）：村民死后 ID 复用会让事件表串到新村民身上，讣告张冠李戴——AI 写的代码 100% 不做 ID 回收，D10 专门修。
翻车点 3：GC 与性能坑，直接挂掉 TapPlay 稳定性检测。AI 默认会写：每次模拟 new List + OrderBy（每帧分配 → GC spike）、每格一个 GameObject（上万对象 → 包体与帧率双杀）、讣告用字符串 + 拼接一次生成一大段（GC spike 卡帧）。守则：单个 Tilemap、事件用 struct、法律求值纯遍历不用 LINQ、讣告 StringBuilder + 分帧生成、对象池、关掉 Physics2D。这些约束要在 D3-D6 写代码前就明确告诉 AI，别等 D14 压测才发现——TapPlay 四道红线（崩溃/ANR/黑白屏）任何一条不过，前面全白做。
一句话总结：保住「讣告复述你的法律」这条钩子、保住「不是他蠢是你的法蠢」这个叙事重心、保住真机性能达标，这个项目就能上；任何一条松动，18 天都不够填。

**只剩 10 天的降级**：

只剩 10 天的砍法——保住「讣告复述你的法律」这条钩子，其余全让路：
【砍哪一层：保输出层（讣告），砍系统层的量，绝不砍系统层的质】

## 三、反方质证

**预计崩点**：10.10（排期 D10）为计划所写范围的确定死亡日；延期实际从 10.4（D4）起跳，10.8（D8）时已滑 3 天且再无缓冲。理由：D4-D8 的法律编辑器 + DSL + 讣告 v1 三块各自超期，到 D10 撞上「三共享变量耦合暴露退化 + ID 回收 bug（计划自己标了 BUG 高发日）」，此后只剩 8 天要装下关系阈值调参、讣告质量、元系统、双端适配、双端压测、内容补量、全流程自测、商店素材、提审共约 11-12 天工作量 —— 数学上不可逆。D19-21 那三天缓冲是留给「审核反馈」的，不是留给开发滑期的，计划里根本没有真正的 dev buffer。

- `fatal` 排期第一句谎在 D4：「法律 DSL 引擎（280 行）+ 12 模板落库 + 一条龙法律编辑 UI（选 5 条 + 调参 + 拖排序）」压进一天。光那一屏编辑器（条件/效果下拉 + 参数滑杆 + 拖拽改优先级 + 5 槽位约束）就是整个项目最大的一块 UI，学生 + AI 至少 2-3 天。D4 当天交付不了，第二天起全部工序顺延 —— 排期里没有任何一天预留了这次顺延。
- `fatal` 真正的谎言是 D5-D11 整段假设「涌现会自己长出来」。这份计划自己的来源报告（涌现重筛报告）第 131 行白纸黑字写着：数值模拟是 C（灵魂），「AI 最帮不上的」，参数调优靠手感。而排期给这件事只留了 D10（关系阈值，一天，还标着 BUG 高发）+ D11（讣告质量，一天）。把整个游戏的核心风险压成两天，还放在第 10、11 天 —— 这是把「不可排期的东西」当成排期项。
- `fatal` 「两条法律叠加出开发者没写的后果」会退化成「每条法独立加减数值」，而且是从设计层面就注定：DSL 是「自上而下首个命中生效」。含义是每个村民每 tick 只触发一条法 —— 法律之间是【竞争/遮蔽】关系，不是组合。加第二条相关法只能盖住第一条，不会和它协同。C(12,5)×5!=9.5 万是组合学幻觉；真实可达行为空间小得多。唯一的真耦合只有 3 个标量（金币/饥饿/恐惧）加「恐惧传播」这 1 个两跳效果，本质是「一个三变量 ODE + 优先级开关」。暴露时点：D5 第一次接三共享变量跑 20 人就会看到村民只在饥饿上下振荡、一条法碾压全场；D10 想让它真的链式连锁时无法否认。
- `fatal` 「确定性 tick：同一（法条+seed）必产出同一故事」是假的，跨端必崩。UnityEngine.Random 非自定义 PRNG 不保证跨平台一致；float 求和的 FMA 收缩/求和顺序在 ARM64 与 x64 的 IL2CPP 后端可能不同；Dictionary/HashSet 迭代顺序不稳定。任一命中，手机与 PC 同 seed 会出两个不同村庄 —— 分享码（「贴我的 seed 复现我的村子」）当场成谎言，且直接违背官方「双端同一内容」。修法必须用整数/定点（×1000）跑模拟、禁 float、自带确定性 PRNG —— 计划把它当成一句「确定性 tick」带过，没意识到这是跨架构雷。
- `fatal` 中文字体是「必须做对否则全盘皆输」的单点，而 D1 只验证了「你好」两个字测不出来。讣告是运行时动态拼接的长中文段落，墓志铭输入框还允许玩家手打任意汉字 —— 计划用「思源宋体 Custom Characters 手动字符集」防缺字，等于给动态文本上静态白名单：任何未收录字（尤其玩家输入、生僻姓氏）当场渲染成 □。必须用动态字体 atlas，可一放宽 Game 字体纹理就爆、TMP 逐字浮现每字重建 mesh 触发 GC spike —— 绕回性能坑。
- `severe` 手机端会拖后腿，D13-D14 的「1.5 天」实际是 3-4 天。具体：首次 IL2CPP + 仅 ARM64，学生的包体大概率 >60MB（strip 没配）；TapPlay 四条红线（崩溃<1%/无 ANR/首帧<3s/启动不一次加载全部资源）任一条不过直接出局；讣告页「逐字浮现 + 羊皮纸 1080x1920 + 事件时间线」在低端机上是 TMP mesh 重建 + GC 尖峰的重灾区，直通 ANR。而且每个真机 repro 是 5-20 分钟 build+deploy 循环，学生技能水平下定位 Android-only 崩溃极慢。PC 端几乎零风险 —— 所以是 Android 单方面拖。
- `severe` 手机切后台/来电恢复会崩 —— 计划通篇没提。Tick 循环若在 onResume 一次性补算离线期间的数百/数千帧（涌现模拟尤其危险，来源报告第 202 行专门警告过），恢复瞬间冻结 = ANR = P1 出局。正确做法是跨暂停直接「跳到结果」或给汇总，绝不逐帧补。这条在 TapPlay 免安装试玩环境里尤其容易触发（玩家随手切后台）。
- `severe` AI 美术方案里「AI 画不出来但计划以为能画出来」的四处：①「12 立绘 Unity 染色扩到 20+ 面孔」→ 得到的是 20 个换色克隆，玩家看到的是「同一个绿衣服的人」。游戏情感内核是「读每个人独一无二的一生」，撞脸直接摧毁这个前提 —— 这是最大的美术谎言。②厚涂量化到 12-16 色出的是色带/糊，不是 Spiritfarer 那种手绘丰富渐变，参照物根本对不上。③8 张地表 tileset 要在大地图上无缝拼接、光照一致、无接缝 —— 无缝平铺恰好是 AI 出图最弱项，必然回 Photopea 手糊。④「地标素材全同模型同 seed 也漂移」，跨 50 张图不能保证老槐树长得像同一个。
- `severe` 关系表 + 三共享变量结算（标称 150 行）会吃 3-4 倍工时。AI 半天就能把这 150 行写出来，然后它一定退化：要么全村同态（所有人做同一件事），要么全员瞬间暴死，要么什么都不发生。让 20 人 / 5 条法 / 3 个标量产生「非退化、非平凡」的涌现，本身就是这个游戏的全部，是参数扫描一周的活。计划却写「关键参数初始值照抄」—— 照抄的是一份未经验证的猜测，它会错。这是被隐藏的最大时间黑洞，仅次于 D5-D11 那条。
- `severe` 讣告会读成模板句，玩家第 5-6 篇就腻。理由在样例里：「他这辈子最怕的就是饿肚子」是饥饿/恐惧数值→措辞映射（确定性查表，同输入必出同句），「饿得只剩皮包骨」会在每 2-3 篇里逐字重现。60 tick 关卡 + 20 人，玩家前 20-30 分钟就读 5-8 篇；到第 5 篇就能看出映射表。更糟的是筛选器（top3、共享 actor/target/tile）+ 短寿命村民会导致事件表极薄，高频走人工兜底句「他还太年轻，没来得及做什么」—— 全游戏最假的一句会反复出现。「读完他们每个人的一生」是留存承诺，150 条语料 + 30 模板撑不住这个承诺（约 50-75 次阅读就见重复）。
- `severe` 5 篇开发者日志（不可同日连发）是评奖资格门槛，却被排在 D5/D7/D11/D14/D17 —— 全部落在赶工窗口里。崩盘期第一个被牺牲的就是「整理+写日志」，一旦少发一篇或同日连发两篇，直接失去参评资格，前面 18 天白干。这不是玩法风险，是运营自毁。
- `severe` D17「全流程自测 + 冻结只修不加 + 商店素材」压一天不成立。商店素材（512 图标 + 5-8 张真机截图 + 简介 + 标签 + key art）单独就要半天；而「冻结」前提是 bug 已清，可 D14 双端压测的问题往往到 D16 才修完 —— 冻结线一旦被击穿，D18 提审就是提交一个会崩的包。
- `minor` 目标奖是「最佳双端 ¥8 万」，但排期里没有任何一条把「保住双端」设成最高优先级。一旦 Android 出问题，最理性的自救是砍 PC 保手机 —— 保住了上线，丢掉了唯一目标奖；反之亦然。计划默认双端总是可行（「成本不增」），没有「如果必须砍一端，砍哪端、何时决定」的决策点。
- `severe` 教学关「90 秒内必死一个老村长，立刻弹第一篇点名某条法的讣告」完全依赖数值调优能不能复现 —— 调不出来时 demo 四要素（目标/规则/挑战/反馈）里的『反馈』就缺席，而这是新玩家 90 秒第一印象，也是保底门槛（≥50 去重下载）的转化命门。它被排在 D9，但 D9 时数值还没调好（见 D5-D11 攻击），顺序错了。
- `minor` JsonUtility「秒存」过于乐观：它不支持嵌套 Dictionary、不支持顶层数组、byte/short enum 字段与 struct 数组的经验性坑不少。LifeEvent[] 里字段全是 byte/short + 关系表是 20×19 有向图（本质是 Dictionary 或二维稀疏表），落盘要手写序列化，不是一行 JsonUtility 的事。存档一处坏 = 讣告图鉴全丢。

## 四、技术负责人的正面回应与重构

先看结论：**这份攻击绝大部分成立，我不辩护。** 原排期不是"乐观"，是**把研究问题当工程任务排期**。下面先认账、给规避，再给修订主干。

# 一、总判断（先认账）

原计划的死因不是"某天排多了"，是三条结构性错误：

1. **把"涌现"当成会自己长出来的东西。** 它是本作的灵魂，也是最不能排期的部分（来源报告第 131 行已写明参数调优靠手感）。计划只给 D10+D11 两天，且放在第 10、11 天——等于把全部核心风险压在最后 1/3 且不留缓冲。
2. **DSL 语义选错，从设计层就杀死涌现。** "自上而下首个命中生效"=法律互相遮蔽，不是组合。这是数学事实，不是实现问题。
3. **把"确定性跨端"当成一行注释。** 它是跨架构雷（ARM64 vs x64 的 FMA/求和序/集合迭代序），命中即违背官方"双端同一内容"。

**因此修订方向是：换引擎语义 + 大幅缩人数/法数 + 把研究风险全部前置到前 8 天 + 砍掉法律编辑器。** 具体见下。

# 二、逐条回应

## 【fatal ×4】

### F1. D4 压一天（法律编辑器）
**成立。** "选5条+调参+拖排序"是整个项目最大的一块 UI，学生+AI 至少 2-3 天。
**规避——直接砍掉"编辑器"：**
- v1 **不做运行时编辑 UI**。选法用**调试面板**（Inspector 里点选 + 一个 debug 热键面板），只在开发期用。
- 正式选法 UI 降级为 **D9**：12 选 5 的**列表 + 步进器（−/＋按钮）**，参数调整**只保留一个**（其余锁死在调好的值），**去掉拖拽、去掉下拉、去掉滑杆**。上下箭头改优先级。
- 法律模板数**从 12 砍到 8**（D5 前只做 4 条能跑的，D5 补到 8）。
- 交付日从 D4 挪到 **D9**（那时规则引擎已稳定，UI 只是壳）。

### F2. D5-D11 假设"涌现会自己长出来"
**成立，且这是最致命的一条。** 把不可排期的东西排进 D10/D11。
**规避——把涌现做成"有截止线的可 go/no-go 里程碑"，而不是普通工期项：**
- **D5 是硬门槛（gate）：** 第一次跑通"8 村民 + 3 共享变量 + 事件队列"，当场判定"活没活"。不活 → **不进入 D6 讣告，直接启动降级预案**（见第三节）。
- **D8 是复核门槛：** 若仍是"全村同态 / 全员暴死 / 什么都不发生"三选一 → **换引擎/换题**，绝不带着死的数值往讣告里灌。
- **总原则：涌现不是"做完"，是"接线 + 调"。"接线"进 D2-D5 是工程（可排期），"调"是研究（不可排期，靠前置 + 兜底）。**

### F3. DSL"首个命中生效"→ 退化
**成立，且是最聪明的一条。** 每 tick 每人只触发一条法 = 法律是竞争/遮蔽，不是组合；C(12,5)×5! 是组合学幻觉。
**规避——换引擎语义：遮蔽 → 叠加 → 反应式链。** 详见第三节（这是核心答案）。

### F4. "确定性 tick"跨端必崩
**成立，100%。** UnityEngine.Random 不保证跨平台、float FMA 收缩、Dictionary 迭代序——任一命中，手机与 PC 同 seed 出两个村，分享码成谎言，直接违背官方硬约束。
**规避——所有修法必须在 D2 就落地（不是 D14 才发现）：**
- 模拟层**只用 int / 定点（×1000）**，**禁 float**，渲染层才允许 float。
- 自带 **xorshift128 / PCG**（uint32 显式运算，整数跨架构精确一致），**永不碰 UnityEngine.Random**。
- **禁 Dictionary/HashSet 迭代**：全部改为**显式全序数组**（按 `(priority, ruleId)` 排序），遍历顺序即确定性。
- **禁 `string.GetHashCode()`**（跨运行时不稳）。
- 固定步长 tick，**不跟帧**。
- **验证手段（D2 当天就要有）：同一 seed 跑两遍 diff 状态哈希；PC 与 Android 各跑一遍比对同一哈希。** 这个测试是"跨端同一内容"的唯一证据，必须成为常驻自测。

## 【severe ×8】

### S1. 手机端拖后腿，D13-D14 的 1.5 天实际是 3-4 天
**成立（是 Android 单方面拖，PC 几乎零风险）。**

### S3. AI 美术四处"画不出来"

- ①**不染色克隆**。要 20 个"人"就**逐个 prompt 出 20 个可区分的扁平立绘**；做不到就**只要 12 个真正不同的村民**，不要 20 个绿衣服克隆。**12 个记得住 > 20 个撞脸。**（人数从 20 砍到 12，见第五节。）
- ②**主动选扁平/限制色风格**（Celeste / 杀戮尖塔风），这是 AI 的长处，也是平铺需要的；**不要厚涂量化**。
- ③**不 tile AI 出图**。地表用**模块化 9-slice/手工 atlas**；要平铺纹理就用 seamless prompt + 镜像混合在 Photopea 手缝，**单列半天**。
- ④**地标不跨图求一致**。每类地标用**一张**精灵，接受它，不要承诺"50 张里同一棵树"。

### S4. 关系表+三共享变量吃 3-4 倍工时
**成立（仅次于 F2 的黑洞）。** AI 半天写出 150 行，然后退化。
**规避：**
- 人数 **20→12（硬砍，实在不行 8）**，法数 **12→8**。变量仍 3 个。
- **把"调参"当研究日**：D5 全天 + D8 全天专门扫参数（可写个小脚本 headless 批量跑 seed，打印"活/死/同态"三分类），**不写别的**。
- **兜底：若 D8 仍不活，用"手写式涌现"替代模拟式涌现**（见第三节）。

### S5. 讣告读成模板句，5-6 篇就腻
**成立。** 确定性查表同输入必出同句；筛完 top3 后事件表极薄，兜底句"他还太年轻"会反复出现。
**规避：**
- **句槽 × 多候选 × 上下文加权**，取消"数值→固定句"的硬映射；同数值在不同事件上下文中选不同句。
- **运行时去重账本**：同一短语在本局 N 篇内不得复用（玩家的"腻"是相对的）。
- **最重要：讣告必须引用因果链**（"第 3 天，因为你写的第 2 条法，A 抢走了 B 的粮——这是 B 第一次恨上 A"）。因果链天然多样，且这是**可叙述的**——把状态爆炸变成内容。
- **坦白**：150 语料 + 30 模板撑不起"41 天留存"的承诺，实际是**数小时级的新鲜度**。这对**≥50 去重下载的保底线完全够**，但**宣传里别提长留存**，改卖"看它长成什么样"的一次性体验。

### S6. 5 篇开发者日志被排在赶工窗口
**成立，且这是运营自毁（少发/同日连发 = 直接失参评资格）。**
**规避——写在前、发在后：**
- **D9 之前把 5 篇全部写好（写稿不占发布节奏）**，发布日固定为 **D3 / D5 / D7 / D9 / D11**（绝不进 D12 后的崩盘期）。

**成立。**

- **冻结线从 D17 提到 D15**；D16-D17 是 bug buffer，不是"冻结日"。
- **冻结前提是 bug 已清**——D12 压测的问题到 D14 才修完是常态，所以 D15 冻结必须**硬执行（只修不加）**。

# 三、特别回应："涌现做假"

## 3.1 先说结论
**"自上而下首个命中生效"必假，攻击成立。** 而且**单纯改成"叠加（所有法效果相加）"也不够**——纯加法是单调系统，会收敛到不动点，没有历史、没有故事。

## 3.2 要在数据结构上保证组合爆炸，必须同时满足 6 条（缺一即退化）

```
寄存器文件 Reg：所有规则读写的同一组整数寄存器
 每村民: {gold, hunger, fear, health, ...}
 每村: {population, wealth, meanFear, ...}
关系图 Rel： V×V 有向整数边（V=村民数）—— 跨实体谓词的来源
规则 Rule（8 条，手写数据，非引擎生成）:
 { trigger: EventType|Tick,
 cond: 谓词列表（引用 Reg / Rel / 他人 Reg / 均值），
 effect: 对 Reg 的写（add / mul / cap / transfer / set），
 priority: int, // 全序 → 顺序敏感 → 非交换
 emit: EventType[] // 触发后续规则 → 链式
 }
引擎:
 queue.push(Tick); depth = 0
 while queue 非空 and depth < CAP(比如 64):
 ev = queue.pop()
 for rule in rules.sortedBy(priority, ruleId): // 稳定全序，禁集合迭代
 if rule.trigger == ev.type and cond.eval():
 rule.effect.apply(Reg)
 queue.pushAll(rule.emit) // 反应式
 log.append(ev, rule, snapshot, cause: ev.id) // 因果父指针
```

**六条结构要求，逐条对应"防哪种退化"：**

| # | 结构 | 若不满足会退化为什么 |
|---|---|---|
| 1 | **共享可变寄存器文件** | 规则彼此独立 → 无耦合（原计划的核心病） |
| 2 | **priority 全序 + 顺序敏感求值** | 5! = 120 个顺序维度归零 → 变成无序集合 |
| 3 | **反应式触发 + 有界反应队列** | 只有 1 跳（原计划的"恐惧传播"就 1 个两跳效果） |
| 4 | **跨实体谓词（引用他人 Reg / 均值 / 关系边）** | 3 变量 ODE（一个村），而非 12 节点有向图动力系统（V×(V−1) 条边） |
| 5 | **非线性算子下限（≥3 条用 阈值/比值/饱和）** | 单调 → 收敛到不动点 → 无振荡、无历史、无故事 |
| 6 | **因果父指针 causeRuleId/causeEventId** | 状态爆了但**玩家看不到** → 数学上爆炸、观感上是黑箱 |

**第 6 条是把"状态空间爆炸"翻译成"玩家可见内容"的唯一桥梁**——也是讣告的数据源。前 5 条保证"真的会炸"，第 6 条保证"炸出来的东西能讲成人话"。

## 3.3 但我必须承认边界
**上面保证的是"状态空间爆炸"，不保证"有趣的爆炸"。** 最后那一步——让 12 人 / 8 法 / 3 变量产生**非退化、非平凡且好玩**的涌现——是**参数扫描一周的活**，来源报告第 131 行自己承认"AI 最帮不上"。**一个学生 18 天做不完这一步。**

**所以真正的建议不是"怎么把模拟涌现做出来"，而是"换掉涌现的实现方式"：**

### 方案 A（推荐，保留《立法村》题材，改机制）：**storylet / 质量驱动叙事引擎**
- 共享 **qualities**（整数寄存器，每村民 + 每村）。
- **60 张手工 storylet**（小事件卡），每张带 `precondition(qualities)` + `weight(qualities)`。
- 每 tick 按权重随机触发前提成立的 storylet，改写 qualities；讣告读**已触发 storylet 链**（带因果父指针）。
- **为什么它一定不退化：** 每张卡是**人工写的**，所以"有趣"是**构造出来的**，不是"希望涌现出来的"。调参问题消失——你直接写有意思的状态，而不是祈祷它自发出现。
- **为什么仍然组合爆炸：** 卡 A 改 qualities → 解锁卡 B → 触发卡 C；60 卡 × quality 状态 = 巨大可达空间，且**每个点都是人写的、有意义的**。
- **为什么 AI 友好：** AI 批量写 precondition/effect/文本又快又好（常见模式）。
- **确定性**：整数 + 自带 PRNG，天然满足 F4。

> 这是业界对"涌现不可控"的标准解法（RimWorld storyteller / CK 事件系统 / Failbetter 的 QBN）。**它把"模拟式涌现"换成"编写式涌现"，把不可排期的研究换成可排期的写作。**

### 方案 B（真换题）：**《讣告推理》**
若连 storylet 都不敢做——那就**把模拟反过来跑**：给你一个村的 5 篇讣告，**反推**当初写了哪 5 条法。
- 100% 可人工编写的内容，**零模拟风险**，零数值调优，确定性天然成立，四要素（目标=猜法/规则=推理/挑战=隐藏法条/反馈=对错+讣告文本）全齐。
- 保留"看出他们一生"的情感内核和 AI 美术需求，**唯一的双端契合度也不变**（纯点选）。

**我的决策线：**
- **D5 gate：** 反应式链引擎跑通且**非退化** → 走方案 A。
- **D8 gate：** 仍退化 → **立即转方案 B**，用剩下 10 天做可交付的版本。**别在 D12 还嘴硬。**

# 六、必须承认的两条无解

1. **"一人 18 天做完原范围（20 人 + 12 法 + 通用 DSL + 全编辑器 + 双端 + 元系统 + 商店）"无解。** 唯一出路是**降范围**——上面那张砍表就是答案。降范围后能否活，取决于 D5/D8 两个 gate。
2. **"让模拟式涌现好玩"这一条，按原做法无解。** 它不是排期问题，是研究问题。所以**换机制（storylet 编写式涌现，方案 A）**，或**换题（讣告推理，方案 B）**——二者都把"不可排期"换成"可排期"。**今天 D1，两个 gate（D5、D8）还都在前头，现在改还来得及；到 D12 再改就已经没救了。**

**一句话总结：原计划的死因是把"研究"排成了"工期"，且引擎语义从设计层杀死了涌现。修订 = 换引擎语义（反应式链 / storylet）+ 砍一半范围 + 把研究风险前置到 D5/D8 两个硬 gate + 砍掉法律编辑器。**

## 五、双端工程总纲

# Unity 双端工程总纲 ·《立法城市》这类 UI 驱动游戏的务实版

> 适用前提：1 名程序员（学生 + AI 辅助）· Unity · 手游端为主 + PC 端同一内容 · 禁联网 · 18 天（10.1–10.18 提审）· 核心玩法是「点卡牌 / 读数值 / 看涌现」，无 3D、无物理、无摇杆、无联机。
>
> 这份总纲的底线立场：**双端对这类游戏是"低成本项"，不是"高风险项"。别把它当成第二款游戏来做。**

## 0. 先看总账（一句话版本）

| 项目 | 数字 |
|---|---|
| 双端净增工时（相对纯手游） | **≈ 16 小时 = 2 个工作日**（理想 1.5 天 / 最坏 3 天） |
| 首次打通双端构建 | 0.5 天，**必须在第 1 天完成**（D1 出两个空包） |
| 需要为 PC 单独做的 UI 布局 | **0 套**（只做 1 套 + 1 个"宽屏档位"） |
| 需要写的第二套玩法逻辑 | **0 行** |
| 真机测试频率 | 每 3 天 1 次，每次 15 分钟 |

## 1. 输入抽象：一套逻辑、两套映射

### 1.1 结论：不要用 Input System 的 Actions 资产来做这件事

Unity 新版 Input System 的正统用法是 `InputActions`（.inputactions 资产）+ Control Scheme + PlayerInput 组件，理论上"一套逻辑两套绑定"是官方卖点。**但对你不适用**，原因很具体：

- `.inputactions` 是**序列化 JSON 资产**，里面全是 GUID 和 binding id。AI 看不到资产、改不动它，只能凭记忆写 schema → **十写九错**，而且报错信息极差。
- Control Scheme 的"设备自动切换"对纯点击游戏是**杀鸡用牛刀**。
- 你的输入面窄到什么程度？《立法城市》全部输入 = **点 (Tap) / 拖 (Drag) / 长按 (LongPress) / 确认 / 取消 / 上一张下一张**。就这些。

### 1.2 推荐结构：Input System 只当"设备层"，上面盖一层 10 行的"语义层"

```
[设备层] Input System（只用来读原始输入）
 Touchscreen / EnhancedTouch Mouse.current Keyboard.current
 ↓
[路由层] InputRouter ← 启动时探测设备，挑一个 IInputSource 实现
 ├── TouchInputSource （手机：触摸为主）
 └── MouseKeyboardInputSource （PC：鼠标 + 键盘快捷键）
 ↓ 统一翻译成"语义事件"
[语义层] GameInput（静态门面，全局唯一入口）
 event Action<Vector2> OnTap;
 event Action<Vector2,Vector2> OnDrag;
 event Action<CardId> OnCardLongPress;
 event Action OnConfirm; event Action OnCancel;
 ↓
[逻辑层] 玩法代码只订阅 GameInput.OnTap / OnConfirm —— 完全不知道设备是什么
```

关键纪律：**玩法层代码里禁止出现任何 `Touchscreen` / `Mouse` / `KeyCode` 字样。** 一旦出现，你就分裂成两个游戏了。

### 1.3 三件必须盯的事（全是 AI 会踩的坑）

1. **uGUI 的 EventSystem 会整条死掉。** 如果项目 Active Input Handling 选了 "Input System Package"，EventSystem 上的 `StandaloneInputModule` 就完全不工作，**UI 全部点不动，而且不报错**。必须换成 `InputSystemUIInputModule`。这个坑 AI 生成项目时命中率极高，第一次跑不通先查这里。
2. **Hover 必须有无鼠标的替代。** PC 上"鼠标悬停卡牌 → 浮出效果预览"在手机上不存在。**所有 hover 才有的信息都必须能被点击/长按取出**（例如：点一下卡牌展开详情面板）。这是"同一内容"的硬要求 —— 不能让手机玩家看不到 PC 玩家看得到的信息。
3. **拖拽的手指点 vs 指针 id。** uGUI 的 `IDragHandler` 鼠标触摸统一，但触摸时**手指会挡住目标**，拖拽的卡牌要偏移到手指上方约 120px（1080 宽下）。PC 不需要这个偏移 → 用 `GameInput.IsTouch` 判断，偏移量写进语义层，不要写进逻辑层。

### 1.4 检查清单

- [ ] Active Input Handling 已定（建议 **Both**，最省事，代价是包体略大）
- [ ] EventSystem 是 `InputSystemUIInputModule`
- [ ] 玩法脚本 grep 不到 `Mouse` / `Keyboard` / `Touchscreen`
- [ ] 所有 hover 信息都有点击替代路径
- [ ] PC 端键盘快捷键有：确认(空格/回车)、取消(Esc)、翻页(←→)
- [ ] 真机验证过：单指点击、双指误触、手势条区域边缘点击

**工时：4–6 小时**（其中 1–2 小时大概率花在 EventSystem 那个坑上）。

## 2. 分辨率与宽高比

### 2.1 先定一件事：手游是竖屏还是横屏

这是全篇最贵的一个决策，**D1 之前必须拍死**。

| 方案 | 手游 | PC | 结论 |
|---|---|---|---|
| **竖屏内容盒**（推荐） | 1080×1920 竖屏原生 | 内容居中，**左右留装饰边（pillarbox）** | 一套布局两端通吃，PC 上一眼就是"手机游戏搬上大屏"，玩家接受度高 |
| 横屏通吃 | 16:9 横屏 | 16:9 到 21:9 | 若玩法本来就是横屏（如"蚂蚁画味"）才选 |

对卡牌/列表/数值面板类玩法，**竖屏是手游最优解**（拇指可达、一屏一卡、列表滚动自然），PC 就用"竖屏画布居中 + 左右装饰背景"。**不要为了填满 16:9 去做第二套横屏布局 —— 那等于做两个游戏。**

### 2.2 Canvas Scaler 具体设置

- **UI Scale Mode**：`Scale With Screen Size`
- **Reference Resolution**：`1080 × 1920`（竖屏基准）
- **Match**：`1`（按高度匹配）。竖屏游戏的内容纵向排布为主，按高度匹配最稳。

### 2.3 SafeArea：写一个脚本，两端共用

Android 刘海/挖孔/手势条、iOS 灵动岛都会吃掉边缘。做法：

- 建一个铺满屏幕的 `SafeAreaRoot`（RectTransform），挂 `SafeAreaFitter` 脚本：`Update`/`OnRectTransformDimensionsChange` 里读 `Screen.safeArea`，换算成 relative anchor 写进 `anchorMin/anchorMax/offset`。
- **PC 上 `Screen.safeArea` 返回全屏 rect → 脚本自动 no-op**，不需要分支。这就是"同一个脚本两端成立"的范例。
- 所有顶部/底部贴边的 UI（标题、按钮条、资源栏）都必须是 `SafeAreaRoot` 的子物体。

### 2.4 锚点纪律（AI 生成的 UI 最大扣分项）

AI 生成 UI 时会**硬编码 `anchoredPosition` 和绝对 offset**，在 1080×1920 上完美，一到 PC 的 2560×1440 就错位。纪律：

- 每个 UI 元素必须先设 `anchorMin = anchorMax`（贴到父容器的某条边/角），再设 offset/pivot。
- **禁止**在 inspector 里出现"左上角锚点 + 大数字 anchoredPosition"的居中元素。
- 需要"内容居中"就用满屏锚点 + 子物体居中，别算坐标。

### 2.5 PC 要不要独立布局？—— 结论：不需要，但允许 1 个断点

- **不做法**：两套 Prefab / 两套 Canvas。
- **做法**：只针对**超宽屏 (>2.2:1)** 加 1 个断点 —— 例如侧边信息栏从"折叠"变"展开"。宽高比 `> 2.2` 时展开，否则收起。一个 `AspectRatioFitter` 判断 + 一个 bool 就够。
- PC 窗口：允许自由缩放，但设 `Min` 尺寸（如 640×960），防止玩家缩到 UI 崩。或用 `Resolution and Presentation` 给 3 个预设分辨率。

### 2.6 检查清单

- [ ] Reference Resolution 已设，Match = 1
- [ ] SafeAreaFitter 挂好，顶部/底部 UI 都是它的子物体
- [ ] 全部 UI 锚点正确，grep 不到"魔法数字 anchoredPosition"
- [ ] 测过这些尺寸：1080×1920（基准）、1080×2340（长屏）、1170×2532（iPhone 刘海）、1920×1080、2560×1440、3440×1440（超宽）、1366×768（小窗）
- [ ] 超宽屏下没有 UI 被拉伸变形

**工时：4–6 小时**（含上面 7 种尺寸逐个过一遍）。

## 3. 构建与打包

### 3.1 两个 Build Target 的配置差异

| 项 | Android（手游 / TapPlay） | Windows (PC) |
|---|---|---|
| Scripting Backend | **IL2CPP**（必选） | **IL2CPP**（保持一致，减少行为差异） |
| 架构 | **ARM64**（+ ARMv7 可选，TapTap 要 64 位） | **x86_64** |
| API Level | Target 34 / Min 24 左右（跟官方要求） | — |
| Graphics API | **GLES3 优先**（兼容性最稳）；Vulkan 可选但不强求 | Direct3D11 |
| Managed Stripping | **Low**（AI 写的反射代码容易在 Medium/High 下被裁掉 → 运行时崩） | Low |
| Default Orientation | **Portrait** | 不适用（窗口） |
| 包体 | .apk（TapPlay 免安装直接用）+ 备一份 .aab | .exe + Data 文件夹（或单文件夹打包 zip） |

### 3.2 Player Settings 哪些要"分开管理"

Unity 的 Player Settings **本身就是按 Build Target 各存一份**，切平台会自动换值，所以不用手动分文件。但下面这些必须两端**各自确认一遍**（切了平台忘了改是高频事故）：

- Product Name / Company Name（决定 PC 的 persistentDataPath 目录名 → 定了别改）
- Version（两端版本号要一致）
- **Icons**（两平台各一套，AI 生成图标记得切圆角/自适应）
- **Keystore**（Android 必填；**现在就去建，建完立刻备份到两处**，丢了无法更新）
- Default Orientation（Android 竖屏）
- Splash Screen（免费版 Unity 那个 Logo 得接受）
- Bundle Identifier / Package Name

### 3.3 构建脚本：一定要自动化

写一个 `Editor/BuildScript.cs`，用 `BuildPipeline.BuildPlayer`，通过命令行 `-executeMethod BuildScript.BuildAll` 一次产出两个包：

```csharp
// 核心就三行，AI 能稳定写对这种常见模式
static void BuildAll() {
 BuildOne(BuildTarget.Android, "Build/Android/LegislativeCity.apk");
 BuildOne(BuildTarget.StandaloneWindows64, "Build/PC/LegislativeCity.exe");
}
static void BuildOne(BuildTarget t, string outPath) {
 EditorUserBuildSettings.SwitchActiveBuildTarget(
 BuildPipeline.GetBuildTargetGroup(t), t);
 var opts = new BuildPlayerOptions {
 scenes = EditorBuildSettings.scenes.Where(s => s.enabled)
 .Select(s => s.path).ToArray(),
 locationPathName = outPath, target = t,
 options = BuildOptions.None };
 var r = BuildPipeline.BuildPlayer(opts);
 if (r.summary.result != BuildResult.Succeeded) { /* 非 0 退出码 */ }
}
```

**价值**：把"构建"从"一件大事"变成"每天一条命令"，第 1 天之后增量成本≈0。这是整份总纲里 ROI 最高的一步。

### 3.4 时间数字（要提前知道的心理预期）

- Android IL2CPP **冷编译 10–20 分钟**；改一行代码热编 **2–5 分钟**。
- 首次配好两端 + 脚本 + keystore，**0.5 天**（一大半时间在等编译）。
- **等编译的时间不要发呆** —— 并行去写日志 / 接美术 / 改文档。

### 3.5 检查清单

- [ ] keystore 已建 + 双备份
- [ ] BuildScript 能一条命令出两包
- [ ] 两包都能装/打开、进主菜单、不崩
- [ ] Android 包 **ARM64**、**IL2CPP**、**Stripping=Low**
- [ ] PC 包在**没装 Unity 的机器**上跑过（确认没漏运行时依赖）
- [ ] TapPlay 免安装环境下启动过一次

**工时：6–8 小时**（含首次编译等待）。

## 4. 存档与路径

### 4.1 persistentDataPath 两端落点

| 平台 | 路径 |
|---|---|
| Windows | `C:\Users\<用户>\AppData\LocalLow\<Company>\<Product>\` |
| Android | `/storage/emulated/0/Android/data/<包名>/files/` |

**纪律：全程用 `Application.persistentDataPath`，禁止手写任何绝对路径。** 拼接用 `Path.Combine`。

### 4.2 跨端存档要不要互通？—— 明确结论：**不做，也做不了**

- 官方"同一内容"指的是**玩法/规则/关卡/数值/美术/叙事一致**，**不要求云端存档同步**。
- 硬约束"禁止联网" → **根本不存在云存档通道**。两端各自本地存档，物理上无法自动互通（玩家手动拷文件不算你的责任）。
- **唯一需要"兼容"的地方**：开发期你想把 PC 上的调试存档 `adb push` 到手机上复现 bug → **两端用同一套存档 schema** 就能互拷。这就够了。

### 4.3 存档实现纪律（AI 最爱在这里翻车）

1. **格式：JSON + 版本号字段。** 禁止 `BinaryFormatter`（跨平台/跨版本必炸，AI 老爱用）。用 `JsonUtility` 或 Newtonsoft。
2. **原子写入**：先写 `save.tmp`，成功后 `File.Replace` 覆盖 `save.json`。防止中途崩溃产生半截坏档。AI 不会主动这么写，**要显式要求**。
3. **版本迁移**：存档顶层放 `{"ver": 1, ...}`，读档时若版本不匹配走迁移或重置，别直接崩。
4. **不加密**：单机游戏不需要，加了反而给自己挖坑。
5. **路径用 Application 前缀**：`Application.persistentDataPath` + 文件名，无平台分支。

### 4.4 检查清单

- [ ] 存档只有一处路径常量（集中在 `SaveSystem` 里）
- [ ] 原子写入（tmp + Replace）已实现
- [ ] 存档带版本号，能优雅处理旧档
- [ ] 手机上有存档的前提下**杀进程再开**，能读回
- [ ] 用 adb pull/push 在两端之间互拷存档，都能读

**工时：2–3 小时。**

## 5. 性能：别让 PC 掩盖手机的问题

### 5.1 立场

**手机端是验收基准，PC 只是开发便利。** 日常在 PC 上快速迭代（编译快、能热重载），但——

**铁律：每 3 天必须上一次真机。** PC 上"很爽"完全不能作为"能上线"的依据。

### 5.2 两端性能差异会掩盖的五件事（PC 上永远看不出来）

1. **帧率体感**：PC 跑 200fps，手机锁 60 甚至掉到 30。**手游锁 60，30 为保底**；PC 不锁。
2. **纹理格式**：AI 生成的大 PNG 进 Unity 默认是 **RGBA32 未压缩**，一张 2048² = **16MB**。Android 必须压成 **ASTC 6x6**（同样一张 ≈ 2.8MB）。这步不做，手机内存直接爆。
3. **GC / 卡顿**：每帧 `new`、字符串拼接、**LINQ**（AI 高频爱写）在 PC 上看不出，手机上一卡一卡。你的"法律组合计算"千万**别每帧跑**，改成事件驱动 + 脏标记（dirty flag）重算。
4. **Canvas 重建**：uGUI 里改任意一个元素会触发**整块 Canvas 重建**。把所有 UI 塞进一个 Canvas = 每帧全量重排。**拆成 2–3 个 Canvas**（静态面板 / 动态数值 / 弹窗分离）。AI 基本不知道这条。
5. **系统级杀进程**：手机上后台被系统回收、过热降频、ANR（主线程卡 >5s）。PC 无此概念，但 **TapPlay 稳定性检测会真抓**。

### 5.3 具体防线（写进日程的固定动作）

| 动作 | 频率 | 工具/做法 |
|---|---|---|
| 真机性能画像 | 每 3 天 | Unity Profiler + Development Build + Autoconnect Profiler（USB 连真机） |
| 纹理压缩审计 | 美术导入后一次 | 全选 Sprite → ASTC 6x6；Sprite Atlas 合图 |
| DrawCall 检查 | 每 3 天 | Frame Debugger，2D 卡牌游戏应 **< 100** |
| GC Alloc 检查 | 每 3 天 | Profiler 的 GC Alloc 列，目标：游戏稳定态**每帧 0 KB** |
| 长挂机测试 | 每周 | 挂 30 分钟看内存是否持续上涨（泄漏） |
| 后台切换 | 每次真机 | 切后台再回，验证 `OnApplicationPause` 存盘、恢复正确 |

### 5.4 检查清单

- [ ] 手游帧率锁 60，掉了加 30 保底
- [ ] 所有 Sprite 是 ASTC 6x6，长边 ≤ 2048
- [ ] Canvas 拆成 ≥ 2 个
- [ ] 稳定态每帧 GC Alloc = 0
- [ ] 真机 Profiler 连过一次以上
- [ ] 挂机 30 分钟内存不涨
- [ ] 后台切换不丢档、不崩、能恢复
- [ ] 首帧不黑屏（启动兜底：加载画面 + 超时跳过）

**工时：4–8 小时**（高度不可控，取决于底子干净程度；如果一开始就按上面写，接近 4h）。

## 6. 测试矩阵

### 6.1 三档测试

| 档 | 何时 | 在哪 | 内容 | 时长 |
|---|---|---|---|---|
| **冒烟** | 每次构建 | PC + Android | 启动→主菜单→跑一次核心循环→退出，无崩溃无红字 | 2 分钟 |
| **每日回归** | 每天收工 | PC | 核心玩法 + 存档读写 + 边界（空档/满档） | 5 分钟 |
| **真机全量** | 每 3 天 / 发日志前 | Android 真机 | 见下 | 15 分钟 |

**真机全量必测项**：
- 冷启动时间（免安装环境下也要测）
- 点击精度 / 手势条边缘 / 刘海遮挡
- 切后台 → 回前台（Android 头号杀手）
- 旋转（若允许）或锁定方向是否正确
- 低内存场景（开一堆后台 App 再进）
- 挂机 30 分钟
- 存档：杀进程再进能恢复
- **TapPlay 免安装环境跑一整套**

### 6.2 能不能只测一次？—— 部分能

**可以复用的（在 PC 上测一次即算数）**：玩法逻辑、规则组合、数值、UI 流程、存档逻辑、任何纯逻辑 bug。这些**跟平台无关**。

**必须在真机测、无法省的**：性能、触摸精度、刘海/手势条、后台切换、免安装启动、真实 DPI 下的可读性。

**结论：把 ~85% 的测试放在 PC 上（快、可重复），手机只跑"PC 物理上测不到的那 15%"。** 别在手机上调数值 —— 那是浪费时间。

### 6.3 设备要求

- **至少 1 台 Android 真机**：要**中端/2–3 年前的老机型**，不要旗舰。旗舰的流畅度会骗你。
- 有预算再借 1 台低端机做最坏情况验证。
- PC 至少测一次 **1366×768 小窗** + 超宽屏。

### 6.4 缺陷分级与处置

- **P1（当场停手修）**：崩溃、黑屏、ANR、存档丢失、必现卡死。**TapPlay 检测抓到 P1 必现 = 直接禁止上线。**
- **P2（当天修）**：玩法可玩性受阻、UI 错位严重。
- **P3（有余力再说）**：观感、动效、文案。

### 6.5 检查清单

- [ ] 有一套 2 分钟冒烟脚本（哪怕就是手点一遍，写成 checklist）
- [ ] 每天收工必跑冒烟
- [ ] 每 3 天必上一次真机
- [ ] 发布前用 TapPlay 官方自测环境跑过一遍
- [ ] 提审前 24 小时**封版**，冻结改动只修 P1

**工时：全程摊在 18 天里，累计 8–12 小时。**

| 输入语义层 + 双设备路由 + hover 替代 | 4–6 | 3 |
| 分辨率 / Canvas Scaler / SafeArea / 锚点修正 | 4–6 | 3 |
| 构建脚本 + 两端 PlayerSettings + keystore + 首出双包 | 6–8 | 4 |
| 存档路径适配 + 原子写入 + 跨端拷档调试 | 2–3 | 2 |
| 真机性能体检 + 修复（纹理/Canvas/GC） | 4–8 | 4 |
| 测试矩阵执行（散在 18 天） | 8–12 | 8 |
| 日志 + 提审材料（双端截图 + 说明） | 2–3 | 2 |
| 缓冲 / 未知 | 6 | 2 |
| **合计** | **36–54h（5–7 天）** | **28h（3.5 天）** |

### 7.2 但真正落到日程上的净增量是：**2 天（16h）**

为什么比"全量"低？因为其中一大块（测试、日志、调试）**做纯手游也要做**，双端只多出"多测一遍、多出一包"的边际成本。真正的**净增量**只有：

1. 输入那点设备适配 —— 因为你只做点击，**4h**
2. 布局留边 + SafeArea —— **4h**
3. 构建脚本 + 适配第二平台 —— **4h**
4. 存档跨端调试 —— **2h**
5. 缓冲 —— **2h**
→ **≈ 16h = 2 天。**

### 7.3 这 1–2 天从哪挤最不伤游戏

**砍（安全区，砍了不心疼）**：
- ✂ **内容量**：法律条目砍 20%（少 3–5 条）→ 省 3h。玩家根本数不出少了几条。
- ✂ **交互动效**：卡牌飞入飞出、粒子、屏震、过渡动画 → 省 4h。这些**在双端还要各自调手感，性价比最低**。
- ✂ **PC 特供功能**：键位自定义、手柄支持、超宽屏专属布局 → 省 6h。**本来就不该做（见第 8 节，可能违规）**。
- ✂ **第二套 UI 主题/皮肤** → 省 3h。

**绝不砍（伤心，且伤到参赛根本）**：
- ✖ 核心循环的"涌现手感"（比如"限价拉到底 30 秒内一定长出黑市"这个 aha）
- ✖ 法律的**组合爆炸**（"法 A × 法 B = 你没写过的后果"）
- ✖ 【目标/规则/挑战/反馈】四要素的完整性
- ✖ 任何会让手机玩家体验变差的东西

### 7.4 最理想的压缩方式（省的是"等"的时间，不是"做"的时间）

- **第 1 天就打通双端构建** → 后面增量趋近 0，且不用在最后几天手忙脚乱。
- **AI 美术先出低分辨率占位**，流程先跑通，最后统一替换（省的是等美术的墙钟时间）。

**结论数字：双端对比纯手游，净增 2 个工作日（16h，含缓冲）。下限 1.5 天，上限 3 天。**

## 8. 官方对双端的硬要求

### 8.1 "同一内容"到底指什么

指**玩法 / 规则 / 关卡 / 数值 / 美术资产 / 叙事 一致，两端各自能独立完整通关**。核心是"**玩家玩到的是同一款游戏**"。

### 8.2 违规红线（会被判"为某一端特供"）

| 做法 | 判定 |
|---|---|
| PC 端有手机没有的关卡 / 法律 / 角色 / 玩法模式 | ❌ 违规 |
| 手机端是"阉割版"（砍玩法 / 砍难度 / 砍结局） | ❌ 违规（**反向也不行**） |
| 手机端专门做了独占内容换数据 | ❌ 违规 |
| 两端核心数值 / 难度是两套 | ❌ 违规 |
| 本质是两个不同的游戏（标题/包名/玩点不同） | ❌ 违规 |

### 8.3 允许的差异（合理适配，不算违规）

| 做法 | 判定 |
|---|---|
| UI 布局、分辨率、画面比例不同 | ✅ 适配 |
| 输入方式不同（触摸 vs 键鼠） | ✅ 适配 |
| 画质/性能档位不同（PC 更华丽） | ✅ 适配 |
| 平台专有 SDK（TapPlay 登录等） | ✅ 适配 |
| 语言、字号自适应 | ✅ 适配 |

**一句话记牢：玩法规则必须同源；界面/输入/画质是"适配"不是"内容"。**

### 8.4 数据与冲奖

- 两端**下载 / 试玩数据合并计算**，算一款参赛 → **两端都得能独立吸引人去下载**，别放弃任何一端的体验。
- 双端本身不是加分项就能拿奖。**最佳双端奖的前提，往往是你先有个能打的 demo。** 别为了"双端"这个名头牺牲游戏性 —— 那是最亏的取舍。

### 8.5 检查清单

- [ ] 两端玩到的法律条目 / 数值 / 结局完全一致
- [ ] 手机端没有因性能而砍掉任何玩法（只降画质）
- [ ] PC 端没有手机端没有的玩法内容
- [ ] 两端标题/包名/版本号一致
- [ ] 两端各自完整通关过一遍

## 六、决赛圈其他四方案的双端增量评估

## 一、deep-01《讣告》——增量最低，PC 反而更强

**1. PC 增量具体情况**

- **输入**：原方案已经用 `Input.GetMouseButton(0)`（Editor 和手机通用），所以"点格子"在 PC 上**零改动**即为鼠标左键。需要新增：
 - 鼠标**悬停显示移动/攻击范围预览**（触屏没有 hover，战棋没有 hover 手感会差一截）；
 - 手势冲突拆解：原来"单指拖动=平移、双指捏合=缩放"，PC 改为**右键/中键拖动=平移、滚轮=缩放**，把左键完整让给"选格/下令"；
 - 键盘：WASD 移光标、回车确认、1-6 选单位、A 攻击 / W 待命 / ESC 取消。
- **分辨率与 UI**：竖屏 HUD（上下边缘）→ PC 横屏改**左右侧栏**（单位面板常驻右侧）；全屏滚动讣告页（1080×1920）→ PC 改为**限宽阅读栏（≤900px）+ 侧边讣告图鉴**；战斗地图 24×16 在 16:9 横屏**可整屏显示**，比手机（短边只跨 10 格、要来回拖）更爽，只需重设 ortho size。
- **哪端吃亏**：**两端都不吃亏，PC 略占优**。战棋+长文本体裁本就是 PC 主场，PC 版是"升级版"不是"移植版"。

**2. 增量工时与挤法**：净增 **≈2.5–3 天**。原排期 D13（移动端 UI 适配）、D14（真机性能压测）、D15（触屏手感收尾）这三天本来就是"手机专属"，直接改造成"双端"三天（PC 端 UI/性能/输入比手机更轻，同一天覆盖两端）；再把 D1 工程搭建升级为"双端空包 D1 就都跑通"。净增部分从 **D11（讣告打磨，砍半天人工兜底模板扩充）+ D16（正式层 2-3 张砍到 2 张）** 挤出。

- D1 ★**双端工程日**：Android + Windows 双目标，两个空包当天首次构建并真机/PC 各跑通；中文字体。

## 二、deep-03《广场症候群》——输入白送，但构图/可读性是命门

**1. PC 增量具体情况**

- **输入**：方案已是 `Input.GetMouseButtonDown(0)/mousePosition`（PC 上即鼠标点地移动，**零成本**）；双击上房=鼠标双击；3 个动作按钮→**键盘 1/2/3 + 鼠标点击**；按钮热区 ≥88dp 在 PC 可缩小。
- **分辨率与 UI**：竖屏 1080×1920、`ortho=10`（近距俯视，NPC 约 96px，"3 秒看懂情绪光环"就是靠这个尺度）。**PC 横屏是核心矛盾**：关卡 36×48、横屏只露约 20 单位高——要么保持 ortho 只多看横向（要大幅纵移），要么拉大 ortho 看更多（NPC 光环缩小，**直接砸掉"3 秒看懂"这条生死线**）。建议 PC 走**竖窗口/pillarbox 保原生构图**，或把关卡重排得更宽。HUD（左下情绪图例、右下动作按钮、屏幕边缘恐慌温度）搬到角落+键位提示。
- **哪端吃亏**：**手机占优——近距离俯视可读性本就是为手机调的**，PC 吃"构图/可读性"的亏，而这恰是它的验收命门。

**2. 增量工时与挤法**：净增 **≈3 天**。它的"6.5 天是杂活、只有 11.5 天做玩法"本来就最紧。挤法：吃掉 **D15 缓冲日整块** + **砍沙盒模式（原 D9）** + 难度 3→2 档。D5（玩家）升级为双端输入、D12（适配）升级为双端适配、D13/D16 双端打包与预演各 +0.5。

- D2–D10 玩法调参**不变**（D5 顺带加键盘 1/2/3）。

## 四、deep-07《蚂蚁只认你画的味》——增量最高，核心动词就是触屏本身

**1. PC 增量具体情况**

- **输入**：单指按住画味→左键按住画；清水橡皮→右键/E；双指缩放平移→滚轮+中键/空格拖动；**多指同时画两条线→PC 砍掉**；最关键的——原设计的**"笔尖画在触点上方 60px 防手指挡屏"在 PC 上完全无意义，必须去掉**（否则鼠标点会偏移 60px）；"笔刷半径按屏幕像素固定"在 PC 可保留。它自己在 scopeOut 里写明"**不做 PC 版**"。

## 五、风险：改成双端后**最危险的是 deep-07《蚂蚁》**

理由（按杀伤力）：

1. **核心动词 = 触屏绘制本身，且被自己的设计钉死**。它的招牌设计"笔尖偏移 60px 防手指挡屏"在 PC 直接作废，多指同画作废——PC 版不是"改几个键位"，而是**重做全项目第二难的"笔刷手感"**（方案自己写的："手感你自己调"）。
2. **"画 vs 平移"在鼠标上抢同一个左键**。canvas（128²）大于屏幕，必须平移；而左键又要画。这是必须自创一套交互的地方，AI 给不出权威范式。
3. **排期零余量**。四个硬闸门 + "任何闸门晚了就砍下游、绝不顺延"，而双端要新增的天数只能从"关卡/围观/慢镜头"这些已被判定为下游的内容里挤，一旦 D4 锁参或 D6 垂直切片晚一天，双端就无处安放。
4. **竖屏方画布→横屏**是结构性妥协，且它 scopeOut 亲手写了"不做 PC 版"，说明作者已判定 PC 是净负担。

**次危险 = deep-05《菌毯》**：同为"画"类、输入改造相当，且它的 scope 是四个里最重的（8 关+4 卡+沙盒+分享卡+种子码+每日陷阱图），在满载 scope 上再加双端，超载概率高。
**deep-03 的独特风险不在工时而在"命门"**：可读性验收线（3 秒看懂）是在手机近距俯视下标定的，PC 横屏要在"看更多/看得清"之间二选一，赌的就是它最不能输的那条线；好在它有"看不懂就砍成固定关卡情绪解谜"的现成兜底。
**deep-01 最安全**：鼠标原生、回合制无时序、文本能换栏宽、体裁双端通吃。

## 一、双端奖现实性评估

**概率拆解：** P(获奖) = P(两端都成功上线) × P(获奖 | 上线)

- **P(两端都上线) ≈ 0.85**（按计划 D1 出双空包、D13 适配、D14 压测）。
 - PC 端（Windows x64，同一份代码切 Build Target）几乎零风险，跑不起来的情况基本不存在。
 - 真正的风险全在**手游端 TapPlay 稳定性**：P1 必现崩溃 / ANR / 黑白屏 = 直接禁止上线。学生 + AI 最容易踩的是**切后台/来电恢复时逐帧补算**（冻结→ANR，P1 出局）和**讣告长文本逐字重建 mesh**（CPU 尖峰→ANR）。这两条必须在 D3 存档框架、D9 常驻自检里就解决，不能等 D14。
- **P(获奖 | 上线) ≈ 0.25–0.40**。TapTap 是手机优先平台，**双端选手天然稀少**，这是最大利好；但本作是 18 天单人内容，体量薄，上限受限。若双端奖只设 1 名，取下限；设 2–3 名，取上限。

**净概率区间：0.13（悲观）– 0.45（乐观），中位约 0.25。**

**风险主要在哪（按真实威胁排序）：**

1. **手机端拖后腿（最大，25–40% 概率出问题）**——不是"性能不够",是 TapPlay 四条红线（崩溃<1% / 无 ANR / 首帧<3s / 不一次加载全部）没做常驻自检。这是**双端和纯手游共担**的风险，不该记在双端奖头上。
2. **两端内容不一致被判违规（10–15%）**——只要坚守"内容零差异，只切平台"就不会发生。**唯一可被误判为"不一致"的点是交互信息不对称**：PC 上"鼠标悬停看效果预览"这类 hover 信息，手机上取不到。规则很简单——**所有 hover 才有的信息，必须能通过点击/长按取出**，加进 InputAdapter 的 `Detail` 语义事件（长按或右键）。
3. **PC 端跑不起来（<5%）**——可忽略。唯一要防的是别把 `Touchscreen`/`Mobile` 专属代码路径带进 PC 分支，用 InputAdapter 一层隔离即可。

**为了它多花几天：约 2 天**（输入抽象 0.5 天并入 D2 + 双端适配 1 天 D13 + 双端压测 0.5 天 D14 + 两次打包 0.5 天 D18）。**结论：值，且必须锁在前段。**

| **选题** | **定《立法村》**（上架名），宣传语「他们死于你写的法律」。备选名不用，备胎见第 6 节。 |

## 二、D1 三段动作（每段半天内可验收）

**上午 · 工程与配置**
- 锁 Unity 2022.3 LTS，建 2D 工程；两个 Build Profile 建好：Android（IL2CPP / 仅 ARM64 / 锁横屏 / 包名 / 签名 / Managed Stripping Medium）、Windows x64。
- 接一个中文字体（TMP），场景里显示一句中文。
- ✅ 验收：工程能开，双 Build Profile 就绪，TMP 出中文不豆腐块。

**下午 · 双端空包（今天最重要的一件事）**
- 出 Android APK → 装中端安卓真机 → 启动进空场景：**不崩、不黑白屏、不 ANR**。
- 出 Windows exe → 双击能开。
- 跑 TapPlay 自检工具，记录基线（包体 / 首帧 / 有无 P1）。
- ✅ 验收：两个包都跑起来，自检无 P1 红项。「双端风险前置」到今天就完成。

**晚上 · 地基 + 日志**
- `git init` + 首次提交；目录：`Scripts/Sim`、`Scripts/Obituary`、`Scripts/UI`、`Art`、`Docs`。
- 写 **xorshift128 RNG + 状态哈希** 空实现，跑通「同 seed 跑两遍 → 比对哈希」的自测骨架（先能跑，D2 再填肉）。
- TapTap 发**开发者日志 #1**（≥5 篇且不能同日连发，今晚必须发第一篇）。
- ✅ 验收：有 commit、哈希自测能跑、日志 #1 已上线。

## 三、D1 结束的验收标准

**这一天合格的信号**
- 手机装得上、启动到空场景不崩不黑白屏；PC exe 双击能开；
- 双 Build Profile 已配好，两个包今天都出过；
- git 有首次提交，哈希自测骨架能跑；
- TapTap 日志 #1 已发。

**必须立刻调整的信号**
- **今天任一平台出不了包** → 明早第一件事换引擎版本 / 重建模板重试，禁止「以后再补」（这就是把双端风险推到 D13 的死法）。
- **TapPlay 自检报 P1（崩溃 / ANR / 黑白屏）** → 当天换引擎版本或换模板，P1 是一票否决。
- **真机启动黑屏/闪退、一小时定位不出** → 降引擎版本或换更干净的 2D 模板，不硬扛。

## 四、D1–D3 时间线（★=拖到 D4 必连锁延期）

- **D1 ★双端工程日**：双端空包 + 自检基线 + git + 日志#1。〔拖到 D2 → 「风险前置」全失效，D13 必挤爆〕
- **D2 ★确定性内核日**：定点数（×1000，禁 float）+ xorshift + 显式全序数组（禁 Dictionary/HashSet 迭代）+ 状态哈希比对；网格/Tilemap + `bool[,]` + 点击吸附最近格。〔拖到 D4 → 跨端不一致只能在 D14 才现 = 死〕
- **D3 数据与循环日**：村民数据结构 + tick 主循环（固定 1s / 暂停 / 单步 / 倍速）+ 移动 steering + `OnApplicationPause` 的「resume 只跳帧、绝不逐帧补」策略；跑一次真机 15 分钟自测。〔拖到 D4 → D5 涌现 gate 没有输入〕
- **硬节点**：**D5 涌现 gate**（8 村民 + 3 共享变量 + 事件队列跑通，「活没活」当场判；不活即启降级）；**D8 复核 gate**（仍同态 / 暴死 / 无事发生 → 换题）。D4 起 DSL 语义按「叠加 → 反应式链」写，**不做运行时法律编辑器**，选法 UI 降到 D9（12 选 5 → 砍到 8 选 5，只留一个可调参数）。

## 五、三条红线（一句话后果）

1. **禁止任何联网功能**（无服务器 / 无实时多人 / 无在线 API / 无在线 LLM / 无局域网）—— 违反 = 直接取消参赛资格。
2. **双端同一内容：单工程 + 两个 Build Profile，只切构建目标，零平台独占内容** —— 违反 = 不符合双端参评条件，¥8 万双端奖直接没资格。
3. **模拟层禁 float、禁 `UnityEngine.Random`、禁 Dictionary/HashSet 迭代，且「同 seed 双端哈希比对」必须常驻自测** —— 违反 = 同 seed 双端跑出两个村、分享码成谎言，且只在真机暴露，发现即来不及。
