## 1. 为什么要有这份东西

技术验证报告里有一句结论，这份测试集就是它的产物：

> **数值必然会崩，而且不会报错。**
>
> 修完五个编译级 bug 之后，游戏仍然不可玩：村庄活着，但所有寄存器收敛到边界，
> 10 个律法条件里只有 2 个可用。**它不崩溃、不报错**，只会让玩家觉得"这游戏没反应"。

更麻烦的是，**同一个症状（σ→0）在验证过程中由完全相反的原因引起过四次**：

| # | 病因 | 症状 |
|---|---|---|
| 1 | 金币只进不出 | 全员顶格 |
| 2 | 恐惧只有汇没有源 | 恒为 0 |
| 3 | 加了正反馈 | 反而全员顶格（与 1 同型） |
| 4 | 恐惧源太强 + 衰减太慢 | 全部饱和在 87（与 2 反向同型） |

**也就是说，靠直觉和"看起来不好玩"来调参，必然会反复踩回去。**
唯一可靠的办法是让这几个数字**常驻在测试里**——它们红了，就是这一版不能发。

还有一类只有测试能抓的东西：**死信**（只被写、从没被读的字段）。
修之前 13 个标签里 3 个是死信，其中「信徒」被写了 33 万次、一次都没被读过。

## 2. 三种跑法

### 2.1 脱机跑（**今天就能跑，不需要 Unity**）

```bash
cd _tests
dotnet test
```

用 NUnit（Unity Test Framework 内置的也是 NUnit 3），所以 `EditMode/` 下的 `.cs`
**一个字都不用改**就能拖进 Unity。

### 2.2 Unity EditMode

1. 把 `_tests/EditMode/` 整个目录拷到 `Assets/Tests/EditMode/`
2. 该目录加一个 `asmdef`：
   - `References`：`Sim`、`Diag`、`UnityEngine.TestRunner`、`UnityEditor.TestRunner`
   - `Define Constraints`：`UNITY_INCLUDE_TESTS`
   - `Precompiled References`：`nunit.framework.dll`
3. `Window → General → Test Runner → EditMode → Run All`

### 2.3 Unity PlayMode（真机冒烟）

见 `_tests/PlayMode/SmokeTests.cs`，拷到 `Assets/Tests/PlayMode/`。
它跑的是**真机才能暴露的东西**：首帧、后台切换、存档往返、内存增长。

## 3. 测试清单（60 条）

> 阈值不是拍脑袋的，都是 `技术验证报告.md` 与 `_proto/` 实测出来的。

### T01 · 确定性随机（10 条）

守的是**整个项目的可复现性**：同 seed 双端逐位一致、反事实对照、分享码、
"只改一条法跑出两个村子"——全部建立在这一层上。

| # | 测试 | 守什么 | 阈值 |
|---|---|---|---|
| 01 | `For_是纯函数` | Rng 里不能有隐藏状态 | 1000 组参数两次调用全同 |
| 02 | `不同channel产出不同值` | 7 个 channel 必须真正参与混合 | 7 个值互不相同 |
| **03** | **`同一tick内序列号必须隔离_Bug2回归`** | ★ **Bug 2** | 8 个 seq 产出 8 个不同值 |
| 04 | `不同tick产出不同值` | tick 必须充分参与混合 | 500 个 tick 无重复 |
| 05 | `不同seed产出不同值` | seed=0 不能自锁 | 500 个 seed 无重复 |
| 06 | `Range永远落在区间内` | 取模不能越界 | 5000 次全在 `[lo, hi)` |
| 07 | `Range的span为0或负数时不崩` | 防 `%0` 崩 | 返回下限，不抛 |
| 08 | `Chance的0和100是短路` | 0%/100% 必须字面成立 | 1000 次全对 |
| 09 | `Chance的分布大致无偏` | 权重必须等于真实概率 | 30% 实测落在 29.3–30.7% |
| 10 | `Mix64无碰撞` | 混合器必须是双射 | 10 万个输入无碰撞 |

> **T01_03 单独说**：它是全套里最重要的一条。Bug 2 的表现是"同一 tick 内 8 个优先级段
> 只产出 1 个不同值"——**不崩溃、不报错**，只会让加权随机静默退化成"高权重卡被系统性偏好"。
> 除了这条测试，没有别的东西能抓住它。

### T03 · 确定性（5 条）

命根子。比赛的"一句话证明"成立的前提是**同 seed 必须逐位可复现**。

| # | 测试 | 守什么 | 阈值 |
|---|---|---|---|
| 01 | `同seed两遍哈希一致` | 无 static 状态泄漏 | 60 个 seed，0 例不一致 |
| 02 | `交错运行不互相污染` | ★ 比 01 严：抓跨实例污染 | A→B→A 三次哈希相同 |
| 03 | `不同seed必须分岔` | 反过来的失败：seed 根本没接进去 | >75% 的 seed 哈希互异 |
| 04 | `槽位顺序是优先级_必须影响结局` | 见下方说明 | ≥50% 的 seed 被顺序影响 |
| 05 | `Villager字段白名单` | ★ "新字段必须显式决定是否进哈希" | 字段集合完全相等 |

> **T03_04 是一条设计裁决，不是实现细节。** 实测：40/40 个 seed 上，同一组 5 条法换个装填顺序
> 就会跑出不同的村子（tick 内按槽位 0→4 依次适用）。我们**保留**这个行为并把它定义成
> "律法的适用优先级"——现实里法条的适用顺序本来就不中性。
>
> ⚠️ **由此产生一条必须落到 UI 上的约束**：槽位顺序绝不能被藏起来，玩家看到的必须是
> 「第 1 条 / 第 2 条 …」。否则同一组合因拖放顺序不同给出不同村子，玩家只会觉得"这游戏随机"。

> **T03_05 是一条绊线。** 它不测对错，测的是"你有没有停下来想一次"。
> 加了 `Villager` 字段却忘了更新白名单 → 它会红 → 你必须显式决定这个字段进不进哈希。

### T05 · 涌现（6 条）★ **主题的守护测试** ★

这一批保护的不是"代码对不对"，而是**"这游戏还配不配叫涌现"**。

| # | 测试 | 守什么 | 阈值 |
|---|---|---|---|
| **01** | **`同seed只改一条法的阈值必须分岔`** | ★ 给评委的核心证明 | **40/40 全部分岔** |
| 02 | `随机律法组合的终局形态必须分化` | 判据 1+4：不能退化到不动点 | 200 个 seed ≥3 种形态 |
| 03 | `结局是梯度而不是两极` | ★ 结构性：承载力模型不能被改坏 | 两极 ≤55%，档位 ≥8 |
| 04 | `存活村庄的三寄存器必须有方差` | 判据 2：反馈环 | 金币 σ>8、饥饿 σ>5、恐惧 σ>3 |
| **05** | **`八条预设法必须全部是载荷法`** | ★ **"立法有效"** | 8 条 `|presence effect| ≥ 1.5` |
| 06 | `恐惧必须是活寄存器` | 恐惧不能是死胡同 | 读次数>0 且 读 > 写/10；p95−p50 ≥6 |

> **T05_05 背后的实测教训**：修之前 8 条法里**只有 2 条承重**。
> "税收"的边际影响是 **0.07**——玩家把它选进去和不选它，村子一样。那就是装饰。
>
> **T05_03 背后的结构性错误**：如果产出与消耗都严格按人头走，收支比值就与人口无关
> → 人口下降既减少产出也减少消耗 → **死人不解决粮食问题** → 中间态不稳定
> → 结局只能非 0 即 20。修法是承载力模型（人均产出随人口递减）。
> 这条测试防止它被改回去。

### T06 · 内容完整性（4 条）

抓**死信**——只被写、从来没有被读的字段。

| # | 测试 | 守什么 | 阈值 |
|---|---|---|---|
| **01** | **`每个标签都必须有读者`** | ★ 13 个标签全部要有真读者 | 死信数 = 0 |
| 02 | `每条预设法都要在真实组合里开火` | 律法不能"装了等于没装" | 平均每局 ≥20 次 |
| 03 | `可用条件数不能太低` | 条件不能落在死区 | 存活村庄平均 ≥5/10 |
| 04 | `死亡必须能归因到律法槽` | 讣告要能写"死于你写的第 N 条法" | 20 个村庄 >20 人死亡 |

> **T06_02 是踩过坑才写成这样的。** 最初把同一条法装 5 份来测，结果
> 「私刑倾向」开火 0 次。查下去发现：它的生效前提是"这人身上已经有伤疤"，
> 而伤疤要靠**另一条法**（饥则抢）打出来——**它不能自举**。
>
> 这不是 bug，这是设计要的**法→法耦合**。但它顺带产出了一条内容设计约束：
> **反应式律法不能单独出现在第一幕的法池里**（已写进开工清单 §6）。

> **T06_01 依赖 `Sim/Diag.cs` 的运行时计数器，不是人工维护的清单。**
> 上一版诊断仪用写死的字符串报告这件事——改完代码后字符串没跟着改，
> 于是它开始报告一个**已经不存在的世界**。数出来的才算数。

### T07 · 性能与 GC（4 条）

| # | 测试 | 守什么 | 阈值 |
|---|---|---|---|
| 01 | `单tick不产生GC分配` | Tick 里不能有 new/装箱/字符串/LINQ | ≤64 B/tick（目标 0） |
| 02 | `单tick耗时留有真机余量` | PC 上留 30 倍折价余量 | ≤500 µs/tick |
| 03 | `构造World的分配量有上限` | 回归：曾有一对 `int[8020]` 纯垃圾 | ≤8 KB/World |
| 04 | `反复跑局不累积内存` | 没东西被 static 集合攒住 | 200 局后增长 ≤2 MB |

> 在 PC 上测手机性能是有意义的，因为这两个指标**不是"快不快"，是"有没有"**：
> PC 上不是 0 字节/tick，在手机上就不是"偶尔卡"，而是"每秒一次的 GC 尖峰"。

### T08 · 纪律（5 条）

> 技术验证报告的结论：**AI 能写"算法"，不能写"纪律"。**
> 它会用 `Dictionary`、用 float 算百分比、调 `UnityEngine.Random`、
> 拿 `struct.GetHashCode()` 做哈希——而**只有一部分会导致编译错误**，其余全是静默退化。

| # | 测试 | 禁用 |
|---|---|---|
| 01 | `Sim层禁用浮点` | `float`/`double`/`Mathf`/`Math.Sqrt` 等 |
| 02 | `Sim层禁用UnityEngine` | 这一层必须能脱离引擎跑 |
| 03 | `禁用非确定性随机源` | `System.Random`/`Guid.NewGuid`/`DateTime.Now`/`Environment.TickCount` |
| 04 | `禁用字典与哈希集的迭代` | `Dictionary<>`/`HashSet<>`（枚举顺序不保证跨运行时一致） |
| 05 | `禁用struct的GetHashCode` | Mono 与 CoreCLR 实现不同，字符串哈希还有每进程随机盐 |

> **这 5 条是文本扫描，扫描前会剥掉注释**——本项目注释里大量出现 `float`/`double` 这些词
> （就是在解释为什么禁用它们）。
>
> ⚠️ **它们依赖 `Sim/` 真的干净。** 因此 `Stat()` 和 `UsableConditions()` 被搬到了 `Diag/`：
> 它们用了 `Math.Sqrt`，留在 `Sim/` 里会让"Sim 层禁浮点"这条规则**无法用扫描证明**，
> 于是只能给它开一个会腐烂的白名单。拆开之后 T08_01 是一条**绝对**断言。

## 4. 红了怎么办

**先看这条表，再动代码。** 大部分红是"设计退化了"，不是"代码写错了"。

| 红的测试 | 最可能的真因 | 先查这里 |
|---|---|---|
| T01_03 | 有人动了 `Rng` 的签名 | 是不是又把 `seq` 去掉了 |
| T02_01/02 | `PackPair` 被"简化"成 `a*N+b` | 别简化，看注释 |
| T02_05 / T04_10 | `ApplyRemoveTag` 的掩码改了 | 伤疤必须免疫 |
| T03_01/02 | 新加了 static 可变状态 | 最近改的字段是不是写成了 static |
| T03_05 | 加了 `Villager` 字段 | **停下来想**：进不进 `HashState`？想完改白名单 |
| T04_01 | 存档路径被重写 | 直接用 `AtomicWrite.Write`，别自己写 |
| T04_07 | `hitsTotal` 又出现了第二个 | 疲劳逻辑只能读 `Law.hitsTotal` |
| **T05_01** | **确定性破了** | 这是**最严重**的一条：先查 T03，再查 float 泄漏 |
| T05_02 | 系统退化到不动点 | 见 `技术验证报告 §2.5` 五条配平 |
| **T05_03** | **承载力模型被改坏** | `PROD_BASE` / `CROWD_K` / `FARM_PCT` |
| T05_04 | 某个寄存器被推到边界锁死 | σ≈0 的那个寄存器，检查它的源/汇是否配平 |
| **T05_05** | **有律法变成了装饰** | 看报告里的边际影响，先查它的条件是否落在死区 |
| T05_06 | 恐惧没有读者了 | `Sim/Diag.cs` 的计数，不要用眼睛看代码 |
| T06_01 | 出现了死信 | 给新标签接一个读者，或者把它从设计里删掉 |
| T06_02 | 律法不开火 | 条件死区 → 先跑 `--deep` 看 B2b 的可用带 |
| T06_03 | 探针阈值落到带外 | **先重跑 `--deep` 看 B2b**，再改 `Diag/WorldStats.cs` |
| T07_01 | Tick 里混进了容器/字符串 | 看最近改的 hot path |
| T07_03 | 又预分配了大数组 | 确认它真的有人读 |
| T08_0x | 纪律破了 | 按提示改；**不要**改测试去迁就代码 |

## 5. 这套测试**挡不住**什么

必须诚实划界。下面这些只能靠别的办法，测试全绿不代表游戏没问题。

| 挡不住的 | 为什么 | 靠什么补 |
|---|---|---|
| **跨端确定性** | 这里测的是同进程内确定 | D2 就出 Android ARM64 IL2CPP 包，**三端哈希比对** |
| **IL2CPP 剥离** | 托管环境测不出 | 真机跑，`link.xml` 保住反射类型 |
| **真机性能** | PC ≠ ARM，差 15–30 倍 | D15 Profiler 连真机 |
| **DrawCall / 纹理上传** | 纯逻辑测试看不见 | D15 |
| **UI 布局** | 需要看屏幕 | §6 手动清单 |
| **内容质量** | "讣告像不像人话"无法断言 | 找 3 个外人读 10 篇 |
| **手感与节奏** | 同上 | 自己完整玩 3 遍 |

## 7. 已知环境坑（不是代码 bug，别去修代码）

> **在同一目录下并发跑 `dotnet build` 与 `dotnet test` / `dotnet run`，进程会随机崩溃**，
> 抛 `AccessViolationException` 或指向 `World.Tick` 的 `NullReferenceException`，
> **崩点每次漂移**（见过同一个测试报三个不同行号）。

本次验证中出现过 **4 次**，独立复现不出来：最重的那个测试（56 组合 × 16 seed）单独跑 7 次全过；
修完 harness 后连续 7 次全套 60/60 全绿。

**运维规则**：
1. 一次只跑一个 dotnet 命令（不要一边 build 一边 test）
2. 崩了就重跑一次——**连续两次崩在同一个测试**才值得去查
3. 后台不要挂着一堆 `dotnet run`

> 顺带修掉的一个真 bug（藏在测试基类里）：原来的 `Diag.On` 是"快照—还原"式的，
> 一旦某条测试在关掉它之前就断言失败，`On` 就留在 `true`，下一条测试的 SetUp 把它快照下来、
> TearDown 又还原成 `true`——**一次失败 = 整个进程后续所有测试都开着诊断跑**。
> 现在两边都硬置 `false`。

## 8. 加新测试的规矩

1. **测"承诺"，不测"实现"。** 名字要写成「XX 必须 YY」，而不是「XX 函数返回 Z」。
   例：`伤疤不可被清除`，不是 `ApplyRemoveTag_Returns`。
2. **阈值必须来自实测。** 拍脑袋的阈值会在第一次调参时全红，然后你就开始改测试——测试就死了。
3. **测试里写清"为什么"**，尤其是"这条为什么不能删"。
   本项目里最有价值的几条测试，价值全在注释里（Bug 1/2/3/5 的回归测试）。
4. **继承 `SimTestBase`。** 它会快照/还原 `World` 的 static 标定参数。
   不继承的话，你改了参数会污染后面的测试，而且**不报错**，只是让某条不相干的测试偶尔失败。
5. **重活标 `[Category("Slow")]`**，让日常能只跑 `Fast`。
6. **别写会腐烂的东西。** 宁可让测试红，也不要给它开白名单。
