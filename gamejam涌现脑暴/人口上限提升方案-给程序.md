# 人口上限提升方案（给程序）

> **目标**：起始 20 → 24，人口上限 50 → 80。
> **手段**：把村民画小，把出生间距从 2 格降到 1 格。
> **不动地图**（地图改大是另一件事，成本高得多，见 §6）。

---

## 0. 一句话原理

上限不是被"地图不够大"卡住的，是被**出生间距**卡住的。

出生点用的是切比雪夫间距。间距 2 意味着**每人独占 2×2 = 4 格**，密度被锁死。

```
间距 2  →  每人 4 格  →  10×8 的出生区放得下 20 人    ← 现状
间距 1  →  每人 1 格  →  同一个出生区放得下 80 人
```

而**间距能不能降到 1，取决于村民画多小**。人小了不挤，密度才提得上去。

---

## 1. 先测三个数，不测别动手

我看不到你的场景，只能读代码。**下面三个数必须在 Unity 里实测**，它们决定这个方案能不能落地。

### 测法

在 `MapViewBinder` 里加一行临时代码打日志。

```csharp
Debug.Log($"content={mapContent.rect.width}x{mapContent.rect.height}  " +
          $"每格= {mapContent.rect.width / 48f:F1} x {mapContent.rect.height / 32f:F1} px");
```

再选中一个 `VillagerWalker` 的 `visual` 节点，看它的 **Width / Height**。

### 要记下来的三个数

| 代号 | 是什么 | 从哪来 |
|---|---|---|
| `CW` / `CH` | `mapContent` 的实际尺寸 | 上面那行日志 |
| `TW` / `TH` | **一格在内容空间里有多少像素** | `CW / 48` 和 `CH / 32` |
| `VW` / `VH` | 村民 visual 的实际尺寸 | 场景里选中节点看 |

> ⚠️ **横向和纵向要分开算。** 地图是 48×32，而内容区大概率不是 3:2（代码里的兜底值是 3840×1136，那是 **3.38:1**，说明地图被横向拉伸过）。
> 如果真是这样，**一格是 80×35.5 的矩形，不是正方形**——那么**竖向才是瓶颈**，横向还宽裕得很。这一点会直接改变你该选哪个方案。

---

## 2. 判断能不能降到间距 1

判据只有一条。

```
竖向间距 px  =  TH × 新间距(1) = TH
触摸目标要求 =  88 px（手机端一个靠谱的点击目标）
```

| 测量结果 | 结论 | 走哪个方案 |
|---|---|---|
| `TH ≥ 88` | 间距 1 可以直接点 | **方案 A** |
| `TH` 在 50–88 之间 | 间距 1 点不准，但**靠相机放大能救** | **方案 A + 默认拉近** |
| `TH < 50` | 竖向太挤 | **方案 B（非对称间距）** |

---

## 3. 方案 A · 等比缩小 + 间距 1（首选）

### 3.1 场景侧（先做，零代码）

1. 把 `VillagerWalker` 的 `visual` 节点**等比缩小到约一半**（具体比例按 §1 的测量结果定，目标是缩小后 `VW` ≈ `TW × 0.8`）
2. **`visual` 的父节点 `body` 不要动。** `body` 负责位置，`visual` 只管显示。缩错节点会导致村民走到别的地方
3. 在 `VillagerActorView` 所在的节点上加一个**透明的点击热区**，尺寸不小于 `TW × 0.9 × TH × 0.9`，勾上 `Raycast Target`，**视觉 sprite 本身关掉 Raycast Target**

### 3.2 代码侧

| # | 文件 | 改什么 | 注意 |
|---|---|---|---|
| 1 | `VillageMap` | `SpawnCount` 20 → **80** | 常量 |
| 2 | `VillageMapGenerator.PlaceSpawns` | 网格 **5 列 × 4 行、间距 2** → **10 列 × 8 行、间距 1** | 锚点仍是 `(23, 15)` |
| 3 | 同上，**强制草地菱形** | 半径 **6 → 10** | ★ 见 §4，漏了会有一半出生点跑到水里 |
| 4 | `VillagerWalker.patrolRange` | `(120, 36)` → 按 §3.3 的公式重算 | ★ 见 §4 |
| 5 | `VillageSaveService.CreateNewGame` | 名字数组 20 → **80** | 要准备 60 个新名字 |
| 6 | `VillageLifecycleService.ResolveBirths` | 上限 `granaryCapacity / 10` → **独立常量 80** | 现在这个 50 是拿容量除以 10 得来的，没有道理 |
| 7 | `MapViewBinder.PlaceVillagers` | 改成遍历**托管列表**，不再用 `FindObjectsOfType` | ★ 见 §4 |
| 8 | `VillageUiController` 约 2815 行 | 同上，改遍历托管列表 | 同一处 `FindObjectsOfType<VillagerWalker>()` |

### 3.3 `patrolRange` 的重算公式

现在是 `(120, 36)`，对应间距 2 格。规律是

```
patrolRange.x ≈ 0.75 × (横向间距 px)
patrolRange.y ≈ 0.50 × (纵向间距 px)
```

代入间距 1 格

```
新的 patrolRange.x = 0.75 × TW
新的 patrolRange.y = 0.50 × TH
```

**巡逻范围必须小于间距，否则相邻两人的活动范围会互相盖住**，看起来像一坨。

## 4. 三个最容易漏的地方

### ★ 漏点一 · 强制草地菱形不放大，一半出生点会掉进水里

`VillageMapGenerator.Generate` 里有一段

```csharp
if (j >= 10 && j <= 37 && i >= 6 && i <= 25 && b == 0 && Math.Abs(j - 23) + Math.Abs(i - 15) <= 6)
    b = 2;   // 强制改成草地
```

那个半径 6 的菱形就是为**20 人的出生区**准备的。新的出生区是 x 19..28、y 12..19，四角的曼哈顿距离是

```
(19,12) → |19-23| + |12-15| = 4 + 3 = 7  >  6   ← 出界了
(28,19) → |28-23| + |19-15| = 5 + 4 = 9  >  6   ← 出界了
```

**不改半径，四角就会保持原本的地形**（可能是水或岩石），然后被 `FindNearestHabitable` 推到别的地方去。表现是**村子四角的村民散落在离群索居的位置**，看起来像撒豆子。

**改成半径 10。** 另外顺手确认一下外层的矩形 `j >= 10 && j <= 37 && i >= 6 && i <= 25` 能覆盖 x 19..28、y 12..19 —— 能覆盖，不用改。

### ★ 漏点二 · `FindObjectsOfType` 撑不住 80 个

现在有两处这样取村民

```csharp
VillagerWalker[] array = UnityEngine.Object.FindObjectsOfType<VillagerWalker>();
```

- `MapViewBinder.PlaceVillagers` 用它来摆位置
- `VillageUiController`（约 2815 行）用它来同步存活状态

**这两个函数都依赖场景里手摆的对象。** 80 个对象手摆、逐个填 `villagerIndex`（那是 `[SerializeField]`，手填的），不现实。

必须改成

```
从一个 prefab 运行时实例化 80 个
挂在 actorContent 下
用一个 List<VillagerWalker> 或数组托管起来
两个函数都改成遍历这个列表
```

顺带把 `VillagerWalker.EditorBind` 换成一个运行时版本（现在那个方法名带 Editor，是给编辑器用的）。

### ★ 漏点三 · 点击热区必须和视觉大小解耦

村民小了之后，`VillagerActorView` 的 `OnPointerClick` 还是靠 RectTransform 的射线检测。**如果热区跟着 sprite 一起缩小，就点不中了。**

正确做法是**视觉小、热区大**

```
visual（视觉）     缩小到约一半，关掉 Raycast Target
actorRoot（热区）  保持 TW × 0.9 × TH × 0.9，勾上 Raycast Target
```

**两个节点是分开的**，不要用同一个。

## 5. 验收标准

跑完之后逐条确认。

- [ ] 新开局有 **24** 个村民（起始），全部**在地图上看得见**
- [ ] 存读档往返一次，24 个人还在原位
- [ ] 跑满 2000 tick，人口能因为生育涨到 **30 以上**（现在最多涨到 30 就停了）
- [ ] 把法律调成"必死局"，人口逼近 **80** 时生育停止
- [ ] **随机点 10 次村民，10 次都点中想点的那个人**（在默认缩放下）
- [ ] 缩小后的村民**不重叠**成一片色块
- [ ] 村民的游荡范围**不超过半个间距**，看不出有人在"跨过邻居家"
- [ ] 手机端实测，帧率不掉（80 个 GameObject 对 Unity 不算多，但要确认）

## 6. 如果不满足条件，两个降级方案

### 方案 B · 非对称间距

只用横向的密度，竖向保持宽松。

```
横向间距 1 格，纵向间距 2 格   →  密度翻倍而不是翻四倍
10×8 的出生区  →  40 人
```

代价是上限只能到 40 而不是 80。**但如果 §1 测出来 `TH` 小于 50，这是唯一能保证点得中的做法。**

### 方案 C · 只缩人不降间距

只是把村民画小，让它"看起来不那么挤"，**上限不动**。

这解决的是观感，不是容量。如果时间不够，这是最保险的一档——**改一个 prefab，零代码，零风险。**

| 顺序 | 做什么 | 工时 | 风险 |
|---|---|---|---|
| 1 | **测量三个数**（§1） | 0.1 天 | 无 |
| 2 | 场景侧：缩小 visual + 加热区 | 0.2 天 | 低 |
| 3 | 改成运行时实例化 + 托管列表（§4 漏点二） | 0.5 天 | **中**，两个函数都要动 |
| 4 | 改出生网格 + 强制草地半径 | 0.2 天 | 低 |
| 5 | `patrolRange` 重算 | 0.1 天 | 低 |
| 6 | 名字补到 80 个 + 上限常量 | 0.2 天 | 低 |
| 7 | 按 §5 验收 | 0.3 天 | — |
| | **合计** | **≈1.6 天** | |

**第 3 步是唯一有风险的**，它动了两处 UI 的村民枚举方式。**先做它，做完单独测一次存读档和点击，再往下走。** 如果它出问题，前三步之外的都别做。

## 8. 一条不属于本方案但必须一起考虑的

**人口涨到 80 之后，讣告横幅会在大屠杀局面里连成一片。**

这跟人数上限是**两件独立的事**（触发它的是法律的恶劣程度，不是村子多大），但如果要上 80，建议同时做**讣告分层**

```
普通死亡  → 只进「讣告历史」列表，加一个红点，不弹横幅
异常死亡  → 弹横幅。判定例如：同 tick 死 3 人以上 / 死因直指某条法 / 死者是最年长或最年幼 / 死者子女数 ≥ 3
```

成本半天，和本方案互不依赖。
