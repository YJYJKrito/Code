## 1. ★ 个人存粮：先更正根因，再改一个条件 ★

### 1.1 《待办清单》P0-4 的根因描述是错的

> P0-4 原文：「`villagerFood` 只有 `--`，**没有任何 `++`**。全项目搜不到一处给它补货的代码」

**这句话不成立。** `VillageLifecycleService.AdvanceGranary` 里**有**补货代码：

```csharp
// Assembly-CSharp.decompiled.cs:5188 附近
data.granaryFood += num4 - num5;
data.granaryFood = Math.Max(0, Math.Min(data.granaryCapacity, data.granaryFood));

if (data.granaryFood <= population)      // ★ 闸门一
{
    return;                              //    整体跳过，连循环都不进
}
for (int j = 0; j < data.villagerAlive.Length; j++)
{
    if (data.granaryFood <= population)  // ★ 闸门二
    {
        break;
    }
    if (data.villagerAlive[j] && data.villagerFood[j] < 12)
    {
        data.villagerFood[j]++;          // ★ 唯一的 ++
        data.granaryFood--;
    }
}
```

**这个区别很重要**，因为它决定了修法：

| 如果根因是 | 修法 | 工时 |
|---|---|---|
| 没有补货代码（原描述） | 要**设计并写一整套**新来源 | 1 天以上 |
| **有补货代码但被条件挡住**（实际） | **改那个条件** | **半天以内** |

### 1.2 实测：确实挡住了，而且挡得很死

30 年 · 60 seed · 默认法（济贫/耕作/税收），逐村民逐刻统计：

| 指标 | 实测 |
|---|---|
| 个人存粮**最大值** | 37 |
| 个人存粮**均值** | **0.25** |
| 存粮 = 0 的村民·刻 | **77.0%** |
| 存粮 < 2 的村民·刻 | **95.1%** |
| 存粮 ≥ 12 的村民·刻 | **0.3%** |
| **粮仓 ≤ 人口 的刻占比** | **63.2%** |
| 30 年累计生育 | **20 人/局** |

**连锁反应**（和 P0-4 描述的一致，只是原因换了）：

```
粮仓 ≤ 人口（占 63.2% 的时间）
  → AdvanceGranary 整体 return
  → 个人存粮补不上去
  → 95.1% 的时间存粮 < 2
  → CanGiveBirth 要求 food >= 2  →  生育几乎停止（30 年只有 20 个新生儿）
  → ResolveInfantMortality 的 if (villagerFood[i] < 2) num2 += 2  →  长期恒真，失去区分度
```

**「20 个米缸」这个设计意图完全归零。**

### 1.3 改动（二选一）

**A（推荐，最小）**：把闸门条件放宽

```diff
- if (data.granaryFood <= population) { return; }
+ if (data.granaryFood <= 0) { return; }
```

循环内那道 `break` 同理改成 `<= 0`。**有粮就分，不要求「粮仓比人口多」。**

> ⚠️ **改完必须重新标定。** 个人存粮活过来会同时改生育率和幼儿夭折率，**很可能把《四项修正》标好的 30 年阶梯打乱**。

**B（更贴设计意图）**：把「分粮」改成按比例，而不是"粮仓宽裕才分"

```
每 60 tick，把当期净产出的一部分（比如 1/4）按人头分给存活村民，上限 40
存量部分留在公仓应付荒年
```

**A 和 B 都要做的**：把 `villagerFood[j] < 12` 这个上限重新审一遍——**12 对上「上限 40」的显示值，中间差得很远**（UI 卡面写的是 `存粮 N / 40`）。

### 1.4 验收

- [ ] 个人存粮**均值 ≥ 5**（现在 0.25）
- [ ] 存粮 < 2 的村民·刻 **降到 40% 以下**（现在 95.1%）
- [ ] **30 年累计生育 ≥ 40**（现在 20）
- [ ] 跑 2000 tick 之后**仍然能看到新生儿**（P0-4 原始判据）
- [ ] **重跑《四项修正》§3.2 的 30 年验收脚本**，确认好法/不作为的阶梯没被打破
- [ ] 确认没有落入 subsistence 陷阱（粮仓常年为 0 + 零生育 + 零饿死三件事同时出现）

## 2. ★ 解锁体系：三个改动 ★

### 2.1 先确认不要动的东西

解锁系统的**管线是完整且接好的**，一行都不用改：

| 件 | 状态 |
|---|---|
| `LawDefinition.hidden / unlockType / unlockThreshold / unlockHint / treasuryCost` | ✅ |
| `LawCatalog.IsUnlocked(save, law)` —— 9 种解锁类型 | ✅ |
| `BuildVisibleCatalog` —— 用 `IsUnlocked` 过滤 | ✅ |
| `SelectVisible` —— **完整扣款 + 写入 `purchasedLawIds`** | ✅ |
| UI 标签 `[隐藏]` / `[稀有]` + 状态文案 | ✅ |

> **特别注意**：`treasuryCost`（稀有法的税库金币购买）**是接好的**，`SelectVisible` 确实扣 `treasuryGold`。
> 我之前在模拟层里说它"零调用点"——**那是错的，模拟层不含 UI**。**不要重复劳动去"实现"它。**

### 2.2 改动一：解锁条件提前可见 ★ 最重要 ★

**病灶**

```csharp
// LawSelectionController.BuildVisibleCatalog
if (!lawDefinition.hidden || LawCatalog.IsUnlocked(save, lawDefinition))
    array[num++] = i;          // ★ 没解锁的直接不进列表
```

```csharp
// LawSelectionController 状态文案（只有已经解锁了才会走到这一句）
text3 = lawDefinition.hidden ? ("已满足隐藏条件：" + lawDefinition.unlockHint) : "可选择";
```

**玩家在法律面板里看不到任何未解锁的隐藏法。** 而 `unlockHint` 只在解锁**之后**才显示，用的还是过去式「已满足」。

> **一个不告诉玩家解锁条件的解锁系统，不是目标系统，是随机器。**
> 玩家无法瞄准任何东西——他连那条法存在都不知道。

**改动**

**`BuildVisibleCatalog` 不再过滤，返回全部 70 条。** 未解锁的走「灰锁」分支：

```csharp
// 新增：判断锁没锁
bool locked = lawDefinition.hidden && !LawCatalog.IsUnlocked(currentSave, lawDefinition);
lawOptionView.button.interactable = !locked && !flag && (flag2 | flag3);
```

**状态文案要给出进度，不是只给条件**。`unlockHint` 是静态字符串（"累计死亡 5 人后解锁"），**要能算出「当前 2」**：

```csharp
// 在 LawCatalog 里加一个方法，返回 (当前值, 阈值)
public static (int cur, int need) UnlockProgress(VillageSaveData save, LawDefinition law)
{
    return law.unlockType switch
    {
        1 => (save.totalDeaths,                     law.unlockThreshold),
        2 => (save.totalBirths,                     law.unlockThreshold),
        3 => (CountAlive(save),                     law.unlockThreshold),
        4 => (save.granaryFood,                     law.unlockThreshold),
        5 => (save.treasuryGold,                    law.unlockThreshold),
        6 => (CountInfantDeaths(save),              law.unlockThreshold),
        7 => (CountFearAbove(save, 80),             law.unlockThreshold),
        8 => (CountGoldBelow(save, 10),             law.unlockThreshold),
        _ => (0, 0),
    };
}
```

文案：

```
未解锁   「🔒 需要：累计死亡 5 人（当前 2）」
已解锁   「✅ 已解锁」
普通法   「可选择」
```

**为什么这条最值钱**：它把一个**随机器**变成一个**目标系统**。这是「增强法条之间的联动性」这件事上现有体系唯一真正的缺口。

**工时**：约 **0.3 天**（`BuildVisibleCatalog` 1 行 + 灰锁分支 + `UnlockProgress` + 文案）。

### 2.3 改动二：解锁率的分布确认（**不需要改，但要知道**）

我原本以为 `#22 瘟疫隔离` / `#64 刑戮` 是"锁死的"，**测错了**——我第一次只测了默认法组（济贫/耕作/税收），而**那组里一条加恐惧的法都没有**，恐惧只降不升。

换成恐惧系玩法后：

| 律法组合 | 个体恐惧最大值 | #22 解锁率 | #64 解锁率 |
|---|---|---|---|
| 默认 济贫/耕作/税收 | 53 | **0%** | **0%** |
| **恐惧系 恐惧蔓延/私刑/连坐/诛心** | **99** | **70%** | **70%** |
| 不作为（空） | 53 | 0% | 0% |

**结论：这两条法不是死的，它们专门为恐惧系玩法准备。这是对的设计，不要改。**

**但值得知道的是解锁率整体分布很不均匀**（30 年 · 200 seed）：

| 律法组合 | 第 0 年可见 | 第 1 年 | 第 10 年 | 第 20 年 |
|---|---|---|---|---|
| 默认 | 57 | **65** | 65 | 65 |
| 恐惧系（大多数局会灭村） | 57 | 65 | 65 | 65 |
| 不作为 | 57 | **63** | 65 | 65 |

**无论怎么玩，20 年只多出 8 条法，其中 6 条在第一年之前。** 所以「隐藏法」提供的**递进感几乎没有**——这是设计意图层面的问题，不是 bug。改不改都行，**但如果想要递进，得改解锁阈值，不是改管线**。

### 2.4 改动三：给解锁法补载荷

**病灶（实测）**：15 条解锁法（13 隐藏 + 2 稀有），把每条加进基准（济贫+耕作+税收 = 20.4 人）看 30 年位移：

| id | 法名 | Δ存活 | | id | 法名 | Δ存活 |
|---|---|---|---|---|---|---|
| **60** | **哭丧** | **−18.99** | ✅ | 21 | 长老议事 | −0.01 |
| **62** | **阴气** | **−10.03** | ✅ | 22 | 瘟疫隔离 | −0.01 |
| 23 | 互助会 | −0.83 | ❌ | 63 | 香火 | +0.07 |
| **24** | **王权税契**（**买 60 金**） | **−0.04** | ❌ | 64 | 刑戮 | −0.01 |
| **25** | **雇佣护卫**（**买 40 金**） | **0.00** | ❌ | 65 | 夭殇 | +0.18 |
| 17 | 流民法 | +0.06 | ❌ | 18 | 起义豁免 | −0.01 |
| 19 | 安葬礼法 | 0.00 | ❌ | 20 | 丰年祭 | −0.01 |
| 61 | 厚葬 | +0.02 | ❌ | | | |

```
15 条解锁法
  ✅ 承重        2 条（#60 哭丧 · #62 阴气）—— 而且两条都是纯负反馈
  ❌ 零载荷     13 条
```

**两句话：**

1. **解锁系统的产出里，没有一个「奖励」是好的。** 唯一有载荷的两条是惩罚（哭丧 = 有人死→全村恐惧+4；阴气 = 累计死亡≥20→全村恐惧+1、粮仓−1）。
2. **稀有法在花钱买空气。** **60 税库金币（约等于开局家底的 1.5 倍）买一个 Δ = −0.04 的法。** 这条最伤——玩家付出了真实的资源，得到的是噪声。

**改动**：**并入 §3 的「补载荷」一起做，不要单独处理。** 但两件事要单独决：

- [ ] **#24 王权税契 / #25 雇佣护卫：要么给它们载荷，要么把 `treasuryCost` 降下来，要么下架。** 花钱买零载荷是最坏的一种。
- [ ] **#60 哭丧 / #62 阴气：保留。** 它们有载荷、有主题（`他们死于你写的法律`），是好的恶法。**它们的问题不在自己，在于解锁它们的玩家以为会得到奖励。**

## 3. 顺带记录（不改，但要知道）

### 3.1 扩槽到 7 时必踩：`lawNames` 不会跟着扩容

```csharp
// VillageLifecycleService.EnsureRuntimeArrays
int num = (data.lawIds != null) ? data.lawIds.Length : 5;
// 按 num 补齐了 lawStrength  ✅
// 按 num 补齐了 lawCooldown ✅
// ★ 没有补 lawNames ★
```

`lawNames` 声明是 `new string[5]`，**没有任何地方 resize 它**。

所以如果哪天把 `lawIds` 改成 `int[7]`：`lawStrength`/`lawCooldown` 会**自动**补齐到 7，**`lawNames` 停在 5，第 6、7 槽没有名字**。UI 不崩（有边界检查），但显示空白。

**改的时候把 `lawNames` 一起加进 `EnsureRuntimeArrays`，并确认旧存档能升到 7。**

### 3.2 「用终局人数衡量联动性」是错的

我自己踩了一次：用「30 年终局存活人口」的 |Δ| 中位数去测前置树有没有提高交互性，**测不出来**。

```
把目录瘦成「只有 9 条承重法」（承重密度 100%）：
  换法 |Δ| 中位  0.50   ← 比 57 条混合目录的 1.12 还低
```

**因为终局人数是个饱和标量**：被人口上限夹住，只看得见向下位移、看不见向上和结构差异；**它分不清「同为 20 人，一局饥荒死一半、一局全是老死」**；而交互效应是个标量在数学上就看不见。

**以后测联动性用向量**：人年数（`∫存活dt`）、死因占比单纯形、生育/死亡时点分布。

### 3.3 ★ 测试台有间歇性内存损坏 ★

同一份二进制、同样的输入，出现过两种异常：

1. **`VillageTime.ToDate` 抛 NullReferenceException**（在一个确定性的、跑过几百次的代码路径上）
2. **同一个 seed 得出了不同结果**（`#62 阴气` 解锁率一次 46%、一次 88%）

**已确认不是并发进程导致**（跑的时候只有一个 simtest 进程）。**重跑三次结果完全一致**，所以是**偶发的进程级损坏**。

**对程序的要求**：**任何一次跑出异常数字，都要重跑确认**，不要拿单次结果当依据。我自己已经作废了一次读数。

## 4. 不要做的两件事

### 4.1 ❌ 法槽改为「开局 4 格 / 每 20 年 +1 / 上限 7」

实测（60 年 · 100 seed · 善政 7 条链）：

| 开局槽数 | 每 10 年一格 | 每 20 年一格 | **永不开新格** |
|---|---|---|---|
| 开局 3 格 | 4.7 | 4.5 | **3.9** |
| 开局 4 格 | 5.0 | 4.9 | **4.9** |
| 开局 5 格 | 9.5 | 11.2 | **11.3** |
| **开局 6 格** | 20.2 | 20.9 | **22.2** ← 最优 |
| 开局 7 格（全装） | 10.1 | 10.1 | **10.1** |

**开局 6 格是基准（7 条全装）的 2.2 倍；开局 4 格只有 5.0，不到四分之一。** 而第 7 格是**净负**（威信维持费 2/法/60tick 养不起）。

**另外**：时间锁和威信锁几乎完全重合（人口 24 养 3 条 / 40 养 5 / 56 养 7），是**同一堵墙撞两次**；而且时间锁专门惩罚善政（善政满配 −6.7 人，因为增益法靠复利生效）。

**结论**：槽位保持现状（5 格平铺）不动。**要动的话只有一种动法有数据支持——开局给到 6、上限 6。**

### 4.2 ❌ 法条前置树

43 条前置边，**只有 2 条**把装饰法变成了「必经之路」（`#11劳役→#41丁役`、`#27丁税→#53丁税宏观`），**34 条法仍然是叶子**。

**根因**：70 条法里只有 **11 条有载荷（16%）**。在空目录上挂边，挂出来的必然是空边。

**推迟，不是否定。** 等承重法从 11 条长到 25 条以上再重估。**树本身已经建好并自检通过**（见设计文档附录），到时候直接用。
