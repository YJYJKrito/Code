# 词条系统设计 · 先天与烙记

> **要的东西**：村民从一出生就带词条，而且这些词条**不和后期产生的打架**。
>
> **现状**：`VillageSaveData` 里没有词条系统（只有 11 个村民数组）。这是从零设计。

---

## 0. 核心答案。不靠规则防冲突，靠职责分离

大多数人想到"不冲突"会去做**位图分区**——低 8 位存先天、中 8 位存后天、高 8 位存临时。那能防住"位被占用"，防不住别的。

**真正干净的做法是让三类词条各自待在不同的地方，连"可能冲突"这个前提都不成立。**

| 类别 | 它定义什么 | 存在哪 | 怎么产生 |
|---|---|---|---|
| **先天** | 他是一个**什么样的人** | 一个并行数组 | 生成时写入，**之后永不改变** |
| **烙记** | 他**经历过什么** | 另一个并行数组 | 律法或事件写入，可永久可清除 |
| **状态** | 他**现在是什么情况** | **不存储** | 每次要用时从当前值算出来 |

三类各自的职责是分开的。

- **先天调制参数**（产粮多少、恐惧基线多高、生育概率多大）
- **烙记充当判定条件**（"有罪人标记的""无嗣的"）
- **状态是实时读数**（"现在饿着的"）

**作用方向不同、存储位置不同、生命周期不同，所以它们不可能冲突。**

### 状态类不存储，这一条单独说

"饥民""惊恐""赤贫"这类，**根本不要写进数组**。

```
饥民  =  villagerHunger[i] > 70
惊恐  =  villagerFear[i] > 70
赤贫  =  villagerGold[i] < 10
```

它们是**纯函数**。不存，就不可能和任何东西冲突——**这一刀直接砍掉了一整类冲突**。

而且它们永远和当前状态一致。如果存下来，你还得处理"这个人不饿了，饥民标记什么时候去掉"这种问题。不存就没这个问题。

---

## 1. 存储方案

现有的村民数据是**一组并行数组**（`villagerGold[]`、`villagerHunger[]`……）。加词条要顺着这个模式走，不要另立一套。

```csharp
// 【先天】生成时写入，之后全项目禁止再写
//   bit 0..15   8 条互斥轴 × 2
public uint[] villagerInnate = new uint[0];

// 【烙记】律法 / 事件写入
//   bit 0..15   永久烙记（不可清除）
//   bit 16..29  可清除烙记
//   bit 30..31  预留
public uint[] villagerMarks = new uint[0];
```

> **位宽从 `ushort` 改成了 `uint`。** 第一版按 8 个先天 + 16 个烙记设计，`ushort` 够用；词条表扩到 **62 条**之后装不下了（烙记就要 30 位）。
> 具体每条词条占哪一位，见 `词条表.md`。

两个数组，**物理隔离**。先天那一份，代码里只有一个地方会写它——生成函数。**这是最彻底的防冲突。**

### 加进现有流程的三处

| 位置 | 做什么 |
|---|---|
| `VillageSaveData` | 加两个字段，`version` 4 → 5 |
| `VillageLifecycleService.EnsureLifecycleArrays` | 两个新数组过一遍 `EnsureLength` |
| `VillageSaveService.Normalize` | 两个新数组跟着做长度同步 |

**漏掉后两处的话**，读旧档时两个数组会是空的，所有村民都没有先天词条——**而且不报错**。

## 2. 先天词条

### 2.1 表

四条互斥轴，每条两个方向。每个村民抽 **1–2 个**（从不同的轴抽）。

| 轴 | 词条 | 效果 | 对应字段 |
|---|---|---|---|
| **胆量** | 怯懦 | 恐惧基线 +20 | 影响 `fear` 的自然衰减速度 |
| | 果决 | 恐惧基线 −20 | 同上 |
| **物欲** | 贪婪 | 攒钱更快，但金币会招来法条 | 影响 `gold` 的回复 |
| | 慷慨 | 会把自己的钱分给穷人 | 影响 `gold` 的转移 |
| **体力** | 勤勉 | 产粮多、吃得省 | 影响粮仓产出与饥饿增速 |
| | 懒散 | 产粮少 | 同上，反向 |
| **体质** | 病弱 | 饿得快、夭折率高 | 影响饥饿增速与夭折判定 |
| | 强健 | 饿得慢、夭折率低 | 同上，反向 |

**8 个词条，四条互斥轴。** 抽的时候按轴抽——**同一轴最多抽一个**，这一条保证了先天内部不会自相矛盾。

### 2.2 互斥是"轴"属性，不是"词条"属性

不要去写"怯懦和果决互斥"这种两两规则。**按轴组织，同轴只能有一个**，规则就只有一条。

以后加轴（比如"智愚"）不用改任何判定逻辑。

### 2.3 先天词条从父母继承 ★ 免费换来家族叙事

`AppendChild(data, mother, father)` **已经拿到了父母的下标**。新生儿的先天词条按这个抽

```
第一个词条
    40% 从母亲的先天里继承
    40% 从父亲的先天里继承
    20% 完全随机
第二个词条
    从与第一个不同的轴上随机抽
```

**代价几乎为零，换来的是"某某家世代怯懦"这种跨代的叙事。**

玩家会自己发现："怎么又是他们家出事？"——**而这是他发现的，不是我们写的。** 这正是这个游戏要的东西。

配 `恤寡` `绝户` `光棍` 那几条法，一个家族连续三代绝嗣的故事会自己长出来。

### 2.4 先天词条不可被后天改写

**这是"不冲突"的核心保证。**

规则只有一条

> **先天那一份数组，除了生成函数，全项目任何地方都不许写。**

如果一个后天效果想"让人变懒"，做法是**加一个烙记**，而不是去改先天位。比如

```
先天：勤勉
后天：烙「荒废」（因为长期饥荒）
效果：实际产粮 = 勤勉加成 + 荒废惩罚   ← 两者相加，不覆盖
```

**先天永远是"他本来的样子"，后天永远是"他后来遇到的事"。** 讣告于是能写出这样的句子

> 他本来是个勤快人。荒年之后，他不再下地了。

**如果让后天覆盖先天，这句就写不出来了**，因为原始值没了。

## 3. 烙记

### 3.1 位分配

```
bit 0..7    永久烙记 —— 一旦写上，任何手段都抹不掉
bit 8..15   可清除烙记 —— 律法可以清除
```

`RemoveMark(mark)` 只允许清 `bit 8..15`。**永久位要免疫**——这条约束写在一个函数里，别散在各处。

> **为什么必须有永久位。**
> 「废掉一条法律是止血，不是撤销。」已经发生的事要一直留在人身上。
> 没有永久位的话，玩家废掉法条就相当于把人治好了，那这个游戏最重要的那层沉重感就没了。

### 3.2 永久烙记（bit 0..7）

| 位 | 名字 | 谁写它 | 作为条件被谁读 |
|---|---|---|---|
| 0 | **罪人** | `私刑倾向`、`连坐` | `私刑` 类法条 |
| 1 | **劫匪** | 抢过别人（`饥则抢` / `阋墙`） | 再犯判定 |
| 2 | **逃兵** | 恐惧极高时逃走 | 劳役类法条 |
| 3 | **绝户** | 无子女且年龄 ≥ 50 | `绝户` 法 |
| 4 | **守寡** | 女 / 有子女 / 高龄 / 长期饥饿 | `恤寡` 法 |
| 5 | **光棍** | 男 / 无子女 / 年龄 ≥ 25 | `光棍` 法 |
| 6 | **债户** | `借粮` 类法 | `追债` 类法 |
| 7 | **徙民** | 从外村迁来的 | `流民法` |

### 3.3 可清除烙记（bit 8..15）

| 位 | 名字 | 谁写 | 谁清除 |
|---|---|---|---|
| 8 | **赦免** | 赦令类法 | 到期自动 |
| 9 | **隔离** | `瘟疫隔离` | 恐怖下降后 |
| 10 | **服劳役** | `劳役` / `丁役` | 停止劳役后 |
| 11 | **免税** | `缓征` | 税库回满后 |
| 12–15 | 预留 | — | — |

### 3.4 烙记的写入必须集中

**不要在每个法条里直接 `|=` 位。** 写一个函数

```csharp
static void AddMark(VillageSaveData d, int i, int bit)      // 只加，不判重
static void RemoveMark(VillageSaveData d, int i, int bit)   // 只清可清除位
static bool HasMark(VillageSaveData d, int i, int bit)
```

**理由**：以后要加"这个烙记会广播给邻居""这个烙记会降低生育率"，只需要改一处。

## 4. 状态类，不存储

| 名字 | 推导式 |
|---|---|
| 饥民 | `villagerHunger[i] > 70` |
| 惊恐 | `villagerFear[i] > 70` |
| 赤贫 | `villagerGold[i] < 10` |
| 富户 | `villagerGold[i] > 60` |
| 幼儿 | `villagerAges[i] < 3` |
| 老人 | `villagerAges[i] >= 65` |
| 待产 | `villagerBirthCooldown[i] > 0` |

**这些现在已经在 `VillagerStatusPanelController.BuildAliveTags` 里算着了。** 要做的是**把它从 UI 层提到一个公共函数**，让法条条件也能读。

```csharp
// Sim 层
public static bool IsStarving(VillageSaveData d, int i) => d.villagerHunger[i] > 70;
// UI 层和法条层都调它
```

**一处定义，两处使用。** 现在 UI 里那份是内联的 if，法条那边读不到——所以「饥民」这个状态现在只有玩家看得到，法条看不到。提出来之后，一条"给饥民发粮"的法就写得出来了。

## 5. 冲突的五个来源，以及各自的解法

| 冲突 | 解法 |
|---|---|
| **存储位被占用** | 两个独立数组，物理隔离 |
| **同轴语义矛盾**（又怯懦又果决） | 互斥轴：同轴最多一个，生成时保证 |
| **后天覆盖先天**（勤勉变成懒散） | **禁止**。后天不写先天数组，改为加烙记，两者效果**相加** |
| **烙记被清掉了不该清的** | 位分区：`bit 0..7` 永久，`RemoveMark` 只碰 `bit 8..15` |
| **状态类过期** | 状态类**不存储**，用时重算，不存在过期 |

**五种冲突，五种不同的解法，但它们都指向同一个原则——不同职责的东西不要放在同一个地方。**

## 6. 词条怎么接进玩法

### 6.1 先天接参数

先天词条作用于**每个村民的物理参数**，类似设计文档里的"性格调制动力学"

```csharp
// AdvanceNeeds 里，按村民取一次
int hungerRate = 1;                               // 基础每 tick 饥饿增量
if (HasInnate(d, i, Innate.Sickly))  hungerRate += 1;
if (HasInnate(d, i, Innate.Robust))  hungerRate -= 1;
if (HasInnate(d, i, Innate.Diligent)) hungerRate -= 1;
// …
```

**这是异质性的来源。** 没有它，二十个人在同样的法律下死法完全一样，故事就没有主角。

### 6.2 烙记接条件

烙记是**法条条件的读取目标**。前面 `法条扩展-实现方案` 里的 `CondKind` 要加两个

```
HasInnate(bit)     自身先天里有没有某位
HasMark(bit)       自身烙记里有没有某位
```

有了它们，`私刑倾向`（有罪人者）、`绝户`、`光棍`、`恤寡` 这些法才有条件可读。

### 6.3 状态接条件

状态类也各加一个条件原语，或者**直接复用数值比较**（`SelfGt(Hunger, 70)` 就是饥民）。**优先复用**，不要为每个状态造一个原语。

## 7. 实现顺序与工时

| 顺序 | 做什么 | 工时 | 验收 |
|---|---|---|---|
| 1 | 两个数组 + 存档字段 + `version` 5 + `EnsureLength`/`Normalize` | 0.2 天 | 旧档能读，新档能存 |
| 2 | 先天词条的生成（互斥轴抽取） | 0.2 天 | 每人 1–2 个，无同轴冲突 |
| 3 | 父母继承 | 0.1 天 | 连开 10 局，能看到"某家世世代代同一个脾气" |
| 4 | 先天接参数调制 | 0.2 天 | 同 seed 下不同先天的人饿的速度不一样 |
| 5 | `AddMark` / `RemoveMark` / `HasMark` + 位分区 | 0.1 天 | 永久位清不掉 |
| 6 | 状态类提取成公共函数，UI 改为调它 | 0.1 天 | UI 显示不变 |
| 7 | 面板显示词条 | 0.1 天 | 点人能看到先天 + 烙记 + 状态 |
| | **合计** | **≈1 天** | |

**第 5 步单独列出来，是因为它是"不冲突"的技术保证。** 位分区写错的话，永久烙记会被清掉，而**这件事不会报错**，只会在某一天你发现"废掉法条之后人就好了"。

## 8. 验收

- [ ] 新开局，**每个村民**都有 1–2 个先天词条
- [ ] 连开 20 局，**不存在任何一个村民同时有两个同轴词条**
- [ ] 存读档往返，先天词条一个不少
- [ ] **读旧版本存档不会崩**（先天数组为空，村民没有先天词条，但不报错）
- [ ] 写一个永久烙记，调 `RemoveMark`，**抹不掉**
- [ ] 写一个可清除烙记，`RemoveMark` 能抹掉
- [ ] 同一个 seed 下，先天词条的分布**完全一致**（用 `Rng` 的专属 channel 抽）
- [ ] 面板点人能看到全部三类词条

### 一条必须做的自检

加一个开发期断言

```
除了生成函数，全项目不许出现对 villagerInnate 的写入
```

做法可以用一个 `readonly` 的包装（写入走一个只在生成期开放的方法），或者一条 grep 式的源码检查。**这条断言是"先天不被后天污染"的唯一保证。**

## 9. 两个可选加深（有余力再做）

### 9.1 烙记的视觉化

有永久烙记的村民，在地图上**换一个颜色描边**。

- 罪人 → 朱红
- 劫户 → 深灰
- 守寡 → 素白

**成本极低**（改一个 `Image.color`），但玩家一眼就能看出"村里有几个被标记的人"。**这是把隐藏状态变成可见信息的最便宜做法。**

### 9.2 讣告里引用先天词条

讣告现在只有三行（名字 / 死因 / 第几条法）。加上先天之后可以写

> 他本来是个勤快人。荒年之后，他不再下地了。
> ——他死于你写的第三条法。

**这是"先天 + 后天 + 死因"三者在文本上的汇合，也是这个词条系统最终要服务的东西。**

---

## 10. 一句话

> **不让先天和后天冲突的办法，不是写规则去挡，是让它们从不相遇。**
>
> 先天定义"他是什么样的人"，烙记定义"他经历过什么"，状态定义"他现在什么情况"。
> **三样东西存在三个地方、干三件事、活三个生命周期——冲突的前提就不成立。**
