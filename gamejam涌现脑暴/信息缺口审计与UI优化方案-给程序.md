> **方法**：把 `testgame` 里的 `Assembly-CSharp.dll` 反编译出来，逐个字段比对「模拟层追踪了什么」和「UI 显示了什么」。

## 0. 一句话 + 一个必须先做的前置

**游戏追踪 40 多个状态量，HUD 常驻显示其中 4 个。差集里有三样是会直接卡住玩法的。**

> ⚠️ **但先做《四项修正》的产出一行（`population * 2` → `120%`）。**
>
> ```
> 当前构建：int num4 = population * 2 + val;     ← 净产出是人口的 1.67 倍
> → 粮仓每 60 tick 顶死在上限 500
> → 此时加"粮仓 N / 500"，显示的是一个永远不变的 500
> ```
>
> **不修产出就加粮仓显示 = 加了个装饰品。** 顺序不能反。

## 3. 逐条分析

### ★ P0-1 · 公共粮仓存量 ★

**病灶**：`granaryFood` 在整个 UI 层**一次都没被读过**。所有读取都在模拟层。

**为什么这是第一位**：粮仓是**全项目唯一真正会动的寄存器**。

《可玩性阻塞清单》§1.3 测过一局内的动态范围：

```
金币    46 → 0，然后永远是 0        ← 后半程静止
饥饿    0 — 23                      ← 够不到危险线 99
恐惧    8 — 27                      ← 够不到危险线 99
粮仓    0 — 475                     ← ★ 唯一有大起伏的
```

**HUD 上四个数字，三个是钉死的，唯一会动的那个看不见。**

**改动**

```csharp
// VillageUiController —— 跟另外三个 summary 同构
granarySummary.text = "粮仓  " + save.granaryFood + " / " + save.granaryCapacity;
```

**工时 0.05 天。**

> ★ **V3 之后这条从"该有"变成"必须有"。** 《开垦》法的触发条件是 **`粮仓 < 150`**——玩家看不到这个数，就无法理解为什么田突然不扩了。

### ★ P0-2 · 每条法杀了几个人 ★

**病灶**：`obituaryLawIndices[]` **这个数组存在**（每条讣告记了死于第几条法），但 UI 只在**翻单条讣告时**用一次，**没有任何聚合**。

**为什么这是最重要的缺口**：这个游戏叫《立法村》，标语是 **「他们死于你写的法律」**。玩家最想问的问题就是：

> **"我写的哪条法最致命？"**

**数据一直都在。** 玩家只能一条条翻几十上百条讣告自己数。

**改动**：在法槽卡上直接写。

```
第 1 条  济贫
  触发：饥饿 > 45    效果：从公共粮仓取粮
  致死 12 人                                    ← 新增
```

实现：遍历 `obituaryLawIndices[]`，按 slot 计数，每帧或每 N 帧重算一次（讣告数 ≤ 几百，一次扫描是微秒级）。

**工时 0.15 天。**

> **这一条是投入产出比最高的。** 它不引入任何新数据，只是把已有的数据摆到玩家眼前——**而且它正好回答游戏标题那句话**。

### ★ P0-3 · 产出 / 消耗的净额 ★

**病灶**：`AdvanceGranary` 里的 `num4`（产出）和 `num5`（消耗）是**局部变量**，算完就丢。模拟层没有任何地方存过它们。

**为什么需要**：光有"粮仓 186"这个数字，玩家回答不了**"我为什么在变穷"**。

**改动**：先让它出得来，再显示。

```csharp
// VillageSaveData —— 加两个字段
public int lastProduction;
public int lastConsumption;

// AdvanceGranary 结尾
data.lastProduction  = num4;
data.lastConsumption = num5;
```

```csharp
// HUD
net = save.lastProduction - save.lastConsumption;
granarySummary.text = $"粮仓  {save.granaryFood} / {save.granaryCapacity}   ({net:+#;-#;0} / 刻)";
```

**工时 0.15 天**（模拟层 3 行 + UI 1 行）。

> ⚠️ **刷新频率要注意。** `AdvanceGranary` 每 **60 tick** 结算一次，而 60 tick ≈ **0.45 真实秒**。直接显示会跳。两个选择：
> - 按结算周期刷新（**推荐**，天然平滑）
> - 或者对净额做一次指数平滑
>
> **不要每帧重算**——那个数在两次结算之间是不变的，每帧算只是浪费。

### P1-1 · 威信的收支

**病灶**：威信会被 **6 条法**改动（捐纳 +3、王权税契 +2、立威 +3、威望 −2、威权 −5、赦令 −10），**但 HUD 只显示当前值**，看不出"这一步为什么变了"。

**为什么需要**：玩家装上「威权」之后看到威信从 120 掉到 115，**他不知道是谁干的**——因为「威权」的卡面写的是"以威信换财政"，没写数字。

**改动**：加"本刻威信变化"。

```
威信  177   (−5 / 刻)
```

实现：和产出一样，在 `SimulateTick` 里记 `prestigeBefore`，末尾写 `data.lastPrestigeDelta`。

**工时 0.15 天。**

> **如果《四项修正》的威信维持费落地了，这一条的价值会翻几倍**——那时威信每刻都在掉，玩家必须能看到收支才能玩。

### P1-2 · 人口的生死流

**病灶**：`totalBirths` 和 `totalDeaths` **两个字段都存在，但 UI 一次都没读过**。

**为什么需要**：HUD 只有"人口 24"一个**静态快照**。玩家看不出这个 24 是**刚从 35 掉下来的**还是**刚从 12 涨上来的**——而这两件事的含义完全相反。

**改动**

```
人口  24   (生 18 · 死 9)
```

**工时 0.05 天。**

> 这一条特别便宜（两个字段现成），而且**它把"人口"从一个名词变成了一个动词。**

### P1-3 · 村民的整体状况

**病灶**：饥饿和恐惧**只能一个个点开村民看**。20–60 个村民，看不出整体。

**为什么需要**：这两个是**危险表**（到 99 就死）。《可玩性阻塞清单》§1.3 说它们一局内只到 23 和 27——**玩家永远不知道"快到线了没有"**。

**改动**（二选一）

```
A：平均值        饥饿均值 12 · 恐惧均值 19
B：最危险的几个   最饿：王五 34 · 赵六 29 · 孙七 27
```

**推荐 B。** 平均值会被大量低值冲淡，而**这个游戏关心的是"谁快要死了"**——指出具体的人，比一个平均数有用得多。

**工时 0.1 天。**

```

**它应该回答"村子现在处于什么状态"，而不是"程序在干什么"。**

## 4. 一个统一的界面提案

**不要把这些散在各处加。** 现在 HUD 已经有 4 个 summary，再加 6 个会挤爆。

**建议改成两块：**

```
┌─ 村庄 ─────────────────────────┐   ┌─ 律法 ─────────────────────┐
│ 人口   24 / 80   (生 18 · 死 9) │   │ 第 1 条  济贫              │
│ 粮仓   186 / 500  (+22 / 刻)    │   │   致死 12 人               │
│ 税库   120                      │   │ 第 2 条  耕作              │
│ 威信   177        (−5 / 刻)     │   │   致死  3 人               │
│ 讣告   7                        │   │ 第 3 条  空置              │
│                                │   │   致死  —                  │
│ 最饿：王五 34 · 赵六 29         │   │                            │
└────────────────────────────────┘   └────────────────────────────┘
```

**左边的四行都是"存量 + 流向"**，右边的核心是**致死数**。

**这个布局直接的收益**：玩家扫一眼就能回答三个问题——**村子在变好还是变坏、哪条法在杀人、我下一步该改什么。**

## 5. 两个实现约束

### 5.1 刷新频率：不要每帧重算

| 量 | 天然刷新周期 | 怎么处理 |
|---|---|---|
| 粮仓 / 人口 / 税库 / 威信 | 每 tick 都可能变 | 每帧读字段（O(1)，无所谓）|
| **产出 / 消耗净额** | **每 60 tick 结算** | **按结算周期刷新**，否则会跳 |
| **致死数** | 只在有人死时变 | **惰性重算**：`obituaryCount` 变了才重扫 |

> **致死数的重算成本**：讣告最多几百条，一次全扫是微秒级。但**每帧扫几百条没必要**——记一个 `_lastObituaryCount`，只在它变化时重算。

### 5.2 确定性：这些**全部**不进哈希

**这一节所有新增量都是纯展示的派生量。** 一个都不能进 `HashState`、不能进存档。

```
lastProduction / lastConsumption / lastPrestigeDelta
致死数统计
最饿的几个
```

> ⚠️ **`lastProduction` / `lastConsumption` 有个陷阱。** 它们虽然是派生量，但**读档后必须是 0 或重算**——不能期望存档里有一份。
> 更稳的做法：**干脆不存，读档后第一次 `AdvanceGranary` 就会重新填上。**
