# P0 · 现在就能感觉到的"坏了"（3 项，约 2 人天）

这三项的共同点：**玩家已经能看到了，而且会直接觉得"这游戏坏了"。**

## P0-1 · 威信是个空数字

| | |
|---|---|
| **现象** | HUD 上显示"威信 100"，从开局到结束**永远是 100** |
| **位置** | `VillageSaveData.prestige`（字段）；全项目只有 4 处引用，全是**读**：初始化、读档 Clamp、拷贝给存档列表、显示 |
| **为什么是问题** | 设计里这是**唯一直接回答"玩家贴完法之后没事做"的机制**。没有它，玩家的循环是：贴 3 条法 → 看数字 → 没有第 4 步 |
| **最小做法** | 见下 |
| **验收** | 见下 |

### 最小做法（不要一次做全套）

```
① 立法消耗      ：贴一条法 prestige -= 30
② 维持费        ：每 60 tick，prestige -= 5 × 当前活跃法数
③ 威信回复      ：每 60 tick，prestige += 存活人数 / 3
④ 归零停摆      ：prestige <= 0 时，所有法暂停生效，直到 prestige >= 40
⑤ HUD           ：顶栏显示"威信 62 ▾ 3/分"（数字 + 净速率）
```

**⑤ 是重点。** 玩家必须能看见"我现在是亏的还是赚的"，否则前四条白做。

### 验收

- 贴满 5 条法，威信应该在 **600–900 tick 内归零**（现在永远不会）
- 归零后 HUD 有明确的停摆提示，且法确实不生效
- 回复到 40 之后法恢复生效

### ⚠️ 不要做

- **不要**做成"消耗型资源"（只减不回）——那样玩家会不敢立法，游戏变成攒钱
- **不要**加冷却时间、审议延迟这些，第一版只要上面 5 条

| | |
|---|---|
| **现象** | 律法选择界面里 25 条法都有卡面文字，但**其中 15 条选中后什么都不发生** |
| **位置** | `LawCatalog.Definitions`（25 条）；实际有行为的只有 10 条 |
| **为什么是问题** | **这比 bug 更糟，是当面骗玩家。** 玩家选「饥则抢」，卡面写着"饥饿 > 55 → 抢邻居 12 金币"，然后村庄毫无变化——他不会觉得是 bug，他会觉得这游戏是半成品 |

### 有效 / 无效清单

**二选一，逐条决定，不许留着不动：**

- **要么把它从 `LawCatalog.Definitions` 里删掉**，或者加一个 `implemented = false` 标记，让 UI **不显示**它

> **不允许的状态是：卡面写着效果，代码里没有。** 那是在骗玩家。

| 14 | 盐铁专卖 | `treasuryGold` 回复加快、`villagerGold` 增长变慢 |
| 15 | 兵役征召 | 成年男性 `fear -= 1`，`ResolveBirths` 概率下降 |

| 19 | 安葬礼法 | 读 `obituaryInfants` 累计数，够则全村 `fear -= 2` |
| 20 | 丰年祭 | `granaryFood > 300` → 生育概率 +30 |
| 22 | 瘟疫隔离 | `fear > 80` 的人本 tick 不参与传染 |
| 23 | 互助会 | 金币 > 60 的人向金币 < 10 的人转移 |

- **不要**给空法写"占位实现"（比如只改一个数字）——玩家看得出来

## P0-3 · 地图完全不影响玩法

| | |
|---|---|
| **现象** | 地图是随机生成的，但**村子在哪块地上跑完全一样** |
| **位置** | `VillageMap.arableCount` / `habitableCount` 在 `CountTerrain()` 里算出来，**全项目零引用**；`mapSeed` 只喂给渲染器 |
| **为什么是问题** | 这块工作量已经花了，但收益是 0。而且"这局为什么饿死"失去了物理解释 |
| **最小做法** | 见下（约 0.5 天） |

### 最小做法

在 `VillageLifecycleService.AdvanceGranary` 里接一步：

```
地图系数 = 当前地图的 arableCount / 参考值      ← 参考值见下
产出 = 人口/3 + 人口/4（如有耕作）… 然后 × 地图系数
```

**⚠️ 关键：先测参考值，不要拍脑袋。**

> 跑 200 个 `mapSeed`，统计 **`arableCount` 的平均值**，用它当分母。
> **必须在"生成器实际产出的地图"上测**，不能用手算的理论值——生成器里那几段
> `EnsureGrassCoverage` / `EnsureWaterCap` 会改变实际分布。

**⚠️ 第二条关键：地图的影响要压缩后再传。**

> 现在的产出系数可用窗口很窄（差 20% 村庄就从"全灭"变"活 8 个"）。
> 直接全量传递会让**大部分种子不可玩**。
> 建议：`系数 = 1000 + (实际比例 - 1000) × 0.4 / 1000`（只传 40% 的方差）。

### 验收

- 跨 100 个 `mapSeed`：**平均存活人数与"不接地图"时相差 < 5%**
- 跨 100 个 `mapSeed`：**存活人数的标准差明显变大**（地图真的在起作用）
- 连续 5 局，能看出"这局地薄所以饿死多"

### ⚠️ 不要做

- **不要**把地图接成"水格子不能走"（寻路）——18 天里不值得
- **不要**让地图影响威信回复、恐惧传染这些**第二条通道**。一条就够，两条会让调参变成二维搜索

## P0-4 · 个人存粮只有汇没有源，`生育`在开局约 800 tick 后彻底停摆

| | |
|---|---|
| **现象** | 玩到中期之后**再也不会有新生儿**，而且不会有任何报错 |
| **位置** | `VillageLifecycleService.AdvanceNeeds` 里 `villagerFood[index]--`（全项目**唯一**的写入点） |
| **根因** | `villagerFood` 只有 `--`，**没有任何 `++`**。全项目搜不到一处给它补货的代码 |
| **为什么是问题** | 见下 |

### 算一下时间线

```
开局      villagerFood 初值 8 到 40（CreateNewGame）
每 20 tick 只要 food > 0，就 food-- 并扣 5 点饥饿
→ 最耐饿的人 40 × 20 = 800 tick 之后个人存粮归零
→ 归零之后永久为 0，因为没有任何地方给它加回去
```

**连带塌掉三处：**

| 塌掉的 | 为什么 |
|---|---|
| **生育** | `CanGiveBirth` 要求 `villagerFood >= 2`。800 tick 之后**没有任何女性村民能满足这个条件**，生育完全停止（除了刚出生、初始食物为 2 的婴儿） |
| **"先吃自家的"这个设计** | `AdvanceNeeds` 里 `if (food > 0)` 分支永远走 `else`，村民从此只吃公共粮仓。"20 个米缸"的设计意图归零 |
| **幼儿夭折判定** | `ResolveInfantMortality` 里 `if (villagerFood[i] < 2) num2 += 2` **长期恒真**，所有幼儿夭折率被永久 +2，这个惩罚失去了区分度 |

### 最小做法

给个人存粮一个来源，二选一。

- **A（推荐）**。让公共粮仓的产出按比例分到个人。每 60 tick 结算 `AdvanceGranary` 时，把产出的一小部分分给存活村民，上限 40
- **B**。让「存粮」变成可以买卖的东西，金币能换粮。这样顺带把 P0-2 里金币无人读的问题也解掉一半

### 验收

- 跑 2000 tick，中期之后仍然能看到新生儿
- 随机抽 5 个村民看他们的存粮，**不应该全是 0**
- 幼儿夭折率在食物充足的局面下明显低于饥荒局面

### ⚠️ 这条和"加法条"直接冲突

**在修好之前，任何读 `villagerFood` 的新法条都是死的。** 因为那个寄存器在 800 tick 之后恒定等于 0，条件永远不成立。设计新法条时请把这条当成前置依赖。

### 一句话

技术验证报告里写过一句话，这个坑在参考实现阶段出现过**四次**。

> 任何新加寄存器、任何新加的源或汇，都必须立刻检查它的分布，而不是等到"看起来不好玩"再回头找。

`villagerFood` 是第五次。

# P1 · 结构性隐患（4 项，约 1.5 人天）

这四项**现在不会让玩家觉得有问题**，但会在最后一周集中爆炸。

## P1-1 · 模拟状态 == 存档对象

| | |
|---|---|
| **位置** | `VillageLifecycleService.Advance(VillageSaveData data, int ticks)` —— 模拟直接改存档 DTO |
| **为什么是问题** | ① 存档格式一改，模拟代码全要跟着动 ② 无法做"不计入存档"的临时状态 ③ 没法做反事实对照（同一份数据跑两遍不同律法） |
| **最小做法** | **不改架构**。只加一条纪律：**所有 `[Serializable]` 的字段，如果只服务于存档（版本号、时间戳、槽位），就不要在 `SimulateTick` 里读写** |

> 现在还没到必须重构的程度。**但"同 seed 跑两个村子"这条给评委的证明做不出来**，就是因为状态和存档绑死了。如果要做反事实对照，这一步躲不掉。

## P1-2 · `Array.Resize` 遍地，GC 会抖

| | |
|---|---|
| **位置** | `AppendChild` —— 一次生育 resize **11 个数组**；`AppendObituary` —— 一次死亡 resize **7 个数组** |
| **为什么是问题** | 手机端一次 resize 就是一次分配 + 拷贝。一局生育/死亡几十次，会在**恰好最戏剧性的时刻**（有人死）触发 GC 尖峰 |
| **最小做法** | 加一个**容量预留**：数组按 `capacity` 分配，只维护 `count`，满了再成倍扩容 |
| **验收** | Profiler 连真机跑一局，**死亡瞬间没有 GC Alloc 尖峰** |

## P1-3 · 种子用 `DateTime.UtcNow.Ticks`

| | |
|---|---|
| **位置** | `GameSession.StartNewGame`：`int seed = (int)(DateTime.UtcNow.Ticks ^ (slot * 7919)) & 0x7FFFFFFF` |
| **为什么是问题** | 新游戏不可复现。"同 seed 重开"做不了，**"同 seed 只改一条法跑出两个村子"这条给评委的核心证明也做不了** |
| **最小做法** | 保留自动生成，但**在存档列表里显示这个种子**，并允许玩家手动输入/复制种子 |

## P1-4 · 没有确定性校验

| | |
|---|---|
| **现象** | 全项目没有 `HashState` 之类的东西 |
| **为什么是问题** | 设计里"同 seed 双端逐位一致"是**整个技术的卖点**，但现在**没法验证**。双端一致性一旦破了，你不会知道 |
| **最小做法** | 加一个 `ulong HashState(VillageSaveData)`，逐字段 `Mix64` 混合。**开发期**用：**
  - 同种子跑两遍 → 哈希必须相同
  - 存盘 → 读盘 → 哈希必须相同
  - 双端（PC/Android）跑同一个种子 → 哈希必须相同 |

### ⚠️ 顺带一个真 bug 风险

`Rng.For` 里 `seed ^ (tick * 374761393) ^ ...` 用的是 **`int` 乘法**。
C# 默认 unchecked 所以不会崩，**但 `tick * 374761393` 在 tick 稍大时就会溢出**。溢出本身是确定的（没问题），
**但如果哪次编译开了 `/checked+`，行为就变了**。

→ 建议：**显式写 `unchecked`**，把意图钉死。
